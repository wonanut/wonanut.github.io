01为什么值得读 Pi

大多数 Agent 产品是黑盒：功能很多，但你很难回答三个基本问题——它每一轮到底给模型发了什么？工具结果如何回填？上下文满了以后，旧消息去了哪里？

Pi 的选择相反。它把核心压到可以完整读一遍的规模：一个通用的 agent 循环（packages/agent），一个统一的模型适配层（packages/ai），一个带 TUI、工具和会话管理的 coding agent（packages/coding-agent），以及一个终端 UI 库（packages/tui）。读完这条链，你对任何 Agent 框架都不会再陌生。

像读一台拆开的小发动机

有些产品是整车：坐进去就能开，但发动机盖焊死了。Pi 更像一台放在工作台上的小发动机：零件不多，每根管线都看得见，你甚至能换掉某个零件再点火。

类比到哪为止：发动机不会自己决定去哪；Pi 的「智能」来自模型，课程讲的是承载智能的那副骨架。

这门课不做什么

🔬 深入：为什么课程从源码读起，而不是从命令读起？

命令会变，数据结构更稳定。Pi 的 CLI 参数、TUI 快捷键和扩展 API 都在演进，但几件事长期不变：一轮 turn 由模型响应与工具结果组成；会话是带 parentId 的树；上下文压缩用摘要替换旧消息；扩展通过事件挂进生命周期。

从这些结构出发，你读任何版本都不容易迷路。具体命令只作为「如何触发某个结构」的入口。

05先自测：你对 Agent 的判断准不准

一个 Agent 产品的能力，主要由模型决定还是由 Harness 决定？

两者分工不同。模型决定「能不能想出下一步、会不会用工具」；Harness 决定「下一步能不能被执行、结果能不能回到模型、状态能不能跨轮次保存」。Pi 的哲学是：智能来自模型训练，Harness 只负责把智能接进环境。

为什么 Pi 只内置少量工具，却仍然能覆盖很多工作流？

因为工具是可执行能力的边界，不是产品能力的全部。Pi 把核心工具做得稳定、可审计，其余能力通过扩展、Skills、prompt templates 与 package 注入。核心越小，越容易验证与替换。

读源码时，最应该先找哪类信息？

先找数据流与状态边界：消息如何进入上下文、工具结果如何回填、会话如何持久化、上下文何时被压缩。函数名与行号只是入口，数据形状才是骨架。

这一讲带走

Pi 值得读，不是因为它功能少，而是因为它的每个核心职责都露在外面：循环、工具、会话、上下文。理解这四件事，你就理解了 Agent Harness 的最小骨架。

第 1 讲 · 出发之前

Pi 是什么：一台刻意做小的 Agent Harness 核心只保留循环、工具、会话与 TUI，其余能力交给扩展

大多数 Agent 产品把「能力」放进核心，Pi 反其道而行：核心只提供最小、最中性的运行时，把子代理、计划模式、权限门禁、MCP 等能力留给扩展。理解这个取舍，才看得懂后面每一层代码为什么长成这样。

01先看 Pi 自己怎么说

Pi 的 README 第一句是：“Pi is a minimal, extensible agent harness that you can make your own.” 这句话里有三个关键词：minimal（小）、extensible（可扩展）、harness（运行时框架）。它不是「更聪明的模型」，也不是「一键生成应用的平台」，而是模型与真实环境之间的那层壳。

它明确接受一个结果：子代理、计划模式这类能力默认不内置。你要，就自己写扩展，或者安装一个按你的方式实现的 package。这个选择不是「还没做完」，而是产品哲学——核心越小，你能读懂、验证和替换的部分就越多。

像一台可换零件的相机

有些相机把镜头、滤镜、闪光灯全部焊死，开机就能拍；Pi 更像一台可换镜头的机身：机身只负责快门、传感器和卡口，拍什么、怎么拍，由你装上去的镜头和附件决定。

类比到哪为止：相机换镜头不会改变机身逻辑；Pi 的扩展可以直接拦截工具调用、注入上下文，能力比「附件」更深。

02四层包结构

Pi 是一个 monorepo。对理解 harness 最重要的四个包是：

包职责你应该先读什么
packages/ai统一的多 provider LLM API：消息、内容块、流式事件、模型目录src/types.ts、provider 适配层
packages/agent通用 agent 运行时：循环、工具执行、事件流、AgentMessagesrc/agent-loop.ts、src/agent.ts
packages/coding-agent编码 Agent 产品层：工具、会话、压缩、扩展、CLI、TUIsrc/core/agent-session.ts、src/core/tools/
packages/tui终端 UI 组件与渲染只在需要自定义界面时读

这四层的关系不是「层层封装到看不见」。相反，边界很清楚：agent 只认识 AgentMessage 与工具接口，不认识文件、终端或模型厂商；coding-agent 把具体的工具、会话和 CLI 装进这个通用运行时；ai 负责把统一请求翻译成各家 API 的格式。

038 个工具，还是 4 个工具？

面试里常见的混淆点：Pi 到底有几个工具？源码里的 ToolName 联合类型一共声明了 8 个：

export type ToolName =
  | "read" | "bash" | "powershell"
  | "edit" | "write"
  | "grep" | "find" | "ls";

export function createCodingToolDefinitions(cwd: string) {
  return [
    createReadToolDefinition(cwd),
    createBashToolDefinition(cwd),
    createEditToolDefinition(cwd),
    createWriteToolDefinition(cwd),
  ];
}

所谓「Pi 的核心四件套」指的是 coding 四件套：read、bash、edit、write。另外 4 个是只读发现工具（grep、find、ls）与 Windows 的 powershell。它们同样通过工具注册表暴露给模型，只是职责更窄。

关键结论

Pi 的「小」不是工具数量少，而是核心机制少：没有内建的计划模式、子代理编排、权限门禁、MCP 管理。它把「多工具」与「多能力」区分开了。

04一台 Pi 是怎么被使用的

同一个 agent/session 核心，被包进不同的接口。你可以在终端里交互，也可以让脚本以 print / JSON 模式调用它，甚至用 SDK 在自己的进程里创建会话：

pi                         # TUI 交互模式
pi -p "解释这个仓库"        # 打印最终回复
pi --mode json -p "..."    # 输出 JSONL 事件
pi --mode rpc              # 通过 JSONL 命令控制

接口不同，底层机制相同：消息进入 active branch、构造请求、流式响应、执行工具、回填结果、必要时压缩。第 8 章会把这几条接口逐一展开。

🔬 深入：Pi 为什么不内置「计划模式」和「子代理」？

因为这两类能力高度依赖工作流与团队约定。计划模式在什么时机触发、计划写到哪个文件、是否强制人工确认；子代理用什么模型、上下文如何隔离、结果如何合并——每个团队都有自己的答案。把它们做成核心，等于把一种工作流强加给所有人。

Pi 的做法是提供稳定的扩展点：工具、事件、命令、UI、会话条目。需要时，用扩展把这些能力装上去；不需要时，核心不会为它们付出复杂度与理解成本。

05常见误区

误区一：极简就是功能弱。Pi 的核心确实小，但它通过扩展与 package 可以接入任意工具、provider、命令和 TUI 组件。功能上限由扩展生态决定，而不是核心代码量。

误区二：工具越多，Agent 越强。工具多了，模型的选择空间也变大，错误调用与上下文开销随之上升。Pi 把常用工具做精，把长尾能力放到扩展里，反而让默认行为更可预测。

06自测

说 Pi 有「8 个工具」和「4 个工具」分别指什么？

8 个是 ToolName 声明的全部内置工具：read、bash、powershell、edit、write、grep、find、ls。4 个是 createCodingToolDefinitions 返回的 coding 四件套：read、bash、edit、write。前者是工具注册表的全集，后者是默认编码工作流的核心集。

Pi 的扩展为什么能改变「核心行为」，而不只是加一个函数？

因为扩展订阅的是生命周期事件，可以拦截工具调用、修改上下文、注册工具和命令、接管 UI。它运行在 Pi 进程内，拥有与宿主相同的权限，因此能力边界远大于普通的插件回调。

如果只读一个文件来理解 Pi 的架构，应该读哪个？

先读 packages/coding-agent/docs/how-pi-works.md，再读 packages/agent/src/agent-loop.ts。前者给全局数据流，后者给循环的真实控制结构。具体工具实现可以稍后再看。

第 2 讲 · 运行时核心

Agent Loop：循环、事件与消息边界packages/agent 用两个 while 处理「工具调用」与「排队消息」

Loop 的骨架只有一件事：调用模型，如果响应里有 toolCall，就执行工具、把结果回填，再调用模型。真正复杂的是边界：什么时候停、消息从哪来、流式事件如何暴露给 UI、被截断的工具调用还能不能执行。

01两个循环，而不是一个

直觉上的 agent loop 是一个 while：有工具调用就继续，没有就停。Pi 的 runLoop 确实有这个内层循环，但外面还有一层：当 agent 本来要停下时，如果队列里来了 follow-up 消息，它要重新进入内层，把新消息当作下一轮的输入。

while (true) {
  let hasMoreToolCalls = true;

  while (hasMoreToolCalls || pendingMessages.length > 0) {
    const message = await streamAssistantResponse(...);
    const toolCalls = message.content.filter(c => c.type === "toolCall");

    const batch = await executeToolCalls(currentContext, message, config, signal, emit);
    hasMoreToolCalls = !batch.terminate;

    // 把 toolResult 追加进上下文，然后进入下一轮
  }

  const followUps = await config.getFollowUpMessages?.() || [];
  if (followUps.length > 0) { pendingMessages = followUps; continue; }
  break;
}

内层处理「这一轮要不要继续调工具」，外层处理「agent 本该停下，但用户又排了消息」。steering 消息则在当前 assistant turn 之后、下一次模型调用之前插入——它改变的是「接下来这一轮看什么」，而不是另起一个 run。

像厨师与传菜口的双循环

内层是「做一道菜」：厨师看订单、做一步、把半成品放回台面、再看下一张订单。外层是「打烊前的最后一单」：本来准备关火了，前台又递来一张单，厨房重新开火。

类比到哪为止：厨房的订单不会改变厨师的训练；Pi 的模型固定，循环只改变「给模型看什么、让它做什么」。

02消息边界：AgentMessage 不是 LLM Message

Pi 的运行时使用 AgentMessage，它比 LLM 认识的 user/assistant/toolResult 更宽：可以包含 UI 专用消息、扩展注入的 custom message、系统消息等。真正调用模型前，必须经过两道转换：

AgentMessage[]运行时状态
→
transformContext可选：裁剪/注入
→
convertToLlm过滤/转换
→
LLM Message[]发给 provider

transformContext 用来做上下文工程（裁剪旧消息、注入外部资料），convertToLlm 是必需步骤：它把运行时专有的消息类型过滤掉，或转换成模型能理解的 user/assistant/toolResult。这个边界让 agent 核心不必知道「UI 想显示什么」，也让扩展可以安全地往状态里加东西。

03事件流：UI 看到的是过程，不是结果

agentLoop 返回一个 EventStream，把内部状态变化逐条推给调用方。典型序列是：

agent_start
turn_start
message_start (user)
message_end   (user)
message_start (assistant, partial)
message_update (text_delta / toolcall_delta ...)
message_end   (assistant)
tool_execution_start
tool_execution_end
turn_end
agent_end

TUI 之所以能边生成边显示、边执行边更新工具状态，就是因为它消费这些事件；SDK 与 RPC 模式也复用同一套事件，只是序列化方式不同。核心循环本身不渲染任何东西。

工具批次还有一个容易忽略的分支：并行还是串行。Pi 默认并行执行同一批 toolCall，但只要某个工具的 executionMode 是 sequential，整批就退化为串行，避免有状态工具互相踩踏。并行结果仍按原调用顺序回填，模型看到的 toolResult 顺序与 toolCall 顺序一致。

const hasSequential = toolCalls.some(
  tc => currentContext.tools?.find(t => t.name === tc.name)?.executionMode === "sequential"
);

if (config.toolExecution === "sequential" || hasSequential) {
  return executeToolCallsSequential(...);
}
return executeToolCallsParallel(...);

并行执行不是「把 Promise.all 包一层」就结束：每个 toolCall 先做参数校验与准备，再并发执行；任一时刻 abort，未开始的任务直接产生取消错误，已经开始的工具仍需自己观察 signal。最终 Promise.all 按数组顺序收口，保证消息序稳定。

04三个容易忽略的边界

被截断的 toolCall 不能执行

如果模型因为输出 token 上限而提前结束（stopReason: "length"），流式解析出的工具参数可能是「能解析但被截断」的。Pi 的处理是：这一批工具调用全部失败，要求模型重新发出完整调用，而不是冒险执行半个参数。

abort 不是 kill -9

AbortSignal 会中止当前 run，但正在执行的工具需要自己观察 signal；文件写入这类操作还要保证锁释放前不破坏状态。第 3 章会看到 write/edit 如何用「检查 signal + 队列」避免半写。

steering 与 follow-up 的时机不同

steering 在 turn 之间插入，适合「纠正当前方向」；follow-up 在 agent 即将结束时才取，适合「追加下一件事」。把两者混用，会让 Agent 的行为变得难以预测。

🔬 深入：为什么事件流要用 async generator 风格的 EventStream？

因为循环是长时间运行的，而 UI 需要在中间状态上做响应：文本 delta、工具开始/结束、turn 边界。一次性返回最终消息会丢失这些信息，回调又容易把 UI 逻辑耦合进核心。EventStream 把「过程」变成可迭代的数据，调用方可以选择消费、转发或忽略，核心保持干净。

这也解释了为什么 TUI、print、JSON、RPC、SDK 能共用同一套机制：它们只是对事件的消费者不同。

06自测

为什么循环要分内层和外层，一个 while 不够吗？

一个 while 只能表达「工具调用没结束就继续」。外层还要处理「本来应该结束，但排队消息在结束后到达」的情况。两者触发条件不同：内层看 toolCalls，外层看 follow-up 队列。

AgentMessage 直接发给模型会怎样？

可能包含 provider 不认识的类型（UI 消息、扩展 custom message），请求会失败或被错误解析。所以必须在边界处调用 convertToLlm，过滤/转换成 user、assistant、toolResult 三种 LLM 消息。

模型返回了带 toolCall 的 length 截断消息，Pi 为什么不让工具执行？

因为工具参数可能被截断，虽然 JSON 能解析，但语义不完整。执行它可能造成误删、误写。Pi 把这一批调用全部标记为错误，提示模型重新发出完整调用，优先保证安全与可恢复。

这一讲带走

01工具定义：schema 是给模型的合同

每个工具都用一个 TypeBox schema 描述参数，再暴露 name、description、parameters、execute。description 不是注释，而是模型决定「什么时候用它」的主要依据。

const editSchema = Type.Object({
  path: Type.String({ description: "Path to the file to edit (relative or absolute)" }),
  edits: Type.Array(Type.Object({
    oldText: Type.String({ description: "Exact text for one targeted replacement..." }),
    newText: Type.String({ description: "Replacement text for this targeted edit." }),
  })),
});

注意 edits 是数组：一次调用可以改同一文件的多个不连续位置。但每个 oldText 必须唯一且不重叠，并且都针对原始文件匹配——不是「改完第一处再匹配第二处」。这避免了增量修改带来的位置漂移。

像给模型配一个分拣台

分拣台不会把整仓库的货一次倒给工人，而是按批次、按目的地送出；同一目的地的包裹还要排队，避免两件货同时塞进一个格口。工具层做的就是这套分拣与限流。

类比到哪为止：分拣台只负责出库；模型仍要自己决定「下一批拿什么」。工具只提供能力与边界，不替模型规划。

02read：先到先得的截断

read 不是把文件整段塞给模型。默认上限是两个独立约束：2000 行或 50KB，谁先到就按谁截断。截断只保留完整行，避免把多字节字符切成半个。

export const DEFAULT_MAX_LINES = 2000;
export const DEFAULT_MAX_BYTES = 50 * 1024;

// 输出会附带 next offset，提示模型继续读
[Showing lines 1-2000 of 4312. Use offset=2001 to continue.]

这不是「省 token」的小优化，而是让模型形成「分段读文件」的习惯：大文件不会被一次性展开，模型可以按需继续。图片文件则走另一条路径，作为附件发送。

03write 与 edit：同一文件的写必须排队

两个工具都通过 withFileMutationQueue 包住实际写入。队列按文件的 realpath 建立：同一个文件的操作串行，不同文件的操作并行。

const fileMutationQueues = new Map<string, Promise<void>>();

export async function withFileMutationQueue<T>(
  filePath: string,
  fn: () => Promise<T>,
): Promise<T> {
  const key = await getMutationQueueKey(filePath); // realpath
  const current = fileMutationQueues.get(key) ?? Promise.resolve();
  // ...排队，执行 fn，最后释放
}

为什么不用一把全局锁？因为两个工具同时改不同文件是安全的，全局锁会把并行变成串行，拖慢整个 agent。为什么不用「文件不存在就跳过」？因为 realpath 失败时仍要回退到解析后的路径，避免同一个尚未创建的文件被两个操作同时写。

abort 时不要提前释放锁

write 的实现没有在 abort 监听器里直接 reject，而是在每个 await 之后检查 signal.aborted。否则队列会在文件操作还没结束时被释放，另一个写操作可能插进来，造成半写或覆盖。

04bash：退出码、超时与截断

bash 的工程细节集中在「失败如何表达」。非零退出码不是抛异常，而是返回带 isError: true 的工具结果，让模型看到错误并自行修复；超时则是一个可选的、有上限的设置。

输出同样会被截断。bash 的尾部截断有一个边界：如果最后一行本身不完整，可能需要特殊处理；这也是为什么工具层不直接返回原始字符串，而是返回结构化的内容块。

超时参数以秒为单位，有最大值上限；超时不是简单 kill，而是把「超时」表达成一次失败的工具结果，附带已经积累的输出。这样模型能看到「跑到哪一步超时」，而不是只收到一个空错误。

05路径与只读发现工具

所有文件工具都通过 resolveToCwd 把相对路径解析到当前会话的工作目录，而不是进程启动目录。这让同一个 Pi 进程可以安全地打开不同 cwd 的会话。

grep、find、ls 是只读发现工具：它们不做修改，因此不需要 mutation queue，但仍受输出截断与路径解析约束。powershell 则是 Windows 上的 bash 等价物，接口形状保持一致。

🔬 深入：为什么 edit 的多个 oldText 不允许重叠？

如果允许重叠，两个替换可能互相影响同一段原文，最终结果取决于执行顺序；而模型给出的 edits 是一个集合，没有可靠顺序。Pi 直接禁止重叠，让每次编辑都可以独立地在原始内容上定位，结果确定且可验证。

相近的修改应该合并成一个更大的 edit，而不是拆成多个相邻片段。这条约束写在工具 description 里，也是模型需要学会的「工具使用习惯」。

07自测

read 的截断为什么必须「只保留完整行」？

因为半个多字节字符或半个语法结构会误导模型，也可能让后续编辑的 oldText 无法匹配。只保留完整行能保证输出是可读、可引用的文本单元。

同一文件的两个 edit 并发时，Pi 用什么保证结果确定？

用按 realpath 建立的 per-file mutation queue。两个操作排队执行，后一个看到的是前一个完成后的文件状态；不同文件仍然可以并行。

bash 非零退出为什么不算「工具崩溃」？

因为命令失败是 agent 工作流的一部分：编译报错、测试失败都需要模型看到输出并修复。Pi 把它表达为带 error 标记的工具结果，而不是中断循环的异常。

01为什么不是消息数组

线性消息数组的隐含假设是：你永远只会沿着一条路往下走。但真实工作里，人经常想「回到刚才那个点，换一种做法」。如果直接截断数组，被放弃的方案就丢失了；如果复制整个会话，又会得到一堆互不相关的文件。

Pi 的选择是树：每个条目有唯一 id，并记录 parentId；从根到当前叶子的路径就是 active branch。回到旧节点再提交，会从那个节点长出一条新分支，旧分支原地保留。

像 Git 的提交图，而不是一条时间线

Git 允许你从旧提交开新分支，旧提交不会消失。Pi 的会话树也是这样：parentId 是「从哪来」，id 是「现在在哪」。模型每次只看到当前分支，但你可以随时切回另一条。

类比到哪为止：Git 合并分支；Pi 不自动合并，切分支时可以选择把旧分支总结成一段 branch summary，再带进新分支。

02文件长什么样

会话文件是 JSONL：第一行是 header，之后每行一个树节点。版本 3 使用 id/parentId 表达树结构。

{"type":"session","version":3,"id":"uuid","timestamp":"...","cwd":"/project"}
{"type":"message","id":"a0b1c2d3","parentId":null,"timestamp":"...","message":{"role":"user","content":"Hello",...}}
{"type":"message","id":"b2c3d4e5","parentId":"a0b1c2d3","timestamp":"...","message":{"role":"assistant",...}}
{"type":"compaction","id":"f6g7h8i9","parentId":"e5f6g7h8","timestamp":"...","summary":"...","firstKeptEntryId":"c3d4e5f6"}

除了普通 message，还有 model_change、thinking_level_change、usage、context_edit、branch_summary、custom、custom_message 等条目。它们有的参与模型上下文，有的只用于 UI/统计，有的只用于扩展状态。读文件时先看 type，再看它是否进入 active branch。

03SessionManager 负责什么

SessionManager 不是简单的 append-only 日志：它维护树、当前叶子、分支切换、压缩与导出。对使用者而言，几个命令对应几个动作：

import { createAgentSession, SessionManager } from "@earendil-works/pi-coding-agent";

const { session } = await createAgentSession({
  sessionManager: SessionManager.inMemory(), // 或持久化 manager
});

console.log(session.messages);   // 当前 active branch 的消息
await session.prompt("继续上一轮的工作");

会话的工作目录在创建时固定，之后不随进程 cwd 改变。这一点很关键：工具、@path 引用、项目配置和 context files 都相对会话 cwd 解析。打开另一个目录的会话时，要么继续使用原 cwd，要么 fork 到当前目录。

在实现层，SessionManager 的核心操作只有几个：appendMessage() 追加消息、branch(id) 把 leaf 移到旧节点、branchWithSummary() 在移动的同时写一条 branch summary、appendCompaction() 追加压缩条目。append-only 是它的基本约定：已有条目从不原地修改，所有变化都是新节点。

class SessionManager {
  appendMessage(message: Message): string;
  branch(branchFromId: string): void;          // leaf 移回旧节点
  branchWithSummary(fromId: string | null, summary: string): void;
  appendCompaction(firstKeptEntryId: string | null, summary: string): string;
  appendContextEdit(targetId: string, replacement: string | null): string;
  getActiveBranch(): SessionEntry[];
}

context_edit 特别值得注意：它不修改目标消息，而是在当前分支追加一个「未来请求里如何处理该消息」的编辑。target 为 replacement: null 表示在后续上下文中省略它；非空则替换内容。原始条目和元数据保持不变，导出/审计仍能看到原貌。

04压缩与会话树的关系

压缩不是删除旧节点，而是在当前分支上追加一个 CompactionEntry。它保存摘要和 firstKeptEntryId：重建上下文时，摘要替换更早的消息，从 firstKeptEntryId 开始保留。原始条目仍然在文件里，可用于导出、审计或未来的 context_edit。

切换分支时，Pi 还可以生成 BranchSummaryEntry，把被放弃路径的工作总结后挂到新分支上。这样既保留了「另一条路试过什么」，又不会把整条旧分支塞回上下文。

🔬 深入：为什么压缩条目要带 firstKeptEntryId，而不是直接存一个新的消息数组？

因为会话树需要保持可导航。如果压缩直接写一个新的消息数组，就丢失了「旧条目与保留条目之间的父子关系」，也无法在 UI 里回到压缩前的位置。用 firstKeptEntryId 标记保留边界，压缩就只是「在树上追加一个读法」，而不是「重写历史」。

重复压缩时，新的 summarized span 会从上次的保留边界开始，而不是从压缩条目本身开始，这样之前幸存的消息还会被再次纳入摘要，不会出现「压缩边界之前的内容永远丢失」。

05常见误区

「会话文件就是模型上下文」。不是。模型只看到 active branch 经转换/压缩后的投影；文件里有大量不参与上下文的内容，例如 usage、custom entry、被 context_edit 省略的消息。

「切分支会丢消息」。不会。旧分支仍在树里，只是不在当前 active branch；你可以切回去，也可以选择生成摘要带走。

06自测

一个会话文件里有 10 条消息，模型这次会看到几条？

不一定 10 条。模型只收到 active branch 的投影：可能经过 context_edit 省略、compaction 摘要替换，以及 convertToLlm 过滤。文件里的条目数不等于上下文里的消息数。

为什么会话的 cwd 要在创建时固定？

因为工具、路径解析、项目配置与 context files 都依赖它。如果 cwd 随进程变化，同一个会话在不同时刻可能读写不同目录，导致结果不可复现、甚至改错仓库。

压缩之后，原始旧消息还在吗？

还在。压缩只是追加一个 CompactionEntry，原始条目保留在 JSONL 中；重建上下文时旧消息被摘要替换，但文件、导出与审计仍然能看到它们。

会话树是 Pi 的「长期记忆」：它用 id/parentId 保存所有探索，用 active branch 决定模型看到什么，用压缩条目在不删历史的前提下控制上下文。理解这棵树，才能理解 Pi 的恢复、分支与审计。

01什么时候压？

Pi 的自动压缩触发条件很直接：

contextTokens > contextWindow - reserveTokens

默认 reserveTokens   = 16384
默认 keepRecentTokens = 20000

reserveTokens 是留给「下一步还要输出」的空间，不是保留的历史；keepRecentTokens 才是压缩时尽量保留的最近消息预算。两者名字相近，作用完全不同。触发点在一轮工具结束、结果追加之后，下一次模型调用之前检查——因为工具结果往往是把上下文撑爆的最后一根稻草。

像给行李箱做减量打包

行李箱装不下时，你不会把最近要用的东西扔掉；你会把早期衣物压缩成收纳袋，留下最近几天要穿的。压缩摘要就是那个收纳袋，保留边界就是「从哪件衣服开始不压缩」。

类比到哪为止：收纳袋里的东西仍能打开查看；Pi 的原始消息也仍在会话树里，只是不再进入下一轮模型请求。

02怎么压：从后往前找切点

03压缩条目长什么样

压缩的结果不是一段拼接文本，而是一个有结构的会话条目：

interface CompactionEntry {
  type: "compaction";
  id: string;
  parentId: string | null;
  summary: string;
  firstKeptEntryId: string;
  tokensBefore: number;
  usage?: Usage;
  details?: CompactionDetails;
}

其中 firstKeptEntryId 是重建上下文的关键：它之前的消息被摘要替代，它之后的消息原样保留。保留边界可能落在一条助手消息上（当一个用户消息 span 本身超预算时），这时 Pi 会分别总结「更早历史」和「当前 span 的前半段」，再合并。

实现上分成两步：prepareCompaction() 负责找切点、估算 token、收集待摘要消息；compact() 负责调用模型生成摘要、写入 CompactionEntry，并记录本次摘要的 usage 与文件追踪信息。摘要生成走 generateSummaryWithUsage()，因此压缩本身也会计入会话 token/cost。

prepareCompaction(session, settings)
  -> { messagesToSummarize, turnPrefixMessages, firstKeptEntryId, isSplitTurn }

compact(...)
  -> generateSummaryWithUsage(...)
  -> append CompactionEntry(summary, firstKeptEntryId, tokensBefore, usage, details)

默认的 details 会累积 readFiles 与 modifiedFiles，这样压缩之后仍能告诉模型「哪些文件被读过/改过」。扩展可以替换压缩逻辑，并把自己的 details 结构写进同一个条目。

04压缩失败与溢出恢复

压缩本身也是一次 LLM 调用，可能失败。Pi 不会因此丢掉会话：失败时保留原始上下文，提示用户修正 provider 或稍后重试。对于 provider 的 context-overflow 错误，或提前出现的 stopReason: "length"，Pi 还有一次「压缩后重试」的恢复机会。

压缩请求不写 prompt cache

摘要请求通常是一次性的，不太可能复用。Pi 在压缩请求中禁用 cache write，避免为一次性的摘要付出缓存写入成本。

05branch summary：换条路时带走经验

压缩解决「当前分支太长」，branch summary 解决「我要离开当前分支，但不想丢掉这段工作」。用 /tree 切到另一条路径时，Pi 可以总结被放弃的分支，把摘要挂到新分支上。它和压缩共用结构化摘要与文件追踪，但触发场景不同。

🔬 深入：为什么压缩不直接生成一堆新消息，而是只追加一个 entry？

因为会话是树，树需要保留导航能力。如果压缩重写消息数组，就无法再从压缩前的节点切回旧分支，也无法审计「模型当时到底看到了什么」。只追加一个 entry，并把「模型从哪开始读」编码进 firstKeptEntryId，压缩就变成一次可逆的读法变化。

重复压缩时，新的摘要从上次保留边界开始，而不是从压缩条目本身开始，避免把之前幸存的消息永久排除在摘要之外。

06动手实验

  1. 手动压缩：在一个长会话里执行 /compact 保留所有关于认证的决策，然后查看会话 JSONL，找到新增的 compaction entry 与 firstKeptEntryId。
  2. 制造溢出：用一个大文件把上下文推过阈值，观察自动压缩发生在工具结果之后还是下一次 prompt 之前；再对比关闭自动压缩时的行为。

07自测

reserveTokens 是「保留的历史」吗？

不是。reserveTokens 是为下一次模型输出预留的空间，触发条件是「已用上下文 + reserve 超过窗口」。保留多少历史由 keepRecentTokens 控制。

为什么切点不能落在 tool result 上？

tool result 必须紧跟对应的 toolCall 才能被模型正确理解。切在 tool result 上会导致保留的消息以一条孤立的工具结果开头，模型无法把它和调用关联起来。

压缩后原始消息还能找回吗？

能。原始 entry 保留在 JSONL 树中；压缩只是改变后续请求的投影。UI、导出、审计仍可访问旧条目，context_edit 也可以对它们做后续处理。

这一讲带走

压缩不是「删历史」，而是「在树上增加一个读法」：摘要替换旧消息，firstKeptEntryId 标记保留起点，原始证据不动。理解这一点，你才能安全地设计长跑 Agent 的上下文策略。

扩展系统：在进程内改造 Pi 扩展不是沙箱插件，而是能订阅生命周期、注册工具与命令的 TypeScript 模块

01扩展是什么

扩展是一个导出默认工厂函数的 TypeScript/JavaScript 模块，工厂收到 ExtensionAPI。它在 Pi 进程内运行，通过 pi.on(...) 订阅生命周期事件，通过 pi.registerTool()、registerCommand()、registerShortcut() 添加能力。

import { type ExtensionAPI, isToolCallEventType } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  pi.on("tool_call", async (event, ctx) => {
    if (isToolCallEventType("bash", event) && event.input.command.includes("rm -rf")) {
      const ok = await ctx.ui.confirm("危险命令", "允许执行 rm -rf？");
      if (!ok) return { block: true, reason: "用户拒绝" };
    }
  });

  pi.registerTool({
    name: "greet",
    label: "Greet",
    description: "Greet someone by name",
    parameters: Type.Object({ name: Type.String() }),
    async execute(_id, params) {
      return { content: [{ type: "text", text: `Hello, ${params.name}!` }] };
    },
  });
}

这段代码同时展示了两种扩展点：拦截（tool_call 事件可以阻止或修改调用）与新增（注册一个模型可调用的工具）。权限门禁、路径保护、git checkpoint 都属于前者；自定义工具、外部系统连接属于后者。

像给笔记本接扩展坞

笔记本本身只保留核心接口；需要网口、读卡器、外接屏时，通过扩展坞接入。扩展坞不是笔记本的一部分，但能直接使用同一套电源与总线。

类比到哪为止：扩展坞通常受硬件隔离；Pi 的扩展与宿主同进程、同权限，所以「信任来源」比接口本身更重要。

03加载位置与热重载

扩展可以放在全局目录、项目目录，或通过 pi -e ./path.ts 临时加载：

~/.pi/agent/extensions/*.ts        # 全局，所有项目
<project>/.pi/extensions/*.ts      # 项目级，项目被信任后才加载
pi -e ./my-extension.ts            # 临时测试
/reload                            # 热重载自动发现目录中的扩展

项目级扩展只有在项目被 trust 之后才会加载，这是安全模型的一部分：扩展能读文件、执行命令，不能对不受信任的仓库自动放权。

事件不是「通知」，而是有顺序的钩子链：启动期有 project_trust、session_start、resources_discover；运行期有 turn_start / turn_end、tool_call / tool_result、message_*、session_before_compact 等。多个 handler 按注册顺序组合，返回值（如 block、修改后的参数或上下文）会继续传给后续 handler 与核心循环。

写扩展时最容易犯的错，是在 tool_call 里做耗时 I/O 却没有处理取消；Pi 的 run 可能被用户 abort，扩展也应观察 signal，否则会把整个会话卡住。事件处理应当短小、可重入，把重活交给工具或后台任务。

04状态：custom entry 与 custom message

扩展如果需要在会话里保存状态，可以用 pi.appendEntry() 写入 custom entry。它会被持久化到 JSONL，但不参与模型上下文。若需要注入模型可见的内容，则使用 custom message；后者会经过 convertToLlm，成为模型输入的一部分。

区分「给 UI 的状态」与「给模型的上下文」

把扩展状态都塞进模型上下文，会浪费 token 并干扰推理；反过来，把该让模型知道的信息只存 UI，也会让它失去关键上下文。Pi 用两种 entry 把这两件事分开。

🔬 深入：为什么扩展能「阻止」工具调用，而不是只能在执行后补救？

因为 tool_call 事件发生在真正执行之前。扩展可以返回 { block: true, reason }，Pi 会把这次调用变成错误结果回填给模型，而不是执行工具。这样权限门禁、路径保护、危险命令确认都能在副作用发生前生效。

代价是扩展拥有了很大的权力：它可以放行、拒绝、修改参数。Pi 的应对不是沙箱（扩展仍在同一进程），而是 trust 机制与「只加载可信来源」的约定。

05常见误区

「扩展是安全的沙箱插件」。不是。扩展运行在 Pi 进程内，拥有同样的 OS 权限，能读凭据、会话与文件。只加载你信任的扩展。

「扩展只能加工具」。它还能拦截事件、注册命令、控制 UI、注册 provider 与 MCP server、持久化状态。工具只是其中一种能力。

06自测

想阻止对 .env 的写入，应该挂哪个事件？

挂 tool_call，判断是否为 edit/write 且路径指向 .env，然后返回 { block: true, reason }。这样在文件被改之前就阻止，而不是事后恢复。

扩展状态应该存 custom entry 还是 custom message？

取决于模型是否需要看到。只需要持久化给扩展自己/UI 用的状态，用 custom entry；需要进入模型上下文的，用 custom message。前者不影响 token，后者会参与请求。

为什么项目级扩展要等 trust 之后才加载？

因为扩展能执行任意代码、读取凭据和文件。如果打开一个不受信任的仓库就自动加载它的扩展，等于让仓库作者在你的机器上执行代码。

这一讲带走

扩展系统是 Pi「极简核心」的另一半：核心提供稳定的生命周期与注册点，扩展把能力装进去。理解事件顺序与两种 entry，你就能在不修改核心的情况下改造 Pi，同时清楚它的信任边界。

01Skill 不是一个函数，而是一份说明书

Skill 是一个目录，核心是 SKILL.md：YAML frontmatter 加正文。前面可以放脚本、参考文档、模板等支持文件。模型看到的不是全文，而是名称、描述和路径；需要时再读。

---
name: pdf-tools
description: Extract text and tables from PDF files. Use when reading, converting, or inspecting PDFs.
---

# PDF tools

Read `references/formats.md` before converting a document.
Run scripts relative to this skill directory.

description 是最重要的字段：它决定模型在什么时候会想起这个 Skill。写「Helps with PDFs」几乎没有路由信息；写清「做什么 + 什么时候用」，才有机会被正确加载。

像图书馆的索引卡，而不是把书全搬来

Skills 启动时只给模型看索引卡：书名（name）、简介（description）、书架位置（path）。模型需要时再按位置取书，读完把关键内容带回工作台。

类比到哪为止：图书馆不会因为你看过索引就自动把书打开；Pi 需要模型主动读取 SKILL.md，或用 /skill:name 强制加载。

02发现与加载

Pi 扫描用户级与项目级目录，把每个 Skill 的名称、描述、路径加入系统提示；完整指令只在任务匹配时读取。常用位置包括：

~/.pi/agent/skills/
<project>/.pi/skills/
~/.agents/skills/
<project>/.agents/skills/

项目级 Skills 会从当前工作目录向上查找，直到仓库根；它们同样受 trust 约束。手动强制加载用 /skill:name，后面的参数会作为用户请求追加到指令之后。

03Skills 之外：prompt templates 与 packages

Prompt template

一段可复用的消息文本，适合「每次都要用同样的话开头」的场景。它在输入阶段展开，不涉及工具执行。

Pi package

把 extensions、skills、templates、themes 打包，通过 npm 或 git 分发。适合团队共享一整套工作方式。

Theme

只影响终端配色与显示，不改变 Agent 行为。它和 Skills 一样，是「资源」而不是「运行时机制」。

三者的共同点是：都不需要改 Pi 核心。区别在于注入点不同——template 改输入，skill 改知识上下文，package 负责分发。

04什么时候不该用 Skill

如果一件事需要新的可执行能力（调用内部 API、写数据库、注册工具），它应该写成扩展，而不是 Skill。Skill 适合「需要一套知识/流程/脚本」但不需要新工具注册的场景。判断标准：模型缺的是「知道怎么做」，还是「有办法做」？

🔬 深入：为什么 Skill 的 description 比正文还重要？

因为正文只有在被选中后才会加载。启动时模型看到的只有 name、description、path；它必须根据 description 判断「这个任务是否属于该 Skill 的适用范围」。描述写得太泛，会导致该加载时没加载；写得太窄，会导致误判。

这也是为什么规范建议描述里同时写「能力」与「触发条件」，并避免「Helps with X」这类没有路由信息的表述。

05自测

Skill 启动时会把 SKILL.md 全文放进系统提示吗？

不会。启动时只加入名称、描述和路径；完整指令在任务匹配时由模型读取，或用 /skill:name 手动加载。这正是它节省上下文的原因。

需要让模型调用公司内部工单 API，应该用 Skill 还是扩展？

扩展。因为它需要一个新的可执行工具与认证/网络逻辑；Skill 只能提供知识与流程，不能替模型注册并执行新工具。

为什么项目级 Skill 也要等项目被信任？

因为 Skill 可以指示模型运行脚本、读取文件，支持文件也可能包含可执行内容。不受信任的仓库不应自动把这种指令注入 Agent。

01五种接口，一套核心

Pi 的交互方式由两个维度决定：是否一次性执行（print）与输出协议（text / json / rpc / sdk）。但它们共享同一套 AgentSession、工具与会话管理。

接口启动方式典型场景
TUIpi人类交互、查看工具过程
Printpi -p "..."脚本里只要最终答复
JSONpi --mode json "..."消费完整事件流、做可视化/审计
RPCpi --mode rpc其他语言的宿主进程控制 Pi
SDKcreateAgentSession()在自己的 Node/Bun 应用内嵌入 Pi
像同一台服务器，不同的客户端

数据库本身只有一套存储与查询逻辑；命令行、GUI、API 只是不同客户端。Pi 的 TUI、print、JSON、RPC、SDK 也是这样：换的是「怎么发起请求、怎么看结果」，不换核心。

02CLI：最短的三条命令

pi --print "总结这个仓库的架构"
git diff | pi --print "review 这次改动"
pi --mode json "检查当前目录" > events.jsonl

--print 只输出最终回答；--mode json 输出逐条事件，适合被程序消费。两者共享同一套工具与会话，只是输出层不同。注意 JSON 与 RPC 模式会占用 stdout 作为协议通道，不能混入其他打印。

03SDK：把 Pi 嵌进应用

如果宿主本身就是 TypeScript，SDK 是最直接的方式。它创建一个 AgentSession，你负责 prompt、订阅事件、最后 dispose。

import { createAgentSession } from "@earendil-works/pi-coding-agent";

const { session } = await createAgentSession();

const unsubscribe = session.subscribe((event) => {
  if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});

try {
  await session.prompt("解释这个仓库的入口");
} finally {
  unsubscribe();
  session.dispose();
}

prompt() 在 run 结束后 resolve；流式输出靠订阅事件，而不是把回调塞进 prompt。若 prompt 在流式过程中到达，必须明确要 steer 还是 follow-up，不能靠猜。

04安全边界：trust、cwd 与进程权限

Pi 的信任模型很直接：先决定项目是否 trust，再加载项目级设置、扩展与资源；trust 之后再加载 context files。扩展运行在 Pi 进程内，拥有与宿主相同的 OS 权限；工具也使用进程权限。Pi 本身不是沙箱。

不要把「极简」误读成「安全隔离」

Pi 的核心代码少，不等于它运行在受限环境里。要隔离，需要容器、虚拟机或操作系统级沙箱；扩展与工具默认都能接触真实文件与凭据。

会话 cwd 在创建时固定，工具与 @path 都相对它解析；这保证了同一会话的行为可复现，也避免了「打开另一个目录的会话却改错仓库」。

05什么时候选哪一种

人用

选 TUI。你需要看工具调用、diff、确认与中断，这些过程信息比最终文本更重要。

脚本/CI

选 print 或 JSON。只要结果用 print；要审计过程、做可视化或回放，用 JSON 事件流。

宿主应用

进程内用 SDK，跨语言/隔离用 RPC。两者都能拿到事件，但 RPC 多了序列化与进程边界。

🔬 深入：为什么 SDK 的 prompt() 不直接返回流式回调？

因为一次 run 可能包含多次模型调用与工具执行，最终答案只是其中一部分。把过程做成事件流，宿主可以按需处理文本 delta、工具状态、压缩和重试；prompt() 只承诺「run 结束」。这也是 TUI、JSON、RPC 与 SDK 能共享核心的原因。

另外，steering 与 follow-up 的语义要求宿主明确消息进入的时机；一个简单的回调参数无法表达这种队列语义。

06自测

CI 里只要最终文本，应该用哪个接口？

pi --print（或 -p）。它运行一次并只输出最终 assistant 文本，适合脚本取结果；需要过程就用 --mode json。

为什么 JSON 和 RPC 模式不能混入普通日志打印？

因为 stdout 被保留为协议通道，混入普通文本会破坏 JSONL 解析。日志应走 stderr 或宿主自己的日志系统。

Pi 的核心小，是否意味着扩展是安全的？

不是。扩展在 Pi 进程内运行，拥有相同的系统权限，能读凭据、文件与会话。安全来自信任来源与外部沙箱，而不是核心代码量。

这一讲带走

接口只是消费者：TUI、print、JSON、RPC、SDK 共享同一个 AgentSession 与事件流。选型看场景，安全看信任边界；不要因为 Pi 小就误以为它默认隔离。

01先给差异一个准确的框架

不要说「Pi 是开源的 Claude Code」——它们解决的是同一个问题，但组织方式不同。Pi 把能力做成可插拔扩展，Claude Code 把常用能力做成内建体验。前者把选择权交给使用者，后者把默认体验做到开箱即用。

这张表不是裁判，而是选型工具：你越需要「审计每一条消息、替换每一层、把 Agent 嵌进自己的系统」，越适合 Pi；你越需要「今天就让团队用起来、少踩坑」，越适合成熟集成产品。

像买车与组装车

买整车：提车即开，维修保养有成熟体系，但每个零件长什么样你未必清楚。组装车：你可以选发动机、悬挂与电控，代价是得自己调校、自己排障。

类比到哪为止：车最终都要上路；Agent 的「路况」是具体业务，选整车还是组装车，取决于你是否愿意维护那套调校能力。

02能力放在哪：三个判断问题

  1. 这件事需要新的执行能力吗？需要 → 扩展/工具；只是知识与流程 → Skill。
  2. 它需要跨会话保存状态吗？需要 → custom entry 或外部存储；只影响当前上下文 → custom message / context 注入。
  3. 它必须在副作用前拦截吗？是 → tool_call 事件；事后补偿 → 其他生命周期事件。

03结课项目：给 Pi 加一个「写前确认」扩展

目标：在模型执行 write/edit 之前，对匹配敏感路径的修改弹确认；拒绝时返回错误结果，让模型知道被阻止。这个项目覆盖了本课最重要的三块：事件、工具 schema、UI。

import type { ExtensionAPI, isToolCallEventType } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  const protectedPaths = [".env", ".git/", "node_modules/"];

  pi.on("tool_call", async (event, ctx) => {
    const tool = event.toolName;
    if (tool !== "write" && tool !== "edit") return;

    const path = String(event.input?.path ?? "");
    if (!protectedPaths.some((p) => path.includes(p))) return;

    const ok = await ctx.ui.confirm(
      "受保护路径",
      `${tool} 将修改 ${path}，确认继续？`,
    );
    if (!ok) return { block: true, reason: "受保护路径被拒绝" };
  });
}

把它放到 ~/.pi/agent/extensions/guard.ts，重启 Pi 或执行 /reload。再让模型尝试写 .env，观察确认框与拒绝后的工具结果。最后把「哪些路径受保护」做成设置项，理解扩展如何读取配置并与 UI 协作。

🔬 深入：为什么说「极简」本身不是卖点？

代码少不等于好。极简的价值在于：你能完整理解它、验证它、替换它；代价是很多能力要自己组装。如果一个团队没有维护 harness 的意愿，极简反而会变成负担。

所以选型时不要问「谁更先进」，要问「谁把复杂度放在了我们能承受的地方」。Pi 把复杂度放在扩展与集成层，Claude Code 把复杂度收进产品内部——两种都合理，取决于你的团队。

07自测

Pi 与 Claude Code 的核心差异，应该怎么表述才准确？

不是「开源 vs 闭源」或「强 vs 弱」，而是能力放置位置：Pi 把非核心能力放到扩展与资源层，Claude Code 把常用能力收进内建产品体验。前者换取可改造性，后者换开箱即用。

团队没有维护扩展的意愿，还适合 Pi 吗？

未必。Pi 的价值依赖「有人组装与维护工作流」。如果团队更看重稳定、开箱即用，成熟集成产品可能更合适。选型要看组织能力，而不是只看架构优雅。

结课项目里，为什么拒绝写操作要返回 block，而不是直接抛异常？

因为需要让模型看到「这次调用被阻止了，以及原因」，从而调整策略。返回 block + reason 会变成工具错误结果进入循环；抛未处理异常可能中断整个 run。
