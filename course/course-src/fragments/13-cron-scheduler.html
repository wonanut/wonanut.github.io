01“每天早上九点”是一个 Agent 自己回答不了的问题

s11 让慢命令在后台跑，但它的启动时机仍然是“模型决定调用工具的那一瞬间”。如果用户说“每天早上九点跑一遍测试，把结果发我”，模型能做的只有：把这句话理解成一项未来的工作，但当前进程里没有任何东西会在明天九点把它叫醒。Agent 进程关掉，一切归零；进程不关，它也只会傻等用户输入。

这件事不能靠模型“记住时间”。模型没有持续运行的时钟，它只在被调用时存在；即使你在 system prompt 里写“现在是 8:59，请等到 9:00”，它也没有办法在两轮对话之间自己醒来。定时能力必须由 harness 提供：一个长期运行的调度器，持续看表，到点把工作塞进某个队列，再找合适的时机交给 Agent。

这里有个关键区分：后台任务解决“怎么执行”，定时任务解决“什么时候开始执行”。前者是执行模型，后者是触发模型。把两者混为一谈，就会写出“后台线程里 sleep 到九点”这种实现——它能跑，但进程重启就丢，而且每个任务占一个线程。

还有一个设计选择值得提前说：调度器用“每秒轮询”而不是“算出下一次触发时间再 sleep”。轮询实现简单、对系统时间跳变不敏感，但代价是每秒唤醒一次；“算下一次”更省 CPU，却要处理夏令时、时钟回拨、任务新增后重算等一系列麻烦。教学版选简单的那条路，生产系统通常会选省电的那条。

注意

本章的调度器用的是 Agent 进程的本地时间，而且进程一关调度线程就停。durable 持久化只保住“任务定义”，不会在你关机期间替你执行。想要真正的“关掉电脑也准时跑”，得用系统 crontab、systemd timer 或外部调度服务。

02直觉：一个 CronJob，就是一张写清时间的任务卡

s12 的设计可以概括成一句话：把“什么时候”和“做什么”存成一条记录，用一个线程每秒看表，到点就排队，Agent 空了再交付。记录就是 CronJob，它只有七个字段，但每个都对应一个真实问题。

像医院预约挂号叫号

你预约了九点的号（cron 表达式），到点时护士把你的号放进候诊队列（cron_queue），但医生正在看诊时不会打断（agent_lock）；医生看完手头这位，才叫下一个号（空闲后交付）。你预约的是“九点开始排队”，不是“九点整被接诊”。

类比到哪为止：医院有护士盯着钟、有真实的人在处理突发情况；这里的“护士”是一个每秒轮询的线程，而且它只认本地时间。更要命的是，医院不会因为你迟到就作废预约，而本章的调度器在进程关闭期间不会补号——错过了就是错过了。这个差异是“教学版”和“生产版”最大的分界线。

为什么非要“先入队、再等空闲”，而不是匹配到时直接启动一轮 Agent？因为 Agent 的会话是单线程状态机：messages[] 正在被用户的一轮对话修改时，突然插进来一轮定时任务，两条时间线会同时往同一个数组里追加消息，消息顺序和 tool_use / tool_result 的配对都会乱。队列把“时间到了”和“可以执行”解耦：调度线程只负责发现，队列处理线程只负责在安全时机交付。

字段含义防的是什么
cron五段式时间表达式“什么时候触发”不可描述
prompt触发后交给 Agent 的任务到点后不知道要做什么
recurring周期任务 or 一次性任务一次性任务被反复触发
durable是否写进 .scheduled_tasks.json进程重启后任务定义丢失
pending_delivery已到期但还没被模型接收同一分钟重复入队、丢任务
last_fired上次触发的分钟标记一秒一轮询导致同一分钟多次触发

三条线程，各干一件小事

整章的后台结构只有三条线程，职责被切得很干净：

  • 主线程：读用户输入，拿 agent_lock 跑一轮对话。
  • 调度线程（cron-scheduler）：每秒 poll_due_jobs(datetime.now())，只判断“有没有任务到期”。
  • 队列处理线程（cron-queue-processor）：每 0.2 秒看一眼队列，抢到锁就启动一轮 Agent。

三条线程共享 cron_lock（保护任务字典与队列）和 agent_lock（保护会话）。把“看时间”“看队列”“改会话”分成三件事，是这段代码能读下去的主要原因：没有哪个函数同时操心所有事。

理解这个分工之后，后面读代码就不会再问“为什么调度线程不直接跑 Agent”——它只负责发现，交付是另一条线程的事。

03代码精读：五段式 cron 怎么匹配

先看数据结构。七个字段里，前四个决定“能不能触发”，后两个是运行时状态：pending_delivery 表示“已经到期、正在队列里或等待确认”，last_fired 记录上次触发的分钟（格式 YYYY-MM-DD HH:MM）。

@dataclass
class CronJob:
    id: str
    cron: str
    prompt: str
    recurring: bool
    durable: bool
    pending_delivery: bool = False
    last_fired: str | None = None

五段式表达式的顺序是“分钟 小时 日 月 星期”，一个星期从 0 开始（周日）。cron_matches() 把当前时间拆成五个数值逐一比较，其中星期需要一次转换：Python 的 datetime.weekday() 里周一是 0，而 cron 里周日是 0，所以 (moment.weekday() + 1) % 7。

这个 +1 取模看着不起眼，却是一类经典 bug 的来源：不做转换的话，“每周一”的表达式会在周二触发，而且差一天的错误很难靠肉眼发现。凡是“两套编号体系对接”的地方，都值得单独写一行测试。

def cron_matches(cron_expr: str, moment: datetime) -> bool:
    fields = cron_expr.strip().split()
    if len(fields) != 5:
        return False
    minute, hour, day, month, weekday = fields
    cron_weekday = (moment.weekday() + 1) % 7
    if not (
        _cron_field_matches(minute, moment.minute)
        and _cron_field_matches(hour, moment.hour)
        and _cron_field_matches(month, moment.month)
    ):
        return False
    day_matches = _cron_field_matches(day, moment.day)
    weekday_matches = _cron_field_matches(weekday, cron_weekday)
    if day == "*" and weekday == "*":
        return True
    if day == "*":
        return weekday_matches
    if weekday == "*":
        return day_matches
    return day_matches or weekday_matches

最后四行是整段代码里最容易被忽略、也最容易写错的部分：当“日”和“星期”都有限制时，标准 cron 的语义是或，不是与。比如 0 9 1 * 1 表示“每月 1 号或者每周一”的九点，而不是“既是 1 号又是周一”。很多手写调度器在这里写成 and，结果某些任务一年只触发几次。代码用三次分支把三种情况写清楚：两个都是 * 时直接通过；只有一个有约束时只比那个；两个都有约束时取或。

_cron_field_matches() 是单字段匹配器，支持五种写法：*（任意）、*/N（步长）、N（精确值）、N-M（区间）、N,M,...（列表），而且列表和区间可以嵌套组合。它是对称的：校验函数用同一套语法规则判断合法性，所以“能通过校验的表达式，匹配时不会抛异常”。

对称不代表完备。校验只检查取值范围，不检查步长的语义，例如分钟段的 */90 能通过校验，但实际只在 0 分匹配，效果和 0 一样。这类输入不算错，只是使用者预期和结果不一致；严格的实现会在校验时警告“步长大于取值范围”。读源码时把“它拒绝什么”和“它没拒绝但不合理什么”分开记，能省掉很多调试时间。

写入前必须过 validate_cron()。它检查段数是否恰好五段，然后逐段按各自的取值范围校验：分钟 0–59、小时 0–23、日 1–31、月 1–12、星期 0–6。任何一段越界、区间起点大于终点、步长非数字或为 0，都会被拒绝并返回一句可读的错误。

def validate_cron(cron_expr: str) -> str | None:
    fields = cron_expr.strip().split()
    if len(fields) != 5:
        return f"Expected 5 fields, got {len(fields)}"

    field_rules = [
        ("minute", 0, 59),
        ("hour", 0, 23),
        ("day-of-month", 1, 31),
        ("month", 1, 12),
        ("day-of-week", 0, 6),
    ]
    for field, (name, minimum, maximum) in zip(fields, field_rules):
        error = _validate_cron_field(field, minimum, maximum)
        if error:
            return f"{name}: {error}"
    return None

校验发生在两个地方：schedule_job() 里保存前校验，load_durable_jobs() 里加载时再校验一次。后者容易被当成多余——文件是我们自己写的，为什么还要验？因为文件可能被手改、被别的版本写过、或者写到一半损坏。加载时把非法任务跳过并打印日志，比让一个坏表达式在运行期每隔一秒抛一次异常好得多。

把表达式翻译成人话

读 cron 表达式最稳的办法是先确认五段对应“分 时 日 月 周”，再从右往左读约束：

表达式含义
* * * * *每分钟
0 9 * * *每天 09:00
*/5 * * * *每 5 分钟
0 9 * * 1-5工作日 09:00
30 8 1 * *每月 1 号 08:30
0 9 1 * 1每月 1 号或每周一 09:00（日与周取或）

注意最后一行：它看上去像“每月 1 号且是周一”，实际语义是“或”。如果业务真的需要“每月 1 号且是周一”，就得写成两条表达式分别判断，或者在任务内部再做一次日期过滤。cron 语法本身没有“与”的写法。

看懂这一行，就避免了最常见的定时任务误解：以为多了字段就一定能表达更精确的条件。

把这张表当成读源码的对照单：看到 cron_matches() 里那三个 if 分支，就回来查一眼“日与周”这一行。能说清每个分支对应哪种输入，这段匹配逻辑就算真正读懂了。

04到期先入队：状态先落盘，任务再排队

调度线程的实现简单到只有五行：每 1 秒醒来一次，调用 poll_due_jobs(datetime.now())。

def cron_scheduler_loop(stop_event: threading.Event = RUNTIME_STOP):
    while not stop_event.wait(1.0):
        poll_due_jobs(datetime.now())

真正的逻辑在 poll_due_jobs()。它遍历所有任务，跳过“已经在等待交付”的，和“这一分钟已经触发过”的，然后对匹配的任务调用 _enqueue_due_job()：

def poll_due_jobs(moment: datetime):
    minute_marker = moment.strftime("%Y-%m-%d %H:%M")
    with cron_lock:
        for job in list(scheduled_jobs.values()):
            try:
                if job.pending_delivery or job.last_fired == minute_marker:
                    continue
                if cron_matches(job.cron, moment):
                    _enqueue_due_job(job, minute_marker)
                    print(f"  [cron] due {job.id}: {job.prompt[:60]}")
            except Exception as error:
                print(f"  [cron] could not enqueue {job.id}: {error}")

为什么需要 last_fired？因为线程每秒都会醒来，而 9:00 这一分钟里它可能匹配 60 次。如果没有分钟粒度的去重，一个任务一分钟就会入队 60 次。pending_delivery 则处理另一个窗口：任务已经入队，但 Agent 还没空处理，此时即使跨过了新的分钟，也不该再次入队。两个字段一个管“同一分钟内不重复”，一个管“未交付期间不重复”。

把去重放在“分钟”而不是“秒”，是因为 cron 的最小粒度就是分钟。如果未来要支持秒级调度，这个标记就得改成秒级字符串，last_fired 的格式也要跟着变——数据格式永远跟着精度走。

这类“时间标记”字段的命名也值得讲究：叫 last_fired 而不是 last_time，读代码的人能立刻知道它记录的是“触发”而不是“执行”。

_enqueue_due_job() 的顺序是本章最值得抄的细节：先把 pending_delivery 和 last_fired 写进任务，必要时持久化到磁盘，成功之后才把任务放进内存队列。如果先入队再落盘，一旦磁盘写失败，内存队列里就有一个“状态没记住”的任务——掉电重启后它可能被再次触发，或者反过来永久丢失。先写状态、后入队，让“队列里的任务”永远对应一个“已经记录在案”的事实。

设计要点

持久化失败时，_enqueue_due_job() 会把 pending_delivery 和 last_fired 恢复成旧值再抛异常，队列里不会出现半成品。这和上一讲的“先登记任务再起线程”是同一个思路：让共享状态的一致点尽可能靠前。

另外注意 cron_lock 是一把可重入锁（threading.RLock）：poll_due_jobs() 持有它遍历任务时，_enqueue_due_job() 又需要它来保存状态。普通锁在这里会直接死锁。选锁的类型不是风格问题，是正确性问题——调用链里是否有嵌套加锁，决定了你该用 Lock 还是 RLock。

05Agent 空闲再交付：不打断当前轮次

队列处理线程和调度线程是两条独立的线。它每 0.2 秒检查一次队列，但只有在能拿到 agent_lock（非阻塞）时才真正启动一轮：

def queue_processor_loop(stop_event: threading.Event = RUNTIME_STOP):
    while not stop_event.wait(0.2):
        if not has_cron_queue() or not agent_lock.acquire(blocking=False):
            continue
        try:
            if has_cron_queue():
                run_agent_turn_locked()
        finally:
            agent_lock.release()

agent_lock 同时被主交互循环使用：用户输入时 with agent_lock: 跑一轮，定时任务处理时也拿同一把锁。所以“Agent 空闲”在这份代码里有一个非常具体的定义：没有用户轮次正在跑。这保证了 messages[] 同一时刻只有一个写者。注意 agent_lock.acquire(blocking=False)：拿不到就跳过，绝不阻塞调度线程——如果阻塞等待，定时任务就会把“发现到期”和“用户正好在忙”耦合在一起。

取队列的动作本身很短，但必须是原子的：先复制、再清空，两步都在 cron_lock 里完成。否则调度线程可能在“复制完、还没清空”的间隙又塞进一个新任务，下一轮就会重复交付。

def consume_cron_queue() -> list[CronJob]:
    with cron_lock:
        jobs = list(cron_queue)
        cron_queue.clear()
    return jobs

拿到锁之后还要再查一次 has_cron_queue()，这不是冗余：从“检查队列”到“拿到锁”之间，另一个线程可能已经把队列消费掉了，或者取消任务清空了队列。典型的 double-checked locking 写法，宁可多查一次，也不要在空队列上白跑一轮。

交付发生在 agent_loop() 的最开头：把队列里的任务全部取走，逐个作为一条 [Scheduled] 开头的 user 消息追加到会话里，再进入正常的模型调用循环。

def agent_loop(messages: list, context: dict | None = None):
    fired = consume_cron_queue()
    scheduled_start = len(messages)
    for job in fired:
        messages.append({"role": "user", "content": f"[Scheduled] {job.prompt}"})
    waiting_for_ack = list(fired)
    while True:
        try:
            response = client.messages.create(...)
        except Exception as error:
            if waiting_for_ack:
                del messages[scheduled_start:]
                restore_cron_jobs(waiting_for_ack)
            return context
        messages.append({"role": "assistant", "content": response.content})
        if waiting_for_ack:
            try:
                acknowledge_cron_jobs(waiting_for_ack)
            except Exception as error:
                print(f"  [cron] acknowledgement failed: {error}")
            waiting_for_ack = []

这段代码里藏着一个完整的“至少一次交付”协议。用 scheduled_start 记下追加消息前的位置，如果模型调用失败，就把这些消息从会话里删掉、把任务放回队列——因为模型根本没收到，不能算交付成功。模型成功返回后，才调用 acknowledge_cron_jobs()：周期任务清掉 pending_delivery，一次性任务直接从 scheduled_jobs 删除。先交付、后确认，中间崩溃就会导致重复交付；反过来先确认、后交付，则会丢任务。两害相权，代码选择了“宁可重复,不可丢失”。

为什么交付方式是“伪造一条 user 消息”？因为模型只有一个输入通道：messages[] 里的 user 消息。定时任务本质上就是“系统替你发了一条 prompt”，用 [Scheduled] 前缀只是给模型一个可识别的标签，让它知道这不是用户刚刚打的字。这个设计也意味着：定时任务和用户消息共享同一套权限、同一套工具、同一个上下文——它不是一个独立的执行环境。

交付时终端还会打印 [cron] delivered ... 日志，方便你对照“到期”和“交付”两个时刻。日志在这里不是装饰，它是排查“任务为什么没跑”的第一手证据。

确认动作 acknowledge_cron_jobs() 同样是一段事务式代码：周期任务清 pending_delivery，一次性任务从字典移除；如果持久化失败，就把移除的任务放回字典、把标记恢复、再把任务重新塞回队列。它保证“确认”要么完整生效，要么完全回滚。注意它只处理“已经成功交付”的任务，模型失败时走的是 restore_cron_jobs()，两条路径不会混淆。

def acknowledge_cron_jobs(jobs: list[CronJob]):
    changed, removed = [], []
    with cron_lock:
        for delivered in jobs:
            current = scheduled_jobs.get(delivered.id)
            if current is None:
                continue
            changed.append((current, current.pending_delivery))
            if current.recurring:
                current.pending_delivery = False
            else:
                removed.append(current)
                scheduled_jobs.pop(current.id)
        try:
            if any(job.durable for job, _ in changed):
                save_durable_jobs()
        except Exception:
            # ... 回滚：放回任务、恢复 pending、重新入队，然后 re-raise

06周期与一次性、durable 与内存、取消与恢复

schedule_job() 的默认值是“周期 + durable”，但两个开关可以组合出四种行为：

组合行为典型用途
recurring=True + durable=True每次都触发，进程重启后仍在每天九点跑测试
recurring=True + durable=False每次都触发，只在本次进程内有效临时的“每五分钟看看进度”
recurring=False + durable=True只触发一次，重启后若未交付会重投“明天九点提醒我发版”
recurring=False + durable=False只触发一次，重启即消失本次会话内的一次性延后任务

durable 的边界要说清：它保存的是任务定义和尚未交付的状态，不是“已经错过的触发记录”。保存文件 .scheduled_tasks.json 用“写临时文件 + os.replace()”的方式更新，避免读者读到半截 JSON；加载时逐条校验，非法记录跳过并打印日志。如果你在 8:59 关掉进程、9:30 再打开，任务定义会回来，但 9:00 那一次不会补跑——调度器只往前看，不回头补课。

def save_durable_jobs():
    with cron_lock:
        payload = [
            asdict(job)
            for job in scheduled_jobs.values()
            if job.durable
        ]
        temporary = DURABLE_PATH.with_name(
            f"{DURABLE_PATH.name}.{os.getpid()}.{threading.get_ident()}.tmp"
        )
        try:
            temporary.write_text(
                json.dumps(payload, indent=2), encoding="utf-8"
            )
            os.replace(temporary, DURABLE_PATH)
        finally:
            temporary.unlink(missing_ok=True)

临时文件名里带进程 ID 和线程 ID，是为了让多个写者互不覆盖：如果两个线程同时保存，各写各的临时文件，最后 os.replace() 是一个原子重命名——读者要么看到旧的完整文件，要么看到新的完整文件，读不到中间态。finally 里删临时文件是收尾，避免失败时在目录里留下垃圾。

取消任务的 cancel_job() 也做了两件事：从 scheduled_jobs 删除，同时从 cron_queue 里移除。如果只删前者，已经入队的任务还会被交付一次；如果持久化失败，它会把任务和队列都恢复回去再抛异常。又是一个“先记状态、再改世界”的原子性练习。

“取消”在并发系统里永远比“创建”难写，因为你要考虑任务正处在哪个阶段：还没触发、已入队、正在交付、已经确认。本章只处理了前两个阶段，后两个阶段里取消会表现为“这一轮照常跑完，但不再有下一次”。

周期与一次性、durable 与内存，这四个开关看起来只是配置项，实际上决定了任务在“进程生命周期”和“时间维度”上的两重存活范围。写业务任务前先把这两个维度想清楚，比事后补幂等逻辑便宜得多。

最后是启动和关闭。调度线程与队列处理线程只在 CLI 入口（__main__）里启动，导入 code.py 不会凭空多出后台线程；关闭时设置 RUNTIME_STOP 事件并 join 两个线程。这个“只在入口启动、只通过事件停止”的结构，是你把它嵌进别的程序时最应该保留的部分——一个 import 就能启动线程的模块，是最难测试的模块。

如果你要把 s12 嵌进一个 Web 服务，记得把“启动/停止”挂到应用的生命周期钩子上，而不是模块导入时。定时器是长生命周期资源，它的创建和销毁必须和进程生命周期对齐。

🔬 深入：时区、错过、重复交付与“会话级”的边界

时区和错过的触发

代码只用 datetime.now()，也就是 Agent 进程所在机器的本地时间，任务里没有时区字段。这意味着同一份 .scheduled_tasks.json 搬到另一个时区的机器上，触发时刻会整体平移；跨时区协作时，“每天早上九点”到底是哪个九点，必须在产品层说清楚。错过触发则是另一个问题：进程关闭期间没有线程在看表，重启后 load_durable_jobs() 只恢复定义，不补跑错过的分钟。要补跑，需要记录“上次醒来时间”并在启动时回溯判断哪些触发点被错过——而补跑本身又牵出“补跑一次还是补跑 N 次”“补跑的任务用当时的数据还是现在的数据”等一连串问题。教学版选择不回答，是诚实的简化。

为什么先入队再 ack，而不是先 ack 再执行

先 ack 的语义是“我已经承诺执行了”，但此时模型可能还没收到 prompt；如果进程在这一刻崩溃，任务就永久消失。先入队、等模型成功返回后再 ack，语义变成“模型确实收到了”，代价是崩溃窗口内可能重复交付。分布式系统里这叫“至少一次（at-least-once）”：不丢，但可能重。幂等性要在任务本身解决——比如“跑测试”重复跑一次无害，而“发版”重复执行就危险，所以危险操作应该在 prompt 里要求先检查当前状态。

它和后台任务到底差在哪

后台任务由模型在工具调用里显式发起，生命周期是“本次进程内、一次命令”；定时任务由一个独立线程按时间发起，生命周期是“一条持久化记录 + 每次触发”。后台结果通过完成队列回到当前会话；定时任务则是新开一轮 Agent 循环，prompt 作为 user 消息进入会话。一个是“执行方式”，一个是“触发方式”，两者可以组合：定时任务被交付后，模型完全可以在那一轮里再发起一个后台 bash。

会话级 vs 系统级

本章的调度器挂在 Agent 进程里，属于“会话级”：进程活着才有闹钟，durable 只是让定义别丢。系统级定时（crontab、systemd timer、云函数）由操作系统或外部服务保证，即使 Agent 没运行，到点也能拉起一次执行。判断该用哪种，看任务是否“必须在 Agent 存活时才有意义”：需要同一份 messages[] 上下文的提醒，适合会话级；需要无条件执行的巡检、备份、报表，适合系统级。

它和 OpenClaw 式 heartbeat 的关系

仓库 README 提到另一条思路：每 30 秒由 harness 主动给 Agent 发一条消息，让它自己检查有没有待办——这叫 heartbeat（心跳）。heartbeat 是“定期叫醒 Agent，让它自己判断”，cron 是“到点把具体任务塞给 Agent”。前者适合“可能有活、也可能没活”的常驻助手，后者适合“明确知道几点该做什么”的自动化。两者不冲突：一个 always-on 的 Agent 往往是 heartbeat 负责唤醒、cron 负责精确触发、后台任务负责执行慢活。

再深一层：为什么调度线程不直接调用模型，而要多一个队列？

因为“时间到了”和“会话可写”是两个独立条件。调度线程若直接调用模型，就必须自己处理“用户正在一轮对话中”的情况：要么阻塞等待（拖慢调度）、要么强行插入（破坏 messages[] 的交替结构）。队列把这层协调交给了 agent_lock 和 queue_processor_loop，调度器只做一件纯粹的、可测试的事：判断时间是否匹配。

07动手实验

这些实验围绕四个观察点：任务有没有落盘、到点有没有入队、交付有没有等空闲、重启后定义还在不在。

  1. 挂一个两分钟的任务：运行 python s12_cron_scheduler/code.py，输入 Schedule "run date" every 2 minutes and keep it after restart.。观察是否返回 Scheduled cron_xxxxxxxx: */2 * * * * -> run date，并用 cat .scheduled_tasks.json 确认任务已经落盘。
  2. 看它到点被交付：保持进程运行最多两分钟，观察终端出现 [cron] due ...、[cron] delivered ...，以及一轮新的模型回复。注意交付的是一条 [Scheduled] run date 用户消息。
  3. 验证周期与一次性：再建一个 recurring=False 的任务，触发一次后用 list_crons 看它是否已经从列表消失；周期任务则应仍然在列表里，pending_delivery 已清零。
  4. 测试取消：对刚建的任务执行 cancel_cron，确认它从 list_crons 消失、也从 .scheduled_tasks.json 消失。如果取消时它正好在队列里，等待下一分钟确认不会再被交付。
  5. 观察重启：保留一个 durable 的周期任务，按 q 退出再重启。启动日志应出现 [cron] loaded N durable job(s)；如果你在停机期间错过了触发点，不会补跑——这正是“不回头”的边界。
  6. 纯代码实验：在 Python REPL 里 import code，直接调用 cron_matches("0 9 * * 1-5", datetime(2026, 1, 5, 9, 0)) 与 cron_matches("0 9 1 * 1", datetime(2026, 1, 5, 9, 0))，验证“日与星期都受限时取或”的语义。
  7. 看非法表达式被拒：在 REPL 里调用 schedule_job("0 25 * * *", "x") 与 schedule_job("0 9 * *", "x")，确认分别返回小时越界和段数不足的错误字符串，而不是抛异常。

08常见误区

很多人以为 cron 表达式匹配就是五个字段全部 AND。“日”和“星期”是例外：两者都受限时按标准 cron 语义取或。代码里的三个分支就是为了处理这个例外。写错这里，要么任务几乎不触发，要么在预期之外的日子触发。

很多人以为 durable 等于“关机也会跑”。它只持久化任务定义，执行仍然依赖进程里的调度线程。进程不在，闹钟就不响；重启后也不会补跑停机期间错过的触发。要真正的“always-on”，得把调度放到系统层。

判断标准很简单：把进程杀掉，任务还会不会在预定时间执行？会，就是系统级；不会，就是会话级。

另外，别把“调度线程”和“执行线程”混为一谈：前者只负责发现，后者才改会话。

很多人以为定时任务会“打断”当前对话。不会。到期只是入队，真正交付要等 agent_lock 空闲；一轮用户对话进行中，定时任务只能排在队列里。这个设计牺牲了一点实时性，换来的是会话消息结构不被两个线程同时改写。

09自测

下面的题覆盖匹配、入队、交付、持久化四条链路。建议先自己推一遍再展开答案。

如果 pending_delivery 和 last_fired 只保留一个，会发生什么？

只保留 last_fired：任务入队后，如果交付延迟跨过了下一分钟（例如 Agent 忙了三分钟），同一任务会在新的分钟再次入队，队列里出现重复项。只保留 pending_delivery：同一分钟内线程每秒轮询，第一次入队后如果 pending_delivery 没及时置位或已被清除，会重复入队。两个字段各防一个时间窗口，缺一不可。

为什么 _enqueue_due_job() 要先持久化状态、再加入内存队列？

为了让“已经入队”这件事在磁盘上先有记录。如果顺序反过来，持久化失败时内存队列里已经有了这个任务，但 pending_delivery / last_fired 没有正确落盘；此时若进程崩溃，重启后的状态与真实交付情况不一致，可能重复或丢失。先写状态再入队，失败时恢复旧状态，保证磁盘、内存、队列三者不会出现“队列里有、状态里没有”的中间态。

调度线程每秒轮询一次，为什么不会让一个任务在 9:00 这一分钟触发 60 次？

因为 poll_due_jobs() 用 moment.strftime("%Y-%m-%d %H:%M") 生成分钟标记，匹配后把 last_fired 设成这个标记；同一分钟内后续轮询都会因为 job.last_fired == minute_marker 而跳过。pending_delivery 再兜住“跨分钟但还没交付”的情况。

模型调用失败时，代码为什么要 del messages[scheduled_start:] 再 restore_cron_jobs()？

因为失败意味着模型没有收到这批定时任务，不能算交付成功。把追加的 [Scheduled] 消息从会话里删掉，恢复会话到交付前的状态；再把任务放回队列，等下一次空闲重试。如果不删消息就恢复任务，重试时会重复追加，同一批任务在会话里出现两份。

一个 durable 的一次性任务在 8:59 触发并入队，但在模型接收前进程崩溃。重启后它会怎样？

取决于持久化是否已经写回。_enqueue_due_job() 在入队前把 pending_delivery=True 和 last_fired 写入磁盘，所以重启后 load_durable_jobs() 会看到 pending_delivery 并把任务重新放进 cron_queue——任务会被再次交付，而不是丢失。这就是“至少一次”：宁可重复，不可丢失。

这一讲带走

Cron Scheduler 把“时间”变成 harness 的一等公民：CronJob 记录表达式与任务、五段式匹配（日与星期取或）、调度线程每秒轮询、到期先把状态落盘再入队、Agent 空闲后把任务作为 [Scheduled] 用户消息交付、模型收到后才 ack。它保证的是“至少一次”，换来的是不丢任务、但可能重复。

判断一个调度器是否可信，就看四件事：表达式会不会错、到期会不会重复、交付会不会打断会话、崩溃会不会丢任务。s12 对这四件事各给了一个明确答案，也各自留了边界。

记住那张“先入队、后交付、再确认”的三段式：它是所有可靠定时系统的共同骨架。

在把它搬进真实系统之前，至少先回答：任务错过时应该补跑还是跳过、任务重复时是否幂等、以及调度器挂了谁来发现。
