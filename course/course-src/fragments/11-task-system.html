01清单能提醒你，但不能替你排顺序

第 6 讲我们给 Agent 装了 TodoWrite：把当前任务的步骤列成一张表，做完一项划掉一项，很适合“一次会话里把一件事干完”。可真实项目里任务不是平铺的。要做数据库表、写 API、加测试，这三件事的顺序是硬的：表没建好，API 没法写；API 没定稿，测试没有对象。

TodoWrite 的表里当然可以写“1. 建表 2. 写 API 3. 加测试”，但它只记录“做了没有”，不记录“能不能做”。当 Agent 隔天重新打开会话，看到“写 API”还没勾，它没有任何依据判断这个任务现在是否可开工——前置条件可能早就完成了，也可能根本没有。更麻烦的是，如果有多个 Agent 在协作，TodoWrite 不记录“谁在做”，两个 Agent 很容易同时认领同一件事。

所以 s10 要解决的是三个具体问题：任务要能跨会话恢复（状态落盘）、任务之间要能表达先后（依赖图）、任务要能被认领（owner + 状态机）。它们合起来，才配叫 Task System，而不是一张更大的待办清单。

维度TodoWrite（s05）Task System（s10）
定位当前任务的执行清单可恢复、可认领的任务系统
存储进程内 / 会话状态.tasks/task_xxxxxxxx.json
依赖无，只是一行行条目blockedBy 构成的依赖 DAG
分工不记录谁在做owner + claim 认领
更新方式整表替换对单条记录增、查、改
生命周期当前会话 / 当前任务跨会话保留，可被别的执行者接手

一张图能回答的三个问题

把任务画成图之后，Agent 在每一轮只需要问三个问题，而且都能用代码回答，不必“回忆”：

  • 现在能开始哪些？扫描所有 pending、且 blockedBy 全部 completed 的任务。
  • 谁在做什么？看 owner 和 in_progress，避免重复认领。
  • 做完这一步会解锁什么？完成任务时比较前后可开始集合，得到增量。

这三个问题正好对应三个工具：list_tasks、claim_task、complete_task。工具不是按 API 对称性设计的，而是按 Agent 每轮真正要做的决策设计的。

反过来说，如果你发现某个任务工具回答不了上面任何一个问题，它大概率就不该存在。

这也是判断“该不该给 Agent 加工具”的通用方法：先列出它每轮要做的决策，再让工具一一对应。工具数量不是能力指标，覆盖决策才是。

回到本章开头那张图：三个问题、三个工具，恰好构成一个完整的调度循环。

把这句话记住，s13 的团队协作只是在这个循环里多加了几个并发执行者。

像工地上的施工许可证

每张任务卡就是一张许可证：卡上写清要干什么、前置哪些验收单必须签字、现在由哪个班组持证施工。没有前置验收单签字，你就不能开工；持证的人才能报完工；完工之后，下一批原本被卡住的许可证自动生效。

类比到哪为止：工地有监理盯着，不会出现两个班组抢同一张卡；而这里的“不抢”必须靠代码保证。本章只做到“认领前检查状态”，真正的并发原子性要等 s13 的团队协作才补上——这正是把 Task System 放在 s13 前面的原因。

02直觉：一个任务一个文件，一条依赖一条边

存储的选择很朴素：.tasks/ 目录下，每个任务一个 task_xxxxxxxx.json。为什么不是一个大 JSON 数组？因为任务会被局部更新：认领只改一条、完成只改一条。一任务一文件意味着每次更新只重写一个小文件，不需要读入、修改、写回整张表，也天然适合以后多个 Agent 各改各的任务。

create生成随机 ID 落盘
→
update用返回的 ID 连边
→
can_start前置是否全完成
→
claimpending → in_progress
→
complete→ completed 并解锁下游

状态机只有两个动作、三个状态，刻意做得很窄：

pending已创建、未认领
→
in_progress已 claim，有 owner
→
completed已完工，可解锁后继

窄有窄的好处：每个状态转换都只有一个合法入口，非法转换（比如没认领就完成、完成了再认领）都能被一句话拒绝。很多任务系统一开始就设计出十几个状态和任意跳转，最后没有一个分支能说清。

设计要点

状态机的价值不在“有几个状态”，而在“每个动作的前置条件是否可检查”。s10 的两个动作分别对应两句显式检查：if task.status != "pending" 和 if task.status != "in_progress"。把检查写进动作入口，比在文档里约定“先认领再完成”可靠得多。

为什么按文件拆，而不是一个 tasks.json

单文件方案看起来更简单，但它把三类操作都变贵了：认领一个任务要读入整张表再写回整张表；两个 Agent 各改一个任务会互相覆盖；一次写入失败会损坏全部任务。拆成一任务一文件之后，每个操作的作用域被压到最小：

.tasks/
  task_a1b2c3d4.json   {status: completed, blockedBy: []}
  task_e5f6a7b8.json   {status: pending, blockedBy: [task_a1b2c3d4]}
  task_11223344.json   {status: pending, blockedBy: [task_e5f6a7b8]}

依赖图：
  schema(completed) → API(pending) → tests(pending)

can_start(API) 为真，因为 schema 已完成。

代价是“列出全部任务”要扫目录、读一堆小文件。这个代价在任务量几十到几百时完全可以接受，而且 sorted() 之后顺序稳定，便于复现和调试。等到任务量上万，再换成数据库也不迟——但那是规模问题，不是设计问题。

记住这个目录形状：s13 的团队协作会原样复用它，只是给每个任务再绑一个工作树（worktree）。

03代码精读：Task 与 TaskStore

数据结构本身没有惊喜，六个字段各司其职：status 是状态机的位置，owner 是认领者，blockedBy 是入边列表。真正值得看的是 ID 的分配方式和写入方式。

用 @dataclass 而不是裸字典，好处不只是可读：asdict(task) 直接给出可序列化的字典，Task(**data) 又能在读取时把字典还原成带类型提示的对象。JSON 文件和内存对象之间有了一个显式的转换点，任何新字段都必须同时出现在两处——这比到处传 task["status"] 更不容易写错键名。

@dataclass
class Task:
    id: str
    subject: str
    description: str
    status: str           # pending | in_progress | completed
    owner: str | None     # 认领这个任务的 Agent
    blockedBy: list[str]  # 前置任务的 ID 列表

TaskStore.create() 负责分配 ID 并落盘。它用一个固定上限的重试循环处理 ID 碰撞：

class TaskStore:
    def create(self, subject: str, description: str = "") -> Task:
        subject = subject.strip()
        if not subject:
            raise ValueError("Task subject cannot be empty")
        self._root(create=True)
        for _ in range(100):
            task = Task(
                id=f"task_{secrets.token_hex(4)}",
                subject=subject, description=description,
                status="pending", owner=None, blockedBy=[],
            )
            try:
                with self._path(task.id, create_root=True).open(
                    "x", encoding="utf-8"
                ) as handle:
                    json.dump(asdict(task), handle, indent=2)
                return task
            except FileExistsError:
                continue
        raise RuntimeError("Could not allocate a unique task ID")

三个细节在防三件事。第一，ID 用随机 8 位十六进制而不是自增：多个进程同时创建任务时，自增计数需要共享状态，随机 ID 只要撞不上就行；secrets 而不是 random，是因为任务 ID 也可能出现在日志或工具结果里，不该可预测。第二，open("x") 是排他创建：文件已存在就抛 FileExistsError，代码重试另一个 ID。这让“检查 ID 是否被占用”和“写入”变成同一个原子操作，避免了先查后写之间的竞态。第三，_path() 会用 TASK_ID_PATTERN 校验 task_[0-9a-f]{8}，并确认解析后的路径没逃出 .tasks/——跟上一讲的 memory_path() 是同一个思路。

读取侧的校验：宁可报错，也不带着坏数据跑

load() 做的工作比“json.load 然后构造对象”多得多。它要确认文件里的 id 和请求的 ID 一致（防止文件名被改过），并且 status 只能是三个合法值之一。这两条检查针对的是“有人手改了 JSON”和“代码写错了状态”两种真实故障：坏任务继续在状态机里流转，比直接报错难查得多。

    def load(self, task_id: str) -> Task:
        data = json.loads(self._path(task_id).read_text(encoding="utf-8"))
        task = Task(**data)
        if task.id != task_id:
            raise ValueError(f"Task file ID does not match {task_id}")
        if task.status not in ("pending", "in_progress", "completed"):
            raise ValueError(f"Invalid task status: {task.status}")
        return task

注意它没有校验 blockedBy 里的每个 ID 是否存在——这是有意的分工：incomplete_dependencies() 在真正判断依赖时才处理缺失，读取阶段不把“图暂时不完整”当成错误。校验要放在语义明确的位置：格式问题在 load 报错，图问题在 can_start 处理。

还有一个容易忽略的设计：save() 用 write_text 直接覆盖。它不是原子写，也没有文件锁：写一半崩掉会得到半截 JSON。教学代码默认单进程顺序执行，所以可以接受；生产实现要换成“写临时文件 + os.replace()”，并考虑跨进程锁。这个缺口先记住，后面的“深入”会展开。

读这一章源码时，建议把“它假定了什么”和“它实现了什么”分开记：假定是单进程、串行、任务量在几百以内；实现是 ID、依赖、状态机。假定的部分就是你要在生产环境补的课。

04两阶段建图：为什么依赖不能和创建一起写

按直觉，创建任务时顺便传 blockedBy 最方便。但 s10 偏偏分成两步：先 create_task 拿 ID，再 update_task 连边。这不是 API 设计洁癖，而是被模型的工作方式逼出来的。

当模型决定“建四张任务卡”时，它可能在一条回复里同时发出四个 create_task 的 tool_use block。而同一批 tool call 的参数，在任何一个工具执行之前就已经全部生成完毕——也就是说，第一个 create_task 真正跑起来之前，模型根本不可能知道它分配的随机 ID。唯一可行的顺序是：第一轮全部创建，拿到四个 ID 的 tool_result；第二轮再用这些 ID 发 update_task。system prompt 里那句“Create all task nodes first… use those exact IDs”就是在教模型这个协议。

第 1 轮  assistant → create_task("setup database schema")
                  → create_task("create API endpoints")
                  → create_task("write tests")
第 1 轮  user      ← Created task_1a2b3c4d: setup database schema
                  ← Created task_5e6f7a8b: create API endpoints
                  ← Created task_9c0d1e2f: write tests
第 2 轮  assistant → update_task(task_5e6f7a8b, [task_1a2b3c4d])
                  → update_task(task_9c0d1e2f, [task_5e6f7a8b])

这份两阶段的往返记录值得记住：它解释了很多 Agent 工具设计里“为什么要有第二个工具”。不是功能拆得越细越好，而是模型的生成顺序决定了有些参数只能在下一轮才知道。

设计要点

凡是“B 的参数依赖 A 的输出”的协议，都值得考虑拆成两个工具、两轮往返。反过来，如果两个操作可以在同一批里并行、互不依赖，就不要硬拆，否则白白多一轮延迟和 token。

def update_dependencies(self, task_id: str, add_blocked_by: list[str]) -> Task:
    task = self.load(task_id)
    if task.status != "pending" or task.owner is not None:
        raise ValueError(
            f"Task {task_id} dependencies can only be updated while "
            "pending and unowned"
        )
    dependencies = list(dict.fromkeys(add_blocked_by))
    for dependency in dependencies:
        if dependency == task_id:
            raise ValueError("Task cannot depend on itself")
        if not self.exists(dependency):
            raise ValueError(f"Dependency not found: {dependency}")
        if dependency not in task.blockedBy and self._depends_on(
            dependency, task_id
        ):
            raise ValueError(f"Dependency cycle detected: {task_id} -> {dependency}")
    task.blockedBy.extend(dependency for dependency in dependencies
                          if dependency not in task.blockedBy)
    self.save(task)
    return task

这段代码的注释里没有废话，每一行都在拒绝一种坏图。自依赖会让任务永远等自己；引用不存在的 ID 会造出悬空的边；_depends_on(dependency, task_id) 会从依赖出发做一次 DFS，如果绕一圈能回到当前任务，说明加这条边会形成环，直接拒绝。注意检查顺序：先确认依赖存在，再判断成环——不存在的节点谈不上可达性。

为什么环检测放在写入前、并且检查的是“加边之后会不会成环”而不是“图里有没有环”？因为每次只加一条边，只要保证新边不引入新的环，整张图就永远无环。这是增量维护的典型技巧：把全局不变量变成“每次操作后仍成立”的局部检查。

设计要点

update_dependencies() 只允许改 pending 且无 owner 的任务。原因很实际：一个已经被认领、正在执行的任务，它的前置条件如果还能被改，执行者看到的约束就随时可能变化。冻结依赖边界，等于冻结“这个任务的合同”。

05认领与完成：状态机的两个动作

can_start() 的语义只有一句：blockedBy 里的任务必须全部是 completed。incomplete_dependencies() 会逐个读取前置任务，只要有一个不是 completed，或者文件已经不存在（读到 FileNotFoundError / ValueError），就判定为未完成——缺失的前置按“没做完”处理，而不是按“没约束”处理，这是保守但正确的选择。

def incomplete_dependencies(task: Task) -> list[str]:
    incomplete = []
    for dependency in task.blockedBy:
        try:
            if load_task(dependency).status != "completed":
                incomplete.append(dependency)
        except (FileNotFoundError, ValueError):
            incomplete.append(dependency)
    return incomplete

注意 except 分支：读不到前置文件时，代码不是跳过，而是把该依赖加入 incomplete。这一行决定了“数据损坏时任务卡住”而不是“数据损坏时任务被误放行”。安全相关的默认值，宁可保守。

def can_start(task_id: str) -> bool:
    return not incomplete_dependencies(load_task(task_id))

def claim_task(task_id: str, owner: str = "agent") -> str:
    task = load_task(task_id)
    if task.status != "pending":
        return f"Task {task_id} is {task.status}, cannot claim"
    dependencies = incomplete_dependencies(task)
    if dependencies:
        return f"Blocked by: {dependencies}"
    task.owner = owner
    task.status = "in_progress"
    TASKS.save(task)
    print(f"  [claim] {task.subject} -> in_progress (owner: {owner})")
    return f"Claimed {task.id} ({task.subject})"

认领是个“读—改—写”序列：先读出任务，检查状态是 pending，再检查依赖，最后写回 owner 和 in_progress。在单进程里这没问题；如果有两个线程或两个 Agent 同时认领同一个任务，双方都可能先读到 pending，然后各自写回 in_progress，后写者覆盖先写者——而且两条“Claimed”都会打印出来。s10 明确不管这个，s13 的团队章节才把认领改成带锁的原子操作。读源码时要能一眼看出这个边界，而不是默认它已经安全。

完成动作比认领多一层“通知下游”。如果只是把状态改成 completed，被它阻塞的任务确实会在下次 can_start() 时变成可开始，但 Agent 未必会主动去查。所以 complete_task() 做了一次前后对比：

def complete_task(task_id: str, owner: str = "agent") -> str:
    task = load_task(task_id)
    if task.status != "in_progress":
        return f"Task {task_id} is {task.status}, cannot complete"
    if task.owner != owner:
        return f"Task {task_id} is owned by {task.owner}, not {owner}"
    ready_before = {
        candidate.id
        for candidate in list_tasks()
        if candidate.status == "pending"
        and candidate.blockedBy
        and can_start(candidate.id)
    }
    task.status = "completed"
    TASKS.save(task)
    unblocked = [candidate.subject for candidate in list_tasks()
                 if candidate.status == "pending"
                 and candidate.blockedBy
                 and candidate.id not in ready_before
                 and can_start(candidate.id)]
    # ... 打印并返回 "Completed ...  Unblocked: ..."

先算“完成之前哪些任务本来就能开始”，改完状态再算一次，差集就是“这次完成刚刚解锁的任务”。这个小技巧保证了消息准确：不会把早就可开始的任务误报成刚解锁，也不会漏掉真正被解锁的。owner 校验则防止一个 Agent 把另一个 Agent 正在做的任务标记为完成——在单 Agent 场景里看不出价值，在 s13 多 Agent 场景里它就是责任边界的兜底。

06六个工具，一套契约

本章在基础五件套之外新增了 create_task、update_task、list_tasks、get_task、claim_task、complete_task。它们的分工是被刻意拆开的：创建只负责建节点，更新只负责加边，查询分摘要（list_tasks）和全文（get_task），认领和完成各自只做一个状态转换。

为什么要把“列表”和“详情”分开？因为它们的成本和使用场景不同。list_tasks 把所有任务压成一行一个标记（[ ] / [>] / [x]），适合每轮快速扫一眼全局；get_task 返回完整 JSON，包含 description 和依赖细节，只在你真正准备做某个任务、或跨会话恢复时调用。如果一个工具既返回全量又返回详情，Agent 会不自觉地每次都拉全量，上下文很快被任务描述灌满。

一眼看懂 list_tasks 的输出

[ ] task_1a2b3c4d: setup database schema [pending]
[>] task_5e6f7a8b: create API endpoints [in_progress] [agent] (blockedBy: task_1a2b3c4d)
[x] task_9c0d1e2f: write tests [completed] [agent] (blockedBy: task_5e6f7a8b)

每行压缩成四个信息：状态标记、稳定 ID、可读标题、owner 与依赖。这个格式是给人快速扫的，也是给模型快速判断“下一步该认领谁”的——它不需要为每个任务付出一整段 JSON 的代价。需要细节时再 get_task，这是“摘要先于详情”的又一个应用。

{
  "id": "task_a1b2c3d4",
  "subject": "create API endpoints",
  "description": "",
  "status": "pending",
  "owner": null,
  "blockedBy": ["task_9f8e7d6c"]
}

这份 JSON 就是跨会话恢复的全部依据：进程重启后，.tasks/ 目录还在，list_tasks 能读出哪些完成了、哪些被谁占着、哪些在等前置。没有它，所谓“长任务”只是把一次会话拉长；有了它，任务的生命周期才第一次长过进程。

这也解释了为什么 get_task 在 s13 会成为热点工具：恢复现场之后，每个被认领的任务都需要完整描述，而描述没法塞进摘要行里。

工具描述也是提示词

回看 TOOLS 里的描述，会发现每一句都在约束模型的使用方式：create_task 明确说“返回运行时生成的 ID”，update_task 明确说“用 create_task 返回的 ID 添加依赖”，参数的 JSON Schema 里还给任务 ID 加了 ^task_[0-9a-f]{8}$ 的 pattern。这些不是装饰：模型选择调用哪个工具、传什么参数，很大程度上取决于描述怎么写。

小技巧

设计多步协议类的工具时，把“上一步的输出长什么样、下一步该拿它做什么”直接写进 description，比在 system prompt 里长篇解释有效得多——因为工具描述会跟着每个工具定义一起出现在模型眼前。

🔬 深入：为什么状态必须落盘，以及落盘之后的新麻烦

为什么不能只存在 messages 里

把任务状态写在工具结果里、让模型“记得”当然也能跑完一次会话，但它有三个硬伤。第一，上下文一压缩，最早的任务定义和依赖关系就变成摘要，细节丢失且不可恢复；第二，会话一到上限，唯一的事实来源就没了，重启后 Agent 不知道哪些任务完成过；第三，多个 Agent 无法共享：每个 Agent 有自己的 messages[]，它们看不到彼此的清单，却可以读同一个目录。落盘的本质是把“任务”从对话的私有状态升级成多个执行者共享的外部状态。

落盘带来的原子性与并发问题

s10 的 save() 是普通覆盖写，认领是“读—检查—写”，两处都没有锁。这在教学场景（单进程、串行）够用，但一旦有并发，就会出三类问题：丢失更新（两个认领互相覆盖）、读到半截文件（写到一半被读）、孤儿依赖（前置被删，后继永远 can_start 不出来）。真实系统的修法很直接：写用临时文件 + os.replace() 保证读者永远看到完整版本；认领用文件锁或数据库的 UPDATE ... WHERE status='pending' 做条件更新；删除任务要连带清理所有指向它的 blockedBy。s13 的团队实现会给出一个可抄的原子认领版本。

依赖环与“图”的边界

_depends_on() 用 DFS 检测环路，代价是每次加边都要遍历一遍依赖链。任务规模在几百以内完全够用；如果任务上万，应该换成记录拓扑序或用数据库约束。另一个容易被忽略的边界是跨会话的“陈旧边”：前置任务被删除后，后继的 blockedBy 里还留着它的 ID，代码会把这种情况归为“未完成”，于是后继永远卡住。修复需要在删除时做级联清理，或者定期跑一次图校验。

它和 s05 TodoWrite 到底怎么分工

不是新旧替代，而是两层不同粒度的东西。TodoWrite 服务“我现在这一轮打算怎么做”，内容可以随时整表重写，读者只有当前 Agent；Task System 服务“这个目标由哪些可独立认领的步骤组成”，每条记录有稳定 ID、可被认领、可跨会话恢复，读者可能是多个 Agent。一个实用的经验法则是：会出现在进度汇报里、需要别人接手的，进 Task System；只影响你自己下一步动作的，留在 TodoWrite。

为什么说它是 s13 团队协作的地基

多 Agent 协作最难的不是“让多个模型同时说话”，而是“让它们不重复干活、不抢同一件事、知道彼此做到哪了”。Task System 提供了三样现成的东西：稳定 ID 让任务可以被引用和传递；blockedBy 让“先做 A 才能做 B”变成了可程序化检查的约束；claim/complete 提供了最小可用的分工协议。s13 要做的，主要是把认领做成原子的、把 owner 换成具体队友、再给每个任务绑定一个工作树（worktree）隔离文件改动。地基已经在这里了。

任务 ID 为什么不用递增序号

自增序号需要维护一个全局计数器：单进程要读改写，多进程要加锁，重启还要持久化“下一个号是多少”。随机 ID 的代价只是极低概率的碰撞，而碰撞已经被 open("x") 的重试兜住了。更重要的区别在安全性：递增序号会泄露“系统里一共有多少任务、这是第几个”，随机 ID 不会。对本地教学项目这无关紧要，但对会出现在日志、通知、甚至 URL 里的标识符，不可预测是默认要求。

任务拆到多大才算一个任务

拆得太粗，一个任务要跑一小时，认领了就没法并行，依赖图也起不到调度作用；拆得太细，任务数量爆炸，每次勾选都要花一轮工具调用，图本身反而成了负担。经验粒度是“一个 Agent 能在一次专注的回合里完成，且中途不需要别人接手”：建表是一个任务，写全部 API 是一个任务，写测试是另一个任务；而“设计数据库字段”如果只是建表的一部分，就该留在 description 里，不必单独开节点。粒度判断错了也没关系——任务可以完成后新建后继，只是别在还没开工时就把图拆成二十个节点。

再深一层：为什么不在任务里直接存复杂对象，比如子任务数组？

因为扁平记录 + 依赖边是一种最小完备的表达：树、DAG、流水线、分组，全都能用“节点 + 边”表示。反过来，一旦引入嵌套子任务，每条记录的 schema 就变成递归结构，更新一个叶子节点要重写整棵树，跨 Agent 合并冲突也无从下手。扁平化还有一个副作用好处：所有任务天然可枚举，list_tasks() 扫一个目录就够了。

07动手实验

没有 API Key 也能做大部分实验：任务图和状态机都是纯 Python 函数，直接在 REPL 里调用就能观察。

  1. 先建图：运行 python s10_task_system/code.py，输入 Create tasks: setup database schema, create API endpoints (depends on schema), write tests (depends on endpoints), write docs (depends on schema)。然后 ls .tasks/，应该看到四个 JSON 文件，每个文件里 blockedBy 存的是真实的任务 ID。
  2. 观察两阶段协议：看终端里工具调用的先后。模型应该先连续调四个 create_task，再拿返回的 ID 调 update_task。如果它在同一条回复里试图“创建并带依赖”，看看 update_task 会报什么错——这就是协议存在的理由。
  3. 走一遍状态机：输入 Claim the first unblocked task and complete it，再 List all tasks。确认 schema 变 [x]，而 endpoints、docs 从“被阻塞”变成可开始；tests 仍然被 endpoints 卡住。
  4. 手动破坏依赖：直接编辑一个 JSON，把某个任务的 blockedBy 改成一个不存在的 ID，再跑 claim_task，观察返回 Blocked by: [...]。理解“缺失的前置按未完成处理”这条保守规则。
  5. 制造环并看它被拒：在 Python REPL 里 import code 后，对两个任务互相 update_task，第二调用应抛 Dependency cycle detected。也可以先自依赖，看 cannot depend on itself。
  6. 删掉前置文件：先建一条 schema → API 的依赖，再把 .tasks/ 里 schema 的 JSON 删掉，然后调用 claim_task。观察 API 一直返回 Blocked by: [...]——理解“前置缺失被当成未完成”，以及为什么删除任务要做级联清理。
  7. 换一种说法试探协议：直接说 Create a task for writing docs, blocked by the tests task。看模型是先建 docs、再问 tests 的 ID，还是试图在同一轮里猜一个 ID。这是观察工具描述和 system prompt 如何共同塑造行为的最好实验。

08常见误区

很多人以为有了 TodoWrite 就不需要 Task System。其实两者的存储位置和读者都不一样：TodoWrite 是给当前 Agent 看的会话内清单，Task System 是给“未来的自己和其他 Agent”看的共享状态。判断标准不是任务复不复杂，而是“它需不需要活得比这次对话久”。

很多人以为状态落盘就是“多写一个文件”。真正的工作量在于一致性和并发：写成原子操作、认领不重复、删除不留下孤儿边、恢复时能校验 schema。s10 只做对了一半，并明确标注了另一半留给 s13——读源码时要能分清“教学简化”和“设计缺陷”。

很多人以为 claim 只是把字段改成 in_progress。认领的本质是“占用”：它必须发生在检查依赖和状态之后、写入之前，并且不能被另一个认领者插队。单进程里看不出问题，多 Agent 时一次重复认领就意味着两份重复劳动。

依赖也一样：加得越多不等于越安全，过密的边会把可并行的任务串成一条链，还让每条边都变成一次可失败的文件读取。

关键结论

Task System 的核心不是“多存了几个字段”，而是把“能不能开始”从模型的模糊判断变成了代码里的一个布尔值。一旦这件事可判定，调度、恢复、多 Agent 分工才有讨论的起点。

09自测

下面几道题里有概念辨析，也有“找 bug”。建议先自己回答，再展开看解析。

为什么 create_task 不直接接收 blockedBy 参数？

因为依赖需要的是“已存在任务的运行时 ID”，而 ID 在任务创建成功之前并不存在。模型可能在一条回复里并行发出多个 create_task，这些调用的参数在任何工具执行前就已确定，第一个任务还没创建，模型不可能引用它的随机 ID。因此协议必须是两阶段：先创建拿到 ID，再 update_task 连边。system prompt 和工具描述都在反复强调这件事。

任务 A 的 blockedBy 指向一个已被删除的任务文件，can_start(A) 会返回什么？

返回 False。incomplete_dependencies() 在读取前置任务时捕获 FileNotFoundError 和 ValueError，并把对应依赖加入“未完成”列表。代码选择了保守语义：前置缺失 ≠ 前置满足。代价是任务可能永远卡住，所以删除任务时必须清理指向它的边，否则会留下“幽灵阻塞”。

如果两个线程同时认领同一个 pending 任务，s10 的代码能阻止重复认领吗？

不能。认领是“读文件 → 检查 status → 写文件”三步，没有任何锁或条件写。两个线程可能都读到 pending、都通过检查、都写回 in_progress，第二个覆盖第一个。修复方向是把检查与写入合成一个原子操作，比如文件锁、flock，或数据库的 UPDATE ... WHERE status='pending'。这是 s10 明确留给 s13 的缺口。

complete_task() 为什么要先算 ready_before 再改状态？

为了准确算出“这次完成刚刚解锁了谁”。如果只算 ready_after，会把完成之前就已经可开始、只是还没被认领的任务也算进去，汇报就失真了。先快照“本来就能开始的集合”，完成后再取差集，得到的是真正的解锁增量。这种“前后对比”在多 Agent 通知场景里尤其重要，因为下游 Agent 收到通知就会开工。

跨会话恢复时，Agent 应该先调 list_tasks 还是 get_task？

先 list_tasks 看全局，再对真正要接手的那一两个任务调 get_task。恢复现场需要的是“哪些完成、哪些在做、哪些可开工”，这是摘要能回答的；完整描述只在准备动手时才有价值。反过来做，会在一开始就把所有任务的 description 拉进上下文，既浪费预算，也淹没了真正重要的依赖信息。

这一讲带走

Task System 把任务从“对话里的备忘”变成“磁盘上的共享状态”：一任务一文件、随机 ID 排他创建、blockedBy 构成依赖 DAG、claim / complete 两个动作驱动三个状态、完成时用前后差集通知被解锁的下游。先创建后连边不是绕路，而是模型并行工具调用的必然协议。

读源码时，Task 结构加上一组状态转换函数，就是能放进任何 harness 的最小任务内核；.tasks/ 目录则是它的持久层。
