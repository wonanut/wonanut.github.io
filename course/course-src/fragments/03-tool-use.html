01一个工具不够用

如果你跳过了上一讲，只需记住一句话：Agent 的全部骨架是一个循环——调用模型、看响应里有没有 tool_use、有就执行、把结果以 tool_result 追加回 messages[]，没有就退出。s01 的执行动作只有一句 run_bash(block.input["command"])。

只有 bash 时，模型的日子是这样的：读文件写 cat path/to/file，写文件写 echo "..." > file.py，找文件写 find . -name "*.py"，改一行要拼 sed -i。这些命令它当然会写，但每一句都要经过一次“意图 → shell 语法”的翻译。

翻译是有代价的。第一，容易错：写一个带引号和三引号的 Python 文件，echo 的转义能让人抓狂，模型也会经常翻车。第二，浪费 token：它得把“读文件”这个简单意图展开成一条命令字符串。第三，也是最关键的——harness 看不懂。在 loop 眼里，所有操作都是一坨不透明的字符串，你没法在“执行之前”按工具类型或路径做判断。

这些工具没有增加新能力

read、write、edit、glob 能做的事，bash 全都能做。它们真正改善的是模型与 harness 之间的接口：模型不必再翻译语法，harness 拿到的不再是字符串，而是“具名操作 + 结构化参数”。后面几讲会反复受益于这一点——权限按工具名判断，钩子按工具名记录，都建立在这个结构上。

意图只有 bash 时有专用工具后
读文件cat path，大文件无法只读一段read_file(path, limit)，自带剩余行数提示
写文件echo "..." > path，引号、换行、特殊字符全是坑write_file(path, content)，内容原样写入
精确改一处sed -i 's/old/new/'，旧文本里的正则元字符会捣乱edit_file(path, old_text, new_text)，字面匹配
找文件find . -name '*.py'，输出还得再解析glob("**/*.py")，直接返回路径列表

把这张表从上往下看一遍，你会发现 bash 那一列的共同点：每一个意图都被编码成了字符串，而字符串里的每个字符都可能有特殊含义。专用工具那一列的共同点则是：意图直接对应参数，参数由 schema 描述类型和必填项。少了一层编解码，模型犯错的概率就低一截。

当然，bash 不会被取消。它仍然是那个“什么都能做”的万能出口；专用工具只是覆盖最高频的几类动作。真实 harness 里两者长期共存，靠权限系统决定“哪些 bash 命令需要额外审批”——这正是下一讲的主题。

02直觉：把“翻译”变成“结构”

新设计只有两块东西，各自服务一个对象：

TOOLS：给模型看的菜单

每个工具一条：叫什么、干什么、参数是什么类型、哪些必填。模型照着菜单点单，不用猜命令怎么写。

TOOL_HANDLERS：给 harness 用的岗位表

工具名映射到处理函数。模型报出工具名，harness 查表找到实现，把参数按名字传进去。

LLM返回 tool_use
name + input
→
TOOL_HANDLERS
按 block.name 查表
→
handler
(**block.input)
→
tool_result
字符串回填 messages[]

和 s01 相比，循环的骨架完全没动。唯一的差别在执行那一行：从写死的 run_bash(block.input["command"])，变成“先查表、再调用”。所以这一讲的标题才敢说“只改一行”。

但“只改一行”背后是一次视角切换：s01 把工具当成“一个要调用的函数”，s02 把工具当成“一份可增长的数据”。函数是写死在代码里的，数据是可以从配置、从插件、从远端服务里长出来的。后面第 15 讲接 MCP 时，外部工具会动态出现在 TOOL_HANDLERS 里，而这个循环依然不需要认识它们中的任何一个。

这也解释了为什么值得先停下来读 s02：它代码量不大，却是整个仓库的“扩展点样板”。后面所有机制——权限、钩子、子代理、MCP——都会反复使用同一个套路：把变化的部分做成数据或回调，让核心保持稳定。

如果这一讲只能带走一个习惯，我希望是：以后写任何“分发”逻辑时，先想想它能不能用一张表表达。能，就别写一长串 if/elif。

菜单与后厨岗位表

TOOLS 是贴在大堂的菜单：顾客（模型）看着它点菜，不需要知道后厨怎么切配。TOOL_HANDLERS 是后厨的岗位表：哪道菜归哪个师傅做。服务员（harness）拿到订单，只看菜名，就把单子递给对应的师傅。

类比到哪为止：真实餐厅的菜单和后厨可以各改各的，顶多某道菜售罄；而这里的菜单和岗位表必须严格一一对应。你加了 schema 却忘了注册 handler，模型会开心地点一道没人会做的菜，harness 只能回一句 Unknown: xxx。反过来，注册了 handler 却没写 schema，模型根本不知道这道菜存在。

03代码精读：三块拼图

第一块：工具定义，给模型看的契约

TOOLS = [
    {"name": "bash", "description": "Run a shell command.",
     "input_schema": {"type": "object", "properties": {"command": {"type": "string"}}, "required": ["command"]}},
    {"name": "read_file", "description": "Read file contents.",
     "input_schema": {"type": "object", "properties": {"path": {"type": "string"}, "limit": {"type": "integer"}}, "required": ["path"]}},
    {"name": "write_file", "description": "Write content to a file.",
     "input_schema": {"type": "object", "properties": {"path": {"type": "string"}, "content": {"type": "string"}}, "required": ["path", "content"]}},
    # ... edit_file / glob 同样格式，此处略 ...
]

input_schema 是标准的 JSON Schema。它做两件事：告诉模型“参数长什么样”，以及在你把请求发过去时，让 API 能在模型输出不符合 schema 时纠正或拒绝。注意 required 的价值：read_file 的 limit 不是必填，所以模型可以只说“读这个文件”，不用先想“读多少行”。

description 也不是装饰。它直接进入模型的上下文，是模型决定“该用哪个工具”的主要依据。写“Find files matching a glob pattern; ** matches recursively”比写“找文件”有用得多——模型会据此知道要传 **/*.py 而不是 *.py。

第二块：分发表，给 harness 用的实现

TOOL_HANDLERS = {
    "bash": run_bash, "read_file": run_read, "write_file": run_write,
    "edit_file": run_edit, "glob": run_glob,
}

这是一个再普通不过的字典，但它是这一讲真正的“机制”。它把“名字 → 实现”的映射从控制流里拿出来，变成一份数据。想加第六个工具？在 TOOLS 里加一条定义，在 TOOL_HANDLERS 里加一行映射，收工。循环不需要知道世界上有几个工具，也不需要 import 谁。

对比 s01 的写法：执行是 run_bash(block.input["command"])，工具名根本不存在，参数位置也是写死的。想加 read_file，你就得在循环里写 if block.name == "read_file": ... elif ...。五个工具还行，十个工具时循环会变成一锅粥。更糟的是，这锅粥每加一个工具都要重改一次，而循环本该是最稳定的那段代码。

第三块：分发那一行

results = []
for block in tool_calls:
    print(f"\033[33m> {block.name}\033[0m")
    handler = TOOL_HANDLERS.get(block.name)
    output = handler(**block.input) if handler else f"Unknown: {block.name}"
    print(str(output)[:200])
    results.append({"type": "tool_result", "tool_use_id": block.id, "content": output})

messages.append({"role": "user", "content": results})

三行核心，每一行都有讲究：

  • TOOL_HANDLERS.get(block.name)：用 .get 而不是 []。模型是可能编出一个不存在的工具名的（尤其是在 context 里见过别的工具之后）。用下标会抛 KeyError，整个循环当场去世；用 .get 拿到 None，还能回一句 Unknown: xxx 给模型，让它自己纠正。
  • handler(**block.input)：字典展开成关键字参数。这一步隐含一个契约：schema 里的参数名必须和 handler 的形参名逐字一致。模型给 {"path": ..., "content": ...}，handler 就得是 def run_write(path, content)。拼错一个字母，** 展开就会抛 TypeError。
  • results.append(...)：和上一讲一样，tool_use_id 必须带。工具名变了、参数结构变了，但配对规则一点没变。
核心抽象

整个工具层可以总结成一句话：模型决定“用哪个工具、传什么参数”，harness 用一张表把名字翻译成函数。想扩展能力，就加表项；循环始终只认识 block.name 和 block.input 这两个字段。

把一次工具调用从模型到回填拆开，就是五个阶段。以后无论加权限、加钩子还是加日志，都是往这五个阶段之间塞逻辑：

① 点单模型按 schema 选工具、填参数
→
② 查表harness 用 block.name 找到 handler
→
③ 执行handler(**block.input)
→
④ 兜错成功返回内容，失败返回 Error: ...
→
⑤ 回填带 tool_use_id 写回 messages[]

四个新工具，各自在防什么

回看实现会发现，它们都不是“bash 的薄包装”，每个都夹带了一个具体的防线：

def run_read(path: str, limit: int | None = None) -> str:
    try:
        lines = safe_path(path).read_text(encoding="utf-8").splitlines()
        if limit and limit < len(lines):
            lines = lines[:limit] + [f"... ({len(lines) - limit} more lines)"]
        return "\n".join(lines)
    except Exception as e:
        return f"Error: {e}"

def run_write(path: str, content: str) -> str:
    try:
        file_path = safe_path(path)
        file_path.parent.mkdir(parents=True, exist_ok=True)
        file_path.write_text(content, encoding="utf-8")
        return f"Wrote {len(content)} bytes to {path}"
    except Exception as e:
        return f"Error: {e}"
  • run_read 的 limit：截断时不是静默少给，而是补一句 ... (N more lines)。模型因此知道“后面还有”，需要时再指定更精确的范围，而不是以为文件只有这么长。
  • run_write 的 parent.mkdir(parents=True, exist_ok=True)：目标目录不存在时自动创建。没有这一行，模型得先跑一条 mkdir -p，白多一轮。工具替模型吸收掉这种“机械前置步骤”，是接口设计的一部分。
  • run_edit 的精确匹配：见下面的深入区。它把“改哪一段”的责任交给模型，靠原文匹配而不是行号，避免改错位置。
  • run_glob 的递归与上限：** 递归匹配、结果排序去重、最多 200 条，并过滤掉逃出工作区的路径。找文件变成一个可预测的操作，而不是一段需要解析的 shell 输出。

一张表看清五个工具

工具关键参数返回什么主要防什么
bashcommandstdout + stderr（截断 50000 字符）超时、危险命令、输出爆炸
read_filepath、limit文件文本 + 剩余行数提示路径越界、读太多撑爆上下文
write_filepath、contentWrote N bytes to ...路径越界、父目录不存在
edit_filepath、old_text、new_text成功或“文本未找到”路径越界、改错位置
globpattern路径列表（最多 200 条）结果过多、路径越界

这张表也解释了为什么五个工具不算多：每一个都对应一个高频动作，且都有明确的失败模式。工具不是越多越好，而是“每个都值得被单独审计”。当模型调用 write_file 时，harness 知道这是写操作；调用 bash 时，它只能看到一个命令字符串——两种信息量完全不同。

错误为什么非要用字符串返回？

看看每个 handler 的结构，它们几乎长得一模一样：try 包住全部逻辑，except Exception as e: return f"Error: {e}"。这不是偷懒，而是这一层最重要的设计决策之一。

工具失败是常态：文件不存在、权限不够、参数类型不对、路径越界、编码不是 UTF-8。这些失败对模型来说都是有用的信息——“这个文件不存在，我该先 glob 一下”。如果 handler 直接抛异常，异常会一路冒泡出 agent_loop，进程结束，模型连“失败了”都不知道，更别提重试。

所以这里的原则是：把异常翻译成模型能读的反馈。失败不是一个要终止世界的事件，而是一条要写进对话的消息。你会发现，后面所有机制（权限拒绝、钩子拦截）都沿用同一个套路——不抛异常，回一句字符串，让循环继续转。

04safe_path：文件工具的边界

四个文件工具共享一个入口检查：

def safe_path(p: str) -> Path:
    path = (WORKDIR / p).resolve()
    if not path.is_relative_to(WORKDIR):
        raise ValueError(f"Path escapes workspace: {p}")
    return path

三行代码，干了两件关键的事。(WORKDIR / p).resolve() 把相对路径拼到工作目录上，并解析掉所有 .. 和符号链接——注意是解析之后才判断，否则 ../../etc/passwd 这种字符串层面的检查一绕就过。is_relative_to(WORKDIR) 再确认最终路径仍在工作区内。

为什么这里敢 raise？因为调用它的地方在 handler 的 try 里面：run_read、run_write 等函数会捕获 ValueError，把它变成 Error: Path escapes workspace: ../x 返回给模型。也就是说，越界不是崩溃，而是一次“被拒绝的工具调用”。这是一次很好的分层示范：底层检查只管拒绝，顶层负责把拒绝翻译成对话。

为什么判断用 is_relative_to，而不是简单的字符串前缀比较？假设工作区是 /work，目标路径是 /work2/secret。字符串层面 "/work2/secret".startswith("/work") 是 True，但它明明在工作区外面。按路径组件判断，就不会被“同前缀的兄弟目录”骗过去。

符号链接是另一个经典绕过点：如果工作区里有个 link 指向 /etc，那么 link/passwd 这个“工作区内路径”实际指向系统文件。resolve() 会先把软链接解开，再做判断，所以这种绕法在 s02 里无效。

当然它仍有边界：检查与写入之间存在时间差（极端情况下路径可能被替换），而且 bash 完全不走这条路。它是“防手滑”和“防误用”的一层，不是不可绕过的安全边界。把这个定位说清楚，比夸大它的作用重要。

它只保护文件工具

safe_path 只管 read / write / edit / glob。bash 完全不受它约束——cat /etc/passwd 照样能跑。所以这一讲的“安全”是局部的、不完整的：它证明了路径检查该放在哪里，但真正的安全边界要等下一讲的权限闸门。

05一次响应里的多个工具调用

模型经常一次点好几道菜：“读一下 a.py 和 b.py，然后列出所有 .py 文件。”这时 response.content 里会躺着两个或三个 tool_use block，tool_calls 列表里也就有好几项。

s02 的处理方式很朴素：for block in tool_calls，按响应里的原始顺序，一个接一个执行。不是并行，不是多线程，就是老老实实排队。这个选择有明确的取舍：

维度顺序执行（s02 的选择）如果并行执行
顺序确定，就是响应里的顺序完成顺序不定，结果顺序需要额外维护
失败一次失败只影响那一个结果需要处理部分成功、部分失败
文件系统不会有两个工具同时改同一个文件写写冲突、读到半成品
速度慢，一个等一个快，但复杂度和风险都上来了

失败隔离在代码里的体现，是每个 handler 自己兜住异常。假设模型一次要求读 a.py（不存在）和 b.py（存在）：第一个返回 Error: ...，循环不中断，第二个照常执行。结果是两条 tool_result：一条错误、一条内容。模型下一轮就能看到“a 读失败、b 读成功”，自行决定补一个 glob 还是先写 a。

这里有个值得记住的判断：“模型一次请求多个调用”不等于“harness 要并发执行”。并发是 harness 的实现自由，不是协议要求。先做对，再谈快；这个仓库到第 12 讲才会引入后台任务，处理“慢”的问题。

返回值为什么都是字符串？

看五个 handler 的返回：read_file 返回文件文本，write_file 返回 "Wrote N bytes to ..."，glob 返回换行拼接的路径列表。没有一个是字典或对象。这是有意的：tool_result 的 content 是给模型读的自然语言，不是给程序解析的 API 响应。

如果返回一个 JSON 对象，模型得先“读懂 JSON 再理解语义”，多绕一步；而且不同工具的 JSON 结构各不一样，模型很容易记混字段。用一句人话总结结果，模型下一轮就能直接行动：“写成功了，去读回来验证”或者“路径越界了，换个位置”。

代价是机器不好解析。如果 harness 自己也想知道“这次写入多少字节”，从字符串里正则抠数字就很别扭。所以真实产品会做两层：给模型看一段摘要文本，同时另存一份结构化的工具执行记录用于日志和审计。两层各服务一个读者，不要混在一起。

设计要点

工具的返回值同时是“模型的输入”和“系统的日志源”。想清楚这一层是给谁看的，就不会纠结该返回字符串还是对象——答案往往是：给模型字符串，给系统另记一份结构。

这一段真正建立了什么

到 s02 结束，你已经有了一个稳定的“执行层”：模型说 name 和 input，harness 查表、调用、把结果变成字符串回填。加能力不用改循环，这是后面所有章节的复用基础。

但还有三样东西没建立。策略：什么操作允许、什么需要问用户——目前模型写什么就执行什么。观测：谁调了什么、花了多久、输出多大——目前只有一句 print。生命周期：循环什么时候必须停、谁能拦它——目前完全靠模型自觉。

接下来的两讲正好一人补一块：s03 用权限管线补“策略”，s04 用钩子把“策略 + 观测 + 部分生命周期”统一挂到固定扩展点上。你现在记住这个缺口，后面看代码时就知道每一段是在补哪一块。

🔬 深入：为什么 if/elif 迟早会崩？

假设你不用字典，直接在循环里写分支：

if block.name == "bash": output = run_bash(...)
elif block.name == "read_file": output = run_read(...)
看起来也能跑，五个工具时甚至挺直观。问题出在“随时间演化”：

  • 改循环才能扩能力。每加一个工具，你都要动 agent_loop 这个最该稳定的函数，回归测试的范围被动扩大。
  • 参数处理各写各的。每个分支都要手工从 block.input 里取参数，写错一个键就是运行时错误，而且错误藏在分支里，不容易看出规律。
  • 无法动态注册。分支是写死在源码里的。而后面第 15 讲接入 MCP 时，工具是运行时从外部服务器发现的——你不可能在代码里为未知工具预写 elif。
  • 容易漏。加了 schema 忘了加分支，模型点单后静默失败；字典至少还能用 .get 给出统一兜底。

所以分发表不只是“写得好看”，它把工具注册从控制流转移到了数据。数据可以加、可以删、可以由外部系统生成；控制流一旦写死，扩展就要动刀。

再深一层：schema 和 handler 的契约靠什么保证？

靠命名约定，不靠类型系统。Python 的 **block.input 只认“键名 = 形参名”，不会读你 JSON Schema 里的约束。所以 required 里写了 content，handler 形参却叫 body，运行时就会 TypeError；这个异常被 handler 外面的 try 捕获，变成一条 Error: ... 发给模型。模型看到一个语法层面的报错，通常会困惑地重试，浪费一轮。

工程上常见的加固手段：一是把 handler 签名写进测试，逐一比对 schema 的 properties；二是在分发前做一次参数校验（缺参数、多参数、类型不对都提前拒绝）；三是统一命名规范，比如 path、content、pattern 这些词全项目复用。这一讲先用最简单的约定，你在自己实现时至少要知道这层契约存在。

🔬 深入：并行调用真的并行吗？顺序和失败谁负责？

不是。模型可以在一条响应里请求多个工具，但 s02 的 harness 是串行执行的。这常被误解成“模型并行调用了工具”，其实模型只是把多个意图打包在了一次输出里。执行是 harness 的事，而这里的 harness 选择了排队。

顺序由 response.content 里的 block 顺序决定。tool_calls 是列表推导，保持原序；for 循环从头跑到尾。结果也按同样顺序 append 进 results。真正保证结果与调用对上的不是顺序，而是 tool_use_id——协议按 id 配对，不按位置。但保持顺序能让日志和调试舒服很多。

失败隔离由每个 handler 自己负责。所谓“隔离”，是指 A 的异常不会阻止 B 执行，也不会让整批结果丢失。代价是：如果 A 是个耗时 120 秒的超时命令，B 就得干等两分钟。串行系统的典型问题——木桶效应，在这里同样存在。

那什么时候该并行？当调用之间没有依赖、不写同一份资源时，比如并行读五个文件。但这需要 harness 引入线程池、结果顺序管理、以及“部分失败”的表达方式。s02 刻意不做，是因为这一讲要教的是分发结构，不是并发工程。先把边界划清楚，比先跑得快重要。

🔬 深入：read / edit 的精确匹配，glob 与 find 的差别

run_edit 的逻辑是：读全文，if old_text not in text 就直接返回错误；否则 text.replace(old_text, new_text, 1)，只替换第一次出现。这个设计把“精确匹配”的责任推给了模型：它必须先读文件，抄一段真实存在的原文，才能改。模糊匹配、按行号猜、正则替换全都没有——因为对 Agent 来说，改错文件比改不动文件危险得多。

但 replace(..., 1) 有个安静的坑：如果 old_text 在文件里出现多次，它只改第一处，不报错也不提示。模型以为改完了，其实别的副本还在。成熟的 edit 工具会要求“匹配必须唯一”，或者返回“发现 N 处匹配，请提供更多上下文”。自己实现时，这一点值得抄走。

run_glob 和 shell 的 find 看起来都是“找文件”，差别却在接口形状：glob 接收一个模式，返回排序、去重、限制在 200 条、且被限制在工作区内的路径列表；find 是一条 shell 命令，返回任意格式的文本，还能顺手执行 -delete。glob 的输出是模型可以直接拿去调 read_file 的干净路径，find 的输出还得再解析。前者是“结构化工具”，后者是“万能但不受控”。

这也是这一讲反复出现的主题：专用工具牺牲了一点灵活性，换来稳定的接口和可审计的参数。值不值，取决于你要做的是玩具还是产品。

再深一层：为什么不用行号或 diff 来编辑？

行号编辑看起来更精确：replace_line(path, 42, "new code")。但它有一个前提——文件内容在你读它和改它之间没有变过。Agent 的运行是异步的：它可能在读完之后又跑了格式化、又执行了另一个写入工具，等它回头按行号改时，第 42 行已经换人了。结果就是“改成功，但改错了地方”，而且不会报错。

原文匹配天然更稳：只要那段文本还在文件里，改的就是它；不在了，就明确失败，模型可以重新读一遍再改。代价是模型必须先把原文抄对，长文件里抄错一个空格就会失败——所以“先 read 再 edit”成了 Agent 的固定动作。

真实的 edit 工具通常还会加两条约束：匹配必须唯一（出现两处就报错，要求更多上下文），以及失败时不写入（先检查后写，避免半成功）。这一讲的实现只做了“必须存在”，另外两条留给你自己补。写工具的时候多问一句“它失败时会不会悄悄改错”，胜过事后加一堆校验。

🔬 深入：description 才是模型选工具的依据

很多人把 description 当成注释，随手写一句“读文件”。它其实是模型做选择的唯一说明书——工具名、描述、参数 schema 一起进入上下文，模型据此决定这一轮要不要调、调哪个。描述写得含糊，模型就会做出你看不懂的选择：明明有 read_file，它偏用 bash cat；或者该用 glob 时反复 find。

好的描述通常会回答四件事：做什么（Read file contents）、关键参数怎么填（** matches recursively）、边界在哪（最多返回 200 条）、什么时候别用（比如“编辑请用 edit_file，不要用 write_file 覆盖整文件”）。后两条最容易被省略，也最影响行为。

看 s02 的实际写法：bash 是“Run a shell command.”，edit_file 是“Replace exact text in a file once.”。后者把“exact”和“once”都点出来了，模型就知道要抄原文、且只会改一处。这不是文学修辞，是在给模型写接口文档。

但描述不是越长越好。它每轮都占上下文，五个工具各写两百字，就是一千字的固定开销。取舍标准和代码注释一样：写“不看就会用错”的信息，省略“看了也不会用错”的常识。

06动手实验

  1. 加第六个工具。照着 read_file 的样子，在 TOOLS 里加一个 list_dir（参数 path），在 TOOL_HANDLERS 里注册一个 run_list，返回目录项列表。运行 python s02_tool_use/code.py，输入“列出当前目录下的所有文件”。预期：模型开始使用你的新工具，而 agent_loop 一行没改。这就是分发表的价值。
  2. 制造一次参数拼写错误。把 TOOLS 里 read_file 的属性名 path 改成 file_path，但 handler 仍然叫 run_read(path, limit=None)。跑一次“读 README.md”。预期：handler 收到 file_path=... 后抛 TypeError，被 except 捕获，模型收到一条 Error: ...，然后大概率重试一次仍然失败。亲眼看一看“契约错位”长什么样。
  3. 试试目录穿越。输入“读一下 ../../etc/hosts”。预期：read_file 返回 Error: Path escapes workspace；模型会改用 bash cat，然后成功——因为 bash 不受 safe_path 约束。这个对比正好引出下一讲。
  4. 观察多工具调用。输入“同时读 README.md 和 requirements.txt，再找一下所有 .py 文件”。在分发处 print(block.name)，观察模型一次返回了几个 tool_use、执行顺序是否和响应顺序一致。再把其中一个文件名改错，确认“一条失败、其余照跑”。
  5. 用 description 引导选择。把 read_file 的 description 改成一句容易误解的话，例如“Run a shell command to read a file.”，再输入“读一下 README.md”。预期：模型更可能选择 bash 而不是 read_file。改回清晰描述后重试，观察选择是否回来。这个小实验能让你直观感到：工具描述是行为的一部分，不是文档。
加工具前的三个问题

这个动作高频吗？它的参数能稳定结构化吗？它失败时能给出模型看得懂的字符串吗？三个都是“是”，才值得加一个工具。否则宁可让模型用 bash——多一个工具，就多一份 schema 维护成本和上下文开销。

做完这几个实验，最好再回头看一眼分发那一行代码。你会发现它短得不像“机制”，但正是这四行让工具数量从 1 变成 5、将来变成 50，而循环不变。判断一段代码重不重要，不要看它多长，要看它承担了多少变化。

07常见误区

  • 很多人以为多写几个工具就“更强”了。其实工具没有增加模型的原始能力，bash 都能做。增加的是接口质量：更少翻译、更少转义、更结构化、更容易被权限和日志系统处理。判断该不该加工具，问的不是“能不能做”，而是“这个动作是否高频、是否值得一个稳定接口”。
  • 很多人以为 handler 里应该让异常冒出去，交给上层统一处理。在这一层不行。工具失败是要写进对话的信息，不是要终止程序的事故。正确姿势是 handler 内部兜住异常、返回字符串；上层判断的只是“要不要继续循环”。
  • 很多人以为 safe_path 让 Agent 安全了。它只保护文件工具。模型完全可以用 bash 绕过，../../etc/hosts 不行就 cat /etc/hosts。真正的权限边界必须建在“所有工具执行之前”，而不是某一个工具内部。
工具是能力边界，也是审计边界

模型能做什么，取决于你注册了哪些工具；系统能审计什么，取决于工具被切得多细。bash 是一把万能钥匙，但它只留下一条命令字符串；write_file 留下的是一次明确的写操作和路径。想让权限、日志、审批做得准，就把高频动作拆成具名工具。

到这里，这一讲的主干就讲完了。接下来先自己动手，再对答案——看代码和写代码之间，差的从来不是理解，而是那几次亲手改错。

08自测

五道题从“机制细节”问到“设计取舍”，建议先自己想一遍再展开答案。

如果模型返回一个 TOOL_HANDLERS 里没有的工具名，会发生什么？

TOOL_HANDLERS.get(block.name) 返回 None，于是 output 变成 f"Unknown: {block.name}"。这条字符串照常作为 tool_result 回填，循环继续。模型下一轮看到“工具不存在”，通常会换成已知工具重试。注意：这里用的是 .get，如果写成 TOOL_HANDLERS[block.name]，就会抛 KeyError，整个循环直接终止。

模型一次返回三个 tool_use，其中第二个执行失败。第一个和第三个还会执行吗？

会。失败被第二个 handler 内部的 try/except 吃掉，返回一条 Error: ... 字符串，循环进入第三次迭代。三个结果都会出现在 results 里，按原顺序排列。这正是“失败隔离”的含义：一次工具失败只影响它自己那条 tool_result，不影响同批其他调用，也不中断 agent 循环。

给 TOOLS 加了新工具、却忘了在 TOOL_HANDLERS 里注册，会怎样？

模型看得见这个工具（schema 在 TOOLS 里），于是可能调用它；但 harness 查不到实现，只会返回 Unknown: 工具名。模型会困惑、重试、或者改用别的工具。这是“菜单和后厨岗位表必须同步”的典型翻车。反过来，注册了 handler 却没写 schema，模型根本不知道有这个工具，永远不会调用——症状更安静，也更难查。

把 run_read 里的 limit 逻辑删掉，只返回全文，风险是什么？

一个大文件就能把上下文撑爆。比如读一个几万行的日志，几千 token 的输出会挤占模型注意力，还可能让后续轮次超出上下文窗口。limit 加上“还有 N 行”的提示，是在“给模型足够信息”和“别把预算烧光”之间做平衡。工具返回什么、返回多少，本身就是一个设计决策。

为什么说“多工具”是为下一讲的权限做铺垫？

因为权限判断需要知道“这是什么操作、参数是什么”。bash 时代 harness 只有一坨字符串，只能做脆弱的子串匹配；有了具名工具和结构化参数，权限系统才能精确地说“write_file 的 path 在工作区外，需要审批”“bash 的命令里含删除动作，需要审批”。s02 先把接口结构立起来，s03 才有地方挂闸门。

延伸：工具改完之后，谁来验证结果？

这一讲的所有工具都只负责“执行”，不负责“验证”。write_file 返回 Wrote 100 bytes，不代表内容写对了；edit_file 返回 Edited，也不代表改的是你想要的那一处。模型的常见做法是“写完再读回来确认”，这需要多花一轮，但比默默写错强。

更成熟的做法是在工具层做校验：写之前检查内容、写之后读回比对、edit 时确认匹配唯一。但校验逻辑一多，工具本身就开始膨胀。s04 给出的解法是把这类“执行前后要做的事”挂到钩子上——写之前检查、写之后提醒，而工具保持单一职责。

所以你读源码时可以留意这个规律：工具负责“做”，钩子负责“看”和“拦”。两者分开，工具才好测，钩子才好换。下一讲先补“拦”，再下一讲补“看”，顺序刚好。

一个自检习惯

每加一个会改文件的工具，就问自己：它失败时会留下半成品吗？重试一次安全吗？如果答案让你犹豫，先把它改成“先校验、后写入”，再谈接进循环。Agent 会重试，工具最好别怕重试。

最后提醒一句：不要把“工具写得万能”当成目标。工具的价值在于边界清晰——输入是什么、输出是什么、什么情况下失败、失败了让谁知道。这四条写清楚，后面权限和钩子才有抓手；写不清楚，再多工具也只是把混乱搬进循环里。

这一讲带走

加工具不是加代码，是加两行数据：一条 schema、一条映射。循环只认识 name 和 input，所以它可以一直保持不变。这个“数据扩展、控制流稳定”的结构，是后面所有能力的地基。
