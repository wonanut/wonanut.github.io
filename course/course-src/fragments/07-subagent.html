01一个真实的麻烦：探路的成本全留在了账上

Agent 在修一个 bug。 为了定位问题，它要追踪调用链：先 grep 找到入口，再读 handler，再顺着 import 读 service、读 model、读配置文件。 前后十几个工具调用，每个 read_file 都往 messages[] 里塞进几百行代码。

半小时后，调用链终于弄清楚了，结论其实只有一句话："问题出在 service 层把 None 当成了合法返回值。 " 但那几十个文件的内容、那些已经无用的中间输出，还全部躺在上下文里。 它们不会自动消失，反而在接下来的每一轮里被重新发送、重新计费、重新稀释注意力。

这就是"探路成本"的不对称：过程很贵，结论很轻。 而 Agent 循环默认把过程全记在账上，因为它们都是 messages[] 的一部分。 上下文窗口就这么大，探一次路，后面的修改和验证就没地方了。

反过来想就通了：如果这部分工作发生在另一个对话里，它读了多少文件都不影响我这边的账本，我只要它最后交回来一张纸条，写清楚结论。 这就是子代理（subagent）的全部动机。

02直觉：派一个人去档案室，只带回来一页纸

像派实习生去档案室查资料

你要写一份报告，需要查清十年前某份合同的条款。 与其自己钻进档案室翻两百个文件夹，不如派一个实习生去。 他在里面翻多久、弄得多乱，你的办公桌都不受影响；他回来时只交给你一页纸的结论。

类比到哪为止：实习生和你在同一个公司、同一个文件柜——他能改文件柜里的东西，你也能看见他的改动。 Subagent 隔离的是"对话记录"，不是进程、文件系统或权限。 它不是沙箱。

落到代码上，这个"另一个房间"不是进程、不是线程，而是一个全新的 messages[] 列表。 父循环照常把 task 当成一个普通工具来调用；run_subagent 收到 prompt，开一个属于子代理的循环，跑完把最终文本当作工具结果交回去。

父 Agentmessages[] 很长
→
task 工具调用，传入 prompt
→
run_subagent新建 messages=[prompt]
→
子循环用它自己的上下文跑工具
→
final text作为一条 tool_result 回父循环

注意这整条路径里，父与子的"接口"只有两处：进去时一个 prompt 字符串，出来时一段 final text。 子代理中间调了多少工具、读了多少文件、错了多少次，父循环一概看不见——也不需要看见。

决策本实现的选择原因
对话全新的 messages[]不把父对话复制给子代理
执行同进程、同 WORKDIR、同 hooks文件系统改动两边都看得见，权限策略一致
返回值只返回最终文本中间工具调用和结果不进入父消息列表
委派深度SUB_TOOLS 里没有 task只允许一层委派
终止条件没有工具调用 / 最多 30 轮防止子代理陷入死循环

03代码精读：一个循环套一个循环

先看子循环本身。 它和父循环几乎是同一个形状，最大的不同是第一行：messages 是新建的，只装了 prompt 这一条。

def run_subagent(prompt: str) -> str:
    messages = [{"role": "user", "content": prompt}]   # 全新的 messages
    for _ in range(30):
        response = client.messages.create(
            model=MODEL, system=SUB_SYSTEM,
            messages=messages, tools=SUB_TOOLS, max_tokens=8000,
        )
        messages.append({"role": "assistant", "content": response.content})
        tool_calls = [
            block for block in response.content if block.type == "tool_use"
        ]
        if not tool_calls:                              # 子代理说完了
            return extract_text(response.content) or "(no summary)"
        results = []
        for block in tool_calls:
            output = execute_tool(block, SUB_HANDLERS)
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": output})
        messages.append({"role": "user", "content": results})
    return "Subagent stopped after 30 turns without a final answer."

逐块解释："

  • messages = [{"role": "user", "content": prompt}] 是本讲的题眼。 它意味着子代理看不到父对话的任何一个字——它只知道这个任务。 这既是隔离，也是失真：父代理知道的背景（用户偏好、之前的决策、已经踩过的坑），子代理一概不知。
  • for _ in range(30) 是一个硬上限。 父循环的 while True 靠"模型不再调工具"来终止，子代理可能因为任务表述模糊而一直转圈，所以额外加一个回合上限兜底。
  • if not tool_calls: return extract_text(...) 是子循环唯一的正常出口。 注意它返回的不是 response.content（里面可能有多个 block），而是 extract_text 抽出来的纯文本——这是"只回传 final text"在代码里的具体落点。
  • 最后一行 return "Subagent stopped after 30 turns without a final answer." 是一种显式失败回报：不抛异常，而是把失败也变成父代理能读到的一条文本。 父循环照常把它塞进 tool_result，模型看到后可以重派、换策略，或者放弃。

最后一段文本是怎么被"抽"出来的？ return extract_text(response.content) 这一行把"只回传 final text"落成了具体的数据操作：

def extract_text(content) -> str:
    if not isinstance(content, list):
        return str(content)
    return "\n".join(
        getattr(block, "text", "")
        for block in content
        if getattr(block, "type", None) == "text"
    )

子代理最后一条响应通常只包含 text block，但也可能有别的类型。 extract_text 只挑出 type == "text" 的块拼起来，其余全部丢弃——这就是"上下文隔离"在返回路径上的实现。 注意它返回的是字符串，不是消息对象：父循环拿到后只会生成一条 tool_result，子代理的消息结构在函数返回的那一刻就被彻底丢掉了。

还有一处容易漏看：子代理用的是 SUB_SYSTEM，不是父代理的 SYSTEM。 它多了一句 "Complete the given task, then return a concise final answer."。 这句话不是装饰——它在子代理的每一次系统调用里重复强调"你的产出是给别人的一段答案"，从而抑制它写长篇过程记录。 system prompt 的措辞会直接塑造返回值的形状，这在设计子代理时值得当成接口契约来对待。

再看工具池怎么裁。子代理用哪套工具，是一行赋值的区别：

SUB_TOOLS = list(BASE_TOOLS)          # 五个基础工具，没有 task
SUB_HANDLERS = dict(BASE_HANDLERS)

TASK_TOOL = {
    "name": "task",
    "description": "Run a subagent with fresh conversation context and return its final text.",
    "input_schema": {
        "type": "object",
        "properties": {"prompt": {"type": "string", "minLength": 1}},
        "required": ["prompt"],
    },
}

TOOLS = [*BASE_TOOLS, TASK_TOOL]      # 父代理：5 + task
TOOL_HANDLERS = {**BASE_HANDLERS, "task": run_subagent}

两个细节值得停一下。 第一，list(BASE_TOOLS) 是浅拷贝外层列表：工具定义 dict 本身还是共享的引用。 这里没关系，因为工具定义只读不改；但如果哪天你想给子代理的某个工具换描述，记得深拷贝，别偷偷改了父代理的 schema。

第二，也是更重要的一点：SUB_TOOLS 里没有 task。 这不是疏漏，是刻意的边界——子代理不能再派子代理。 没有这条限制，一个"帮我查查"的任务可能退化成无限递归的委派树，每一层都烧 token、每一层都丢失上下文，最后谁也没在真正干活。 需要嵌套时再显式加上 task 并限制深度，那是另一个设计问题。

为什么 execute_tool 要接受 handler 参数？ 这是从 s05 到 s06 最不显眼、但最见功力的一处重构：

def execute_tool(block, handlers: dict) -> str:
    blocked = trigger_hooks("PreToolUse", block)
    if blocked:
        return str(blocked)
    handler = handlers.get(block.name)
    try:
        output = handler(**block.input) if handler else f"Unknown: {block.name}"
    except Exception as e:
        output = f"Error: {e}"
    trigger_hooks("PostToolUse", block, output)
    return str(output)

s05 里这段逻辑是直接内联在 agent_loop 里的，工具表写死为 TOOL_HANDLERS。 到了 s06，父循环要用 TOOL_HANDLERS（含 task），子循环要用 SUB_HANDLERS（不含 task），于是把"用哪张表"变成参数传进来。 这个泛化带来两个好处：

  1. 权限和日志钩子天然共享。 子代理的工具调用同样经过 trigger_hooks("PreToolUse")，也就是说子代理删文件一样要过 deny list、一样要向用户确认。 隔离的是上下文，不是权限。
  2. 错误处理只有一份。 handler 抛异常、工具名不存在，都在同一个地方兜住，变成 Error: ... 文本返回给对应循环的模型。 父和子看到的是同一种错误格式。
设计要点

子代理不是"更小的模型"，也不是"更安全的沙箱"。 它是同一个模型、同一套工具、同一份权限，换了一个全新的 messages[]。 所有"隔离"都发生在消息层，不发生在执行层。

顺带一提，task 工具只接受一个 prompt 字符串，这让"怎么写 prompt"变成了使用子代理最重要的技能。 一条好的子任务 prompt 至少要说清三件事：目标（要产出什么结论）、边界（去哪里找、不要动哪些文件）、回报格式（结论 + 证据）。 因为子代理看不到父对话，任何"你也知道的那个问题"都必须重述一遍——这既是它的缺点，也逼着调用方把任务想清楚。

小技巧

派活时把"验收标准"写进 prompt，比如"回答里必须包含你读过的文件路径和证明结论的那一行代码"。子代理的 final text 是父代理唯一能看到的东西，验收标准写在哪，它就会往哪个方向总结。

04上下文隔离的本质：出口只有一个

把子代理想象成一块"上下文抽水机"：它把原本会灌进父窗口的东西（几十个文件内容、十几次工具往返）抽走，只在出口处留下一段文本。 父代理的 messages[] 里只多了一条 tool_result。

这带来两个常被混淆的收益，需要分开算账：

省的是上下文空间

父窗口不再被探路过程占满，后面的修改、验证、长任务还能继续。这是子代理最确定的收益，和模型价格无关。

省不省 token 要看总账

子代理自己也要调用模型、传输工具结果。总 token 往往比"父代理自己干"更多，只是分摊到了两个窗口。它买的是"父窗口的可用性"，不是"更便宜"。

再算一笔粗账。 父代理自己读 40 个文件，假设每个文件 3000 token，光文件内容就 12 万 token；改成子代理去读，父窗口只多一条可能几百 token 的结论。 子代理那边确实消耗了这 12 万 token，但那是另一个窗口里的消耗，而且那个窗口用完就丢——父代理后面的任务依然有充足空间。 如果子代理只用来做一次短查询，总 token 甚至可能更多；如果用来探索一个陌生仓库，父窗口能省下的空间是数量级的。 这就是为什么判断标准必须是"信息后续还需不需要"，而不是"总 token 会不会变少"。

所以"什么时候派子代理"有一条清晰的标准：当这段工作产生的中间信息，对后续任务不再需要时。 "帮我查一下这个项目用什么测试框架"是典型——过程很脏，结论很干净。 "帮我把这个文件里的函数重命名"通常不值得——工作本身很短，派一个子代理反而多一次上下文重建和一次结论转述。

任务形状建议原因
读几十个文件、定位一条调用链派子代理中间结果后续无用，结论可压缩成一段话
在陌生代码库里做一次可行性调研派子代理探索过程不确定，失败也不该污染父上下文
改一个文件、跑一次测试自己做过程短，子代理的上下文重建成本反而更高
需要连续多轮的状态调整（改—测—修）自己做状态强，跨窗口转述会丢细节
多个互不依赖的调研任务可并行派发天然隔离，但本章实现是串行同步的

还有一层：本章是串行同步的。 run_subagent 在父循环里被同步调用，父代理在它返回前完全停住。 如果一次响应里有多个 task 调用，它们会依次执行。 真正的并行子代理需要并发执行工具、按顺序回填结果，那是生产环境的话题；本章先建立"隔离"这个核心心智模型，并行是它之上的工程优化。

子代理和上一讲的 todo 正好互补：todo 管"接下来做哪几步"，子代理管"其中某一步在哪儿做"。 一个负责注意力，一个负责上下文空间，两者都不改变模型能力，只改变信息怎么摆放。

🔬 深入：为什么不共享父历史？以及只回传一段文本的三个坑

先回答"为什么不直接共享父历史"。把父代理的 messages[] 复制一份给子代理，看起来省事，实际有三个坏处。 第一，父历史里的中间细节会全部进入子代理的窗口，子代理反而更容易在无关信息里迷路——它本来只需要知道任务本身。 第二，父子共享同一段历史后，"哪些是父代理说的、哪些是子代理做的"会混在一个消息流里，后续压缩和审计都失去边界。 第三，成本会翻倍：同一段历史在每个子代理里各传一遍，子代理越多、越贵。 所以最干净的做法是让接口只有两句话："给你这个任务"和"把结论给我"，其余一概不传。

坑一：final text 丢失结构化信息。 父代理拿到的是一段自然语言。 它不知道子代理读了哪些文件、哪些结论是推测、哪些是实测。 如果子代理说"没找到测试框架"，父代理无法区分"确实没有"和"子代理没找对地方"。 改进方向：在 task 的 prompt 里明确要求返回格式（例如"列出你读过的文件路径 + 每条结论的依据"），或者在生产环境里用结构化输出、把关键文件路径写进 final text 便于复核。 代价是 final text 变长，隔离的收益被侵蚀一点——这是一个可以调的旋钮，不是非黑即白。

坑二：子代理悄悄失败。 run_subagent 的失败几乎都变成了"正常文本"：(no summary)、Unknown: ...、30 轮超时的提示。 父循环分不清"任务完成"和"任务放弃"，除非文本里写清楚了。 给子代理的 prompt 里要求它显式报告失败原因，比在父循环里猜更可靠。

坑三：共享文件系统的副作用。 子代理和父代理在同一个 WORKDIR 里。 子代理写过的文件、删过的东西，父代理下次 read_file 就会看到。 这既是特性（子代理可以真的把活干完），也是风险（一个跑偏的子代理会污染工作区）。 所以权限钩子必须共享——这也是 execute_tool 泛化那一步的隐藏价值。

再深一层：如果真要嵌套子代理，边界该怎么划？

把 task 加进 SUB_TOOLS 很容易，难的是控制它的后果。 至少要加四个约束：

其一，深度上限。 给 run_subagent 加一个 depth 参数，超过 2 层就拒绝并返回错误。 其二，预算上限。 每层有独立的 turn 数和 token 预算，父层能看到子层的消耗。 其三，回报协议。 深度越深，final text 的信息损失越严重；要么每层都要求结构化摘要，要么限制嵌套只用于"读多写少"的探索任务。 其四，写权限收窄。 子代理的子代理通常只该有只读工具，否则一个误判会连着写坏三层。

还有一个反直觉的点：嵌套并不总是更省上下文。 中间层的 final text 会成为上一层的工具结果，如果中间层转述得啰嗦，父窗口反而更挤。 生产系统里，嵌套深度通常被压得很低（1–2 层），原因不是实现不了，而是收益随深度快速衰减、调试成本指数上升。

05动手实验：看见那条"只回传一条消息"的边界

  1. 跑起来：python s06_subagent/code.py，输入 Use a subtask to find what testing framework this project uses。
  2. 看前缀：终端会先打印 [Subagent started]，子代理的每次工具调用带 [sub] 前缀，结束时打印 [Subagent done]。 确认父代理自己没有读任何文件——那些 read_file 全部发生在子循环里。
  3. 量一下隔离效果：在 run_subagent 的 return 之前加一行 print(f"[sub] local messages: {len(messages)}")，再在父循环 agent_loop 收到 task 结果后打印 len(messages)。 预期现象：子循环内部消息可能有十几条，而父循环只增加了 2 条（assistant 的 tool_use + user 的 tool_result）。
  4. 观察失败回报：给一个故意模糊的任务，比如 Use a task to investigate something。 看子代理是给出一段含糊的总结，还是触发 30 轮上限。 记下父代理收到这段文本后怎么反应——它是重新派了一次、自己动手，还是直接接受了模糊结论？
  5. 让子代理附上证据：把 task 的 prompt 改成 "Use a task to find the testing framework. Require the subagent to list the files it read and quote the exact line that proves the answer."。 重跑后比较：父代理拿到的 final text 是否变长、结论是否更容易复核。 这个实验能让你直观感受到"隔离"和"可验证"之间的张力。
  6. 危险实验（可选）：把 SUB_TOOLS = [*BASE_TOOLS, TASK_TOOL] 打开，输入一个会诱发递归委派的任务，观察它是否会陷入"派子代理去派子代理"。 这个实验不需要跑很久就能看到 token 消耗失控的趋势，动手前想清楚。

06常见误区

误区一：以为子代理省钱

子代理省的是父窗口的上下文空间，不是账单。 它自己也要跑循环、发请求、传工具结果，总 token 常常比父代理单干更多。 正确的判断标准是"这段过程的中间信息后续还要不要"，而不是"能不能少花钱"。

误区二：把子代理当沙箱

它和父代理同进程、同工作目录、同一套权限钩子。 子代理的一条 bash 可以删掉父代理正在编辑的文件。 如果你需要真正隔离，那是容器、工作树（worktree）或权限系统的事，不是子代理。

误区三：以为 final text 是可信的结论

父代理拿到的是一段自然语言，无法区分"查证过的结论"和"子代理的猜测"。 生产系统里通常要求子代理在 final text 里附上证据（文件路径、命令输出片段），或者由父代理对关键结论做一次独立校验。 子代理是加速器，不是免检章。

07自测

父代理和子代理共享 WORKDIR，那"上下文隔离"到底隔离了什么？

隔离的是对话记录：子代理拥有全新的 messages[]，父代理的历史不会传进去，子代理的中间工具调用也不会传回来。 文件系统、进程、环境变量、权限钩子都是共享的。 所以子代理能看到父代理刚写的文件，父代理也能看到子代理的环境改动；但子代理读过的 200 个文件内容不会出现在父代理的上下文里。 一句话：隔离消息，不隔离世界。

把 SUB_TOOLS 写成 TOOLS（含 task）会发生什么？为什么本章刻意不这么做？

子代理就能再调用 task，形成递归委派：子代理派子代理，理论上可以无限深。 后果有三层：一是 token 消耗随深度爆炸且难以归因；二是每一层只传 final text，信息在每一层都被有损压缩一次，最底层的细节到顶层几乎不剩；三是调试极其困难，你很难知道某个错误结论是哪一层产生的。 本章刻意让 SUB_TOOLS 不含 task，把委派深度钉死在 1 层——先建立正确的心智模型，再谈扩展。

子代理任务失败（比如一直没找到答案），父代理为什么会"不知道它失败了"？

因为失败在代码里被转成了普通文本：(no summary)、Subagent stopped after 30 turns without a final answer.，以及工具层的 Error: ...。 这些都会作为一条正常的 tool_result 回到父循环，父代理只能从文本内容里推断。 而且 run_subagent 的循环本身不抛异常，父循环拿不到任何"失败信号"。 解决办法是在 task 的 prompt 里要求子代理显式说明"我尝试了什么、卡在哪、结论是否可靠"。

一个任务需要读 40 个文件来定位 bug，然后修改 1 个文件并跑测试。你会怎么拆？

把"读 40 个文件定位"派给子代理，让它只回传"根因 + 关键文件 + 证据"；父代理拿到结论后自己改那 1 个文件、自己跑测试。 理由：读文件的中间产物后续完全不需要，正好是上下文隔离的甜点区；而修改和验证需要连续的上下文（改了什么、测试报了什么），拆出去反而要在两个窗口之间来回转述，得不偿失。 判断口诀：过程脏、结论轻 → 派出去；过程短、状态强 → 自己做。

execute_tool 把 handler map 作为参数传入，除了让子代理用不同的工具表，还有什么收益？

它保证父与子走同一条工具执行路径，于是 PreToolUse / PostToolUse 钩子、异常兜底、Unknown: ... 处理全部共享。 子代理因此无法绕过权限检查——它删文件一样要过 deny list，越界访问一样要用户确认。 如果 s06 复制一份 execute_tool 给子循环，两条路径迟早会漂移，权限漏洞往往就出在这种"看起来差不多的复制"里。

这一讲带走

子代理的本质不是"更小的模型"，而是"换一个全新的 messages[] 跑同一个循环"：进去一个 prompt，出来一段 final text，中间的过程不进父窗口。 隔离消息，不隔离世界；省的是上下文，不一定省 token。
