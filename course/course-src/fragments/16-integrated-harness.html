01十七个 demo，拼不成一个 Agent

回顾一下你学过的东西：s01 给了循环，s02 给了工具，s03 给了权限，s04 给了 hooks，s05 给了 todo，s06 给了子代理，s07 给了技能，s08 给了压缩，s09 给了记忆，s10 给了任务图，s11 给了后台任务，s12 给了 cron，s13 给了团队和工作树（worktree），s14 给了 MCP。每一讲都是独立的 code.py，各自跑得通。

现在把它们放进同一个进程，问题立刻出现：谁先谁后？压缩应该在组装 system prompt 之前还是之后？cron 注入的消息应该在压缩前还是压缩后？权限检查是工具执行前的一行 if，还是一个 hook？后台任务的结果什么时候变成消息？

这些问题的共同点是：它们都不是"某个机制怎么实现"，而是"多个机制在同一轮里如何排序"。一个能长期工作的 coding agent 需要的不是第 18 个机制，而是一个把已有机制按正确顺序串起来的运行时。

像机场塔台，而不是再多买一架飞机

机场已经有跑道、廊桥、行李系统、加油车、安检。真正让航班准点的是塔台的调度顺序：先放行哪架、什么时候加油、行李什么时候上、安检排队怎么消化。塔台本身不飞，它只决定"谁先动"。

类比到哪为止：塔台调度的是同时发生的事件，可以并行；Agent 循环大部分步骤是严格串行的——你必须先压缩完才能组装 prompt，先拿到 tool_use 才能执行工具。所以这里的"顺序"更像流水线工位，而不是机场跑道。搞混两者，就会写出"权限检查和工具执行并发"这种危险代码。

设计要点

集成不是把所有代码粘在一起。s15 的价值在于它给出了一个可复用的"装配点清单"：每个机制只在一个明确的时机被调用，输入输出都是 messages[] 或一个上下文对象。装配点稳定之后，加新机制的边际成本才会降下来。

如果按"机制来自哪一讲"重新看 s15 的工具表，你会发现它其实是一张前序章节的目录：

而循环的骨架仍然只有那四步，和 s01 一模一样：

def agent_loop(messages: list, context: dict, active_request: str):
    tools, handlers = assemble_tool_pool()
    state = RecoveryState()
    max_tokens = DEFAULT_MAX_TOKENS
    while True:
        fired = consume_cron_queue()
        for job in fired:
            messages.append({"role": "user",
                             "content": f"[Scheduled] {job.prompt}"})
        inject_background_notifications(messages)
        prepare_context(messages, active_request)
        context = update_context(context, messages)
        tools, handlers = assemble_tool_pool()
        response = call_llm(messages, context, tools, state, max_tokens)
        # ... stop_reason == "max_tokens" 时升级 token 上限或要求续写
        messages.append({"role": "assistant", "content": response.content})
        if not has_tool_use(response.content):
            trigger_hooks("Stop", messages)
            remember_after_turn(messages)
            return
        # ... 下面逐个执行 tool_use block

这段代码里没有一行"新机制"。它做的全是排序：定时任务先注入，后台通知再注入，然后压缩，然后更新上下文、重新组装工具池、调模型。每个机制都在自己该在的位置上。

03一个真实回合：从用户敲回车到下一轮

把顺序落到一次具体回合里。下面这条轨迹是简化后的终端输出，左边是事件，右边是"谁在什么时候做了什么"：

[UserPromptSubmit hook] working in /repo
user: 在后台安装依赖，同时继续阅读 README.md。

[cron] no due jobs
[background] no finished tasks
[compact] snip_compact: 42 -> 30 messages
[prompt] memory: 2 relevant records | skills: 10 | mcp: docs
> bash(run_in_background=true)
[PreToolUse hook] permission: allow
[background] bg_0001: pip install -r requirements.txt
tool_result: [Background task bg_0001 started]

> read_file(README.md)
[PreToolUse hook] permission: allow
[PostToolUse hook] 12.4 KB output
tool_result: ...README 内容...
[Stop] turn finished with 4 tool results

注意第一行和最后一行：UserPromptSubmit 在模型调用之前，Stop 在本轮没有 tool_use 之后。它们不是装饰性的日志，而是扩展点：审计系统可以在第一行记录用户输入，在最后一行统计工具调用次数。中间那段才是模型真正参与的推理与工具选择。

还要注意 [background] 出现的位置。启动后台任务时，主循环没有等 pip install 结束，而是立刻拿到占位结果继续读 README。如果这时用户又输入一句话，下一轮开始前会先检查后台结果；如果后台还没完成，检查就是空操作。整个机制没有一个"后台轮询循环"，只有"每轮开始前顺手收一下已完成的結果"。

04代码精读：四个必须按顺序发生的装配点

prepare_context：压缩是一组有先后的工序

压缩不是"调一个函数把上下文变小"那么简单。s15 把它拆成四级，从最便宜、最不伤信息的手段开始：

def prepare_context(messages: list, active_request: str) -> list:
    # Every LLM turn enters through the same context budget pipeline.
    messages[:] = tool_result_budget(messages)
    messages[:] = snip_compact(messages)
    if estimate_size(messages) > CONTEXT_LIMIT:
        target = int(CONTEXT_LIMIT * 0.8)
        messages[:] = micro_compact(messages, target)
        if estimate_size(messages) > CONTEXT_LIMIT:
            messages[:] = fit_tool_results(messages, target)
    if estimate_size(messages) > CONTEXT_LIMIT:
        messages[:] = compact_history(messages, active_request)
    return messages

顺序有明确动机。tool_result_budget 先处理单条超大工具输出，因为它最占地方、又最容易安全地换成一个摘要或路径；snip_compact 再按消息条数裁剪中段，因为早期消息价值通常最低；只有仍然超限时才动用 micro_compact 压缩旧 tool_result，最后才让 compact_history 做一次真正的摘要。每一步之后都重新估算大小，避免"明明裁完就够了，还多花一次摘要调用"。

这里还有一个容易忽略的细节：compact_history 接收 active_request。摘要不是把历史均匀压扁，而是要知道"用户当前到底要什么"，才能在摘要里保留相关线索。压缩是有损的，损哪些信息取决于你以为任务是什么——所以这个参数必须由宿主从本轮请求里传进来，而不是让模型在压缩时自己猜。

assemble_system_prompt：每轮重建，而不是启动时拼一次

system prompt 在 s15 里不是一个常量，而是一个每轮重新计算的函数。原因很直接：技能目录会变、已连接的 MCP server 会变、记忆会变、队友会变、时间也会变。

def assemble_system_prompt(context: dict) -> str:
    sections = [PROMPT_SECTIONS["identity"],
                PROMPT_SECTIONS["tools"],
                PROMPT_SECTIONS["tasks"],
                PROMPT_SECTIONS["teams"],
                PROMPT_SECTIONS["workspace"],
                PROMPT_SECTIONS["memory"],
                PROMPT_SECTIONS["compaction"]]
    sections.append(f"Current time: {datetime.now().isoformat(timespec='seconds')}")
    sections.append("Skills catalog:\n" + list_skills() +
                    "\nUse load_skill(name) when a skill is relevant.")
    if context.get("memory_catalog"):
        sections.append(f"Memory catalog:\n{context['memory_catalog']}")
    if context.get("memories"):
        sections.append(f"Relevant memory records:\n{context['memories']}")
    mcp_names = list(mcp_clients.keys())
    if mcp_names:
        sections.append(f"Connected MCP servers: {', '.join(mcp_names)}")
    return "\n\n".join(sections)

这里体现了一个重要取舍：技能只放目录，正文按需加载。如果每轮都把十个技能的全文塞进 prompt，上下文会被无关知识撑满；只放一行名字和描述，模型知道"有这个能力"，需要时再调 load_skill(name)。记忆也是同理：memories 是"根据当前请求选出的相关记录"，不是整个记忆库。

注意 context 是在 prepare_context() 之后用 update_context() 重新算的。顺序是：先裁消息，再根据裁完的消息更新记忆索引和上下文，最后组装 prompt。如果反过来，装配出的 prompt 可能引用了刚刚被裁掉的内容。

PreToolUse：权限、hooks、后台任务共用一个入口

工具执行阶段是集成度最高的地方。每个 tool_use block 都要走过同一串检查，顺序是固定的：

tool_use block
→
PreToolUse hooks / permission
→
分发内置 / MCP / 后台
→
PostToolUse hooks
→
tool_result 回 messages
        for block in response.content:
            if block.type != "tool_use":
                continue
            # ... compact 请求在更早的分支单独处理
            blocked = trigger_hooks("PreToolUse", block)
            if blocked:
                results.append({"type": "tool_result",
                                "tool_use_id": block.id,
                                "content": str(blocked)})
                continue
            if should_run_background(block.name, block.input):
                bg_id = start_background_task(block, handlers)
                results.append({"type": "tool_result",
                                "tool_use_id": block.id,
                                "content": f"[Background task {bg_id} started]"})
                continue
            output = call_tool_handler(handlers.get(block.name), block.input, block.name)
            trigger_hooks("PostToolUse", block, output)
            results.append({"type": "tool_result",
                            "tool_use_id": block.id, "content": output})

PreToolUse 返回非空就表示"拦下"，直接生成一个错误 tool_result，不执行 handler。权限判断不再是散落在每个 handler 里的一行 if，而是挂在 hook 点上的一个回调。这样 permission、日志、审计可以共用同一个入口，加一个检查只需要注册一个 hook，不用改 26 个工具。

权限回调本身也很克制：

def permission_hook(block):
    if block.name == "bash":
        command = block.input.get("command", "")
        if not isinstance(command, str):
            return "Permission denied: shell command must be a string"
        for pattern in DENY_LIST:
            if pattern in command:
                return f"Permission denied: '{pattern}' is on the deny list"
        if threading.current_thread() is not threading.main_thread():
            return ("Permission denied: interactive shell approval is unavailable "
                    "during an asynchronous turn")
        # ... 主线程里询问用户 y/N
    if block.name in ("read_file", "write_file", "edit_file"):
        path = block.input.get("path", "")
        if not (WORKDIR / path).resolve().is_relative_to(WORKDIR):
            return "Permission denied: path is outside the workspace"
    # ... MCP 工具按 mcp_tool_policies 判断
    return None

两个设计值得记住。第一，文件工具越出 WORKDIR 直接拒绝，不询问——这不是"默认不信任模型"，而是"路径越界根本不该成为一个可选项"。第二，在异步轮次里（cron 唤醒、后台通知、团队事件），涉及需要用户交互确认的操作直接拒绝，因为后台线程不能和主 CLI 抢输入。权限系统必须知道"现在有没有人在终端前面"。

后台任务：先回占位结果，完成再注入

慢命令不应该卡住整个循环。s15 的规则非常窄：只有显式带 run_in_background=true 的 bash 才走后台。

def inject_background_notifications(messages: list):
    notes = collect_background_results()
    if notes:
        messages.append({"role": "user", "content": [
            {"type": "text", "text": note} for note in notes]})

# 主循环里，后台任务启动后立即返回占位结果：
if should_run_background(block.name, block.input):
    bg_id = start_background_task(block, handlers)
    results.append({"type": "tool_result",
                    "tool_use_id": block.id,
                    "content": f"[Background task {bg_id} started] "
                               "Result will arrive as a task_notification."})

顺序是：主循环先返回占位 tool_result，模型继续做下一件事；后台线程完成后把结果放进 background_results；下一轮开始前 inject_background_notifications() 把已完成的结果作为 user 消息注入。占位结果让模型知道"这件事已经启动了"，注入则让它在结果到达时看到真实输出。两件事分开，模型才不会误以为命令已经跑完。

05两张计划表：别把 todo 和任务图混为一谈

s15 同时保留了 s05 的 todo_write 和 s10 的 task graph。它们看起来都在"列任务"，但解决的问题完全不同：

维度todo_writeTask graph
存放位置内存中的当前会话清单.tasks/task_*.json 文件
生命周期本次会话跨会话、跨 Agent
更新方式整表替换稳定 ID，单条生命周期更新
依赖关系无blockedBy，完成后解锁下游
主要用户单个 Agent 的注意力Lead 与队友协作

还有一个命名陷阱：工具池里那个单独出现的 task 工具，是"一次性派发隔离子代理"，不是 Task System。读 s15 代码时如果不注意，很容易把它和 create_task 混起来。前者是 s06 的子代理，后者是 s10 的任务图。

任务图的构建仍然是两阶段：Lead 先为所有节点调用 create_task，拿到运行时生成的 ID，再用这些 ID 调 update_task(addBlockedBy=...)。为什么不让模型自己指定 ID？因为模型编的 ID 可能重复、可能互相引用成环，交给运行时生成才能保证唯一性和可校验性。只有 Lead 能改依赖，队友只能列举、认领、完成——任务图的结构在派发前就冻结了。

07常见误区

误区一：先组装 system prompt，再压缩也没关系

有关系。如果先组装 prompt 再压缩，你压缩的只是 messages，而 prompt 里可能已经包含了来自旧上下文的记忆摘要、技能目录或 MCP 状态。更严重的是，compact_history 可能裁掉刚刚注入的 cron 或后台通知，而 prompt 却还按"它们存在"来组装。正确顺序是先裁消息、再根据裁完的结果更新 context、最后组装。

误区二：工具越多，越能体现 Harness 强大

26 个工具意味着 26 份 schema 要进上下文，模型选择成本也随之上升。s15 的工具表是"这一章实际用到的机制"的并集，不是"越多越好"的清单。生产环境里更常见的做法是按子代理或按任务阶段裁剪工具集，而不是把所有能力一次性摊给同一个模型。

误区三：把所有状态都塞进 messages 就"统一"了

messages 只适合放对话和工具结果。任务图、收件箱、cron 队列、后台任务句柄、记忆库都必须落磁盘：它们要跨会话、跨进程、跨重启存活，而且会被多个 Agent 共享。把共享状态塞进某一段对话，等于用最脆弱的地方存最重要的东西。

08深入区

🔬 深入：集成顺序为什么重要？三个顺序错误的具体后果

错误一：先组装 prompt，后压缩消息

system prompt 里的 memories 是根据压缩前的消息选出来的。压缩之后，其中一部分对话已经变成摘要或归档标记，prompt 却仍在引用被删掉的细节。更隐蔽的问题是工具定义：assemble_tool_pool() 也会读取已连接的 MCP server，如果顺序错了，模型可能拿着上一轮的 MCP 工具列表去调用一个这一轮已经断开的 server。

错误二：cron / 后台通知在压缩之后注入

注入发生在 prepare_context() 之后，意味着新注入的 prompt 不经过预算管线。一条很长的定时任务 prompt 可能直接把上下文推过限制，而下一轮 prepare_context() 才来补救——中间那次模型调用可能已经因为 prompt too long 失败。s15 把注入放在循环最前面，就是为了让所有新内容都经过同一套压缩。

错误三：PreToolUse 放在 handler 内部

如果权限检查写在每个 handler 里，你必须为每个工具重复实现一遍，而且很容易漏。更糟的是，MCP 工具是运行时发现的，新增一个 server 就要补一份权限代码，否则默认全放行。把检查提到分发层，所有工具（内置、MCP、未来的新来源）自动共享同一道闸门。

再深一层：hook 和 permission 是同一件事吗？

不是。permission 是 hook 的一个具体实现：register_hook("PreToolUse", permission_hook) 让权限检查挂到通用扩展点上。hook 是机制，permission 是策略。同一套 hook 还可以挂日志、审计、指标，它们不需要知道权限逻辑。反过来，把 permission 硬编码进 hook 分发器，就会失去"用配置替换策略"的灵活性。

🔬 深入：组件失败了怎么办？隔离、降级与恢复

集成系统里，任何一个组件失败都不应该让整个会话消失。s15 在不同层用了不同的失败策略：

  • 工具层：call_tool_handler 捕获 handler 异常，把 Error: TypeError: ... 作为 tool_result 返回。模型下一轮可以修正参数或换工具。
  • hook 层：权限 hook 抛异常会让这一轮出错，所以 hook 内部要尽量只做判断、不做可能失败的重 IO；PostToolUse 的后处理失败不应影响已经拿到的工具输出。
  • 模型调用层：with_retry 处理 429/529，max_tokens 升级处理截断，reactive_compact 处理 prompt too long。重试有上限，超过就终止本轮，而不是无限重试烧钱。
  • 后台任务层：worker 内部捕获异常，状态记为 failed，结果仍然通过通知回到主循环——失败也是一条要告诉模型的信息。
  • 队友层：线程崩溃走 finally 释放 assignment，并向 Lead 发 error 事件。

模型调用层的恢复逻辑值得单独看一眼，因为它展示了"哪些错误该重试、哪些该升级、哪些该放弃"：

def with_retry(fn, state: RecoveryState):
    for attempt in range(MAX_RETRIES):
        try:
            result = fn()
            state.consecutive_529 = 0
            return result
        except Exception as e:
            name = type(e).__name__.lower()
            msg = str(e).lower()
            if "ratelimit" in name or "429" in msg:
                # ... 打印退避日志后重试
                time.sleep(retry_delay(attempt))
                continue
            if "overloaded" in name or "529" in msg:
                state.consecutive_529 += 1
                if (state.consecutive_529 >= MAX_CONSECUTIVE_529
                        and FALLBACK_MODEL):
                    state.current_model = FALLBACK_MODEL
                # ... 打印切换与退避日志后重试
                time.sleep(retry_delay(attempt))
                continue
            raise
    raise RuntimeError(f"Max retries ({MAX_RETRIES}) exceeded")

429 和 529 都是"稍后会好"的错误，所以退避重试；529 连续出现说明主模型可能过载，于是切 fallback model；其他异常直接抛出，交给更外层决定是记录还是终止。MAX_RETRIES 是硬上限，避免一个持续故障把会话拖进无限重试。重试不是"让错误消失"，而是"给瞬时故障一个恢复窗口"。

这些处理有一个共同原则：失败要变成事件，不要变成静默。静默失败最危险，因为模型会以为操作成功了，继续基于错误的前提往下做。把失败写回 messages[]，模型才有机会纠正；把失败写进日志和事件，人才能事后排查。

恢复状态放在哪里？

RecoveryState 是每轮循环的局部对象，记录 has_escalated、recovery_count、consecutive_529 这些"这一轮已经试过什么"的信息。它不持久化，因为重试状态只对当前调用链有意义。反过来，cron 的 durable 任务、任务图、记忆、队友收件箱都必须落盘，因为它们要在进程重启后继续存在。判断标准是：丢了它，重启后会不会做错事。

🔬 深入：从 17 个独立 demo 收敛成可维护 harness

把 17 个 code.py 合成一个 3300 行的文件，看起来像退步。但它能成立，靠的是四个结构性决定：

  1. 工具定义和 handler 显式成对。BUILTIN_TOOLS 和 BUILTIN_HANDLERS 是两张平铺的表，新增能力时两处都要改，但一眼能看出有没有漏。
  2. 一个分发入口。不管工具有多少来源，执行都走 call_tool_handler，前面统一过 PreToolUse，后面统一过 PostToolUse。
  3. 装配点固定。每轮循环只在这些位置调用机制：注入、压缩、组装 prompt、调模型、分发工具、回填结果。新机制只能挂到已有装配点上，不能随便插进循环中间。
  4. 共享状态外置。任务、邮箱、cron、记忆、transcript 全部在磁盘上有明确目录，进程内只保留句柄和缓存。

如果要把它拆成可维护的模块，自然的切法是按装配点切：context/（压缩）、prompt/（组装）、tools/（定义与分发）、runtime/（后台与 cron）、team/（团队与 worktree）、mcp/。切分的关键不是"代码行数差不多"，而是"每个模块只在一个装配点上被调用，输入输出是 messages 或 context"。

09自测：集成运行时的判断题

为什么 prepare_context 必须在 assemble_system_prompt 之前执行？

因为 system prompt 里的记忆、技能目录、MCP 状态和队友列表都来自 context，而 context 是根据当前 messages 算出来的。先压缩再更新 context，prompt 才和真正发给模型的消息一致。反过来会出现 prompt 引用已删除内容、或工具列表与消息状态脱节的问题。本质上是"先确定输入，再生成元信息"的依赖顺序。

后台 bash 命令启动后，为什么要先返回一个占位 tool_result，而不是等命令跑完再返回？

后台任务的意义就是不让主循环空等。先返回占位结果，模型知道"任务已启动"，可以继续做别的事；等后台线程完成，真实输出通过 task_notification 在下一轮注入。如果等命令跑完再返回，主循环就被阻塞了，后台和前台没有区别，还多了一层线程开销。注意占位结果必须明确写"结果稍后到达"，否则模型会误以为命令已经完成。

为什么异步轮次（cron 唤醒、团队事件）里，需要用户确认的操作要直接拒绝？

因为异步轮次跑在后台线程里，没有"当前终端输入"的所有权。如果它去调用交互式确认，就会和主 CLI 抢 stdin，导致输入串线、两个问题混在一起，甚至死锁。s15 的 permission hook 明确检查 threading.current_thread() is not threading.main_thread()，异步轮次直接返回拒绝。这不是降低安全性，而是承认"没有人坐在终端前时，不能假装能问人"。

todo_write 和 Task System 都能"列任务"，为什么集成运行时两个都要保留？

因为它们服务不同的主体。todo 是给单个 Agent 的注意力工具：轻量、会话内、整表替换，帮助模型不跑偏；Task System 是给多 Agent 协作的共享状态：落盘、带依赖、可认领、可恢复。用一个替代另一个会出问题：只保留 todo，团队没法共享任务；只保留任务图，单个 Agent 的日常规划会变得过重。判断标准是"这个计划需不需要跨会话/跨 Agent 存活"。

既然 s15 已经有 26 个工具，为什么说它"没有引入新机制"？

因为 26 个工具里没有一个是新能力：bash、文件工具来自 s02/s03，todo 来自 s05，task 来自 s06/s10，cron 来自 s12，团队来自 s13，MCP 来自 s14。s15 新增的是"装配"——每轮什么时候注入、什么时候压缩、什么时候组装 prompt、什么时候过权限、什么时候分发后台。工具数量是结果，装配顺序才是这一讲的内容。

这一讲带走

集成运行时的核心不是把代码堆在一起，而是给每个机制一个固定的装配点，并保证顺序正确：先注入新事件，再压缩上下文，再根据压缩结果组装 system prompt，然后调模型；工具执行统一走 PreToolUse → 分发 → PostToolUse → tool_result。循环仍然是 s01 那个循环，复杂的是它周围那些"什么时候做什么"的约束。
