02术语表

Agent 领域最大的沟通成本，是同一个词在不同团队指不同东西。下面这组定义是本课的统一口径，建议你在自己的项目文档里也固定下来：

术语本课定义容易混淆的说法
Agent模型 + harness 构成的完整系统，能在环境中自主决策与行动"一个 prompt""一个工作流"
模型 / LLM通过训练获得判断能力的神经网络，Agent 的"驾驶员"把它当成"文本生成器"
Harness围绕模型运行的全部工程代码：工具、权限、上下文、状态、编排"脚手架"（脚手架暗示临时）
Agent 循环调用模型 → 检查 tool_use → 执行工具 → 回填结果 → 重复"Agent 引擎"
工具（tool）模型可请求的一个原子动作，有 JSON schema 和 handler"技能"（技能是指令与知识）
技能（skill）按需加载的领域知识/操作指南，注入上下文而非执行动作"工具"
tool_use block模型响应中表示"我要调用工具"的结构化内容块"函数调用"（在不同 API 里同名不同物）
tool_resultharness 把工具输出包装成的消息块，必须带 tool_use_id"工具返回值"
上下文（context）本次模型调用实际看到的全部 token：system + 历史 + 工具结果"记忆"
压缩（compact）在不破坏 tool_use/tool_result 配对的前提下缩短历史"截断"（粗暴丢弃会破坏协议）
记忆（memory）跨会话持久化、可被召回的事实与偏好，存于磁盘"上下文"
子代理（subagent）用全新 messages[] 执行子任务、只回传最终文本的独立循环"小模型"
队友（teammate）持久存在、有独立循环与收件箱、通过消息总线协作的 Agent"子代理"（子代理是一次性的）
任务（task）落盘的状态机记录，含依赖、拥有者、状态，可被认领与完成"todo"（todo 是注意力工具）
工作树（worktree）git worktree 创建的独立工作目录，隔离并行编辑"工作区"（IDE 概念）
钩子（hook）在循环固定事件点（PreToolUse 等）注册的回调"中间件"
权限（permission）执行前的决策：allow / deny / ask，以及拒绝后的回填"鉴权"（那是身份认证）
MCPModel Context Protocol，外部工具服务器的发现与调用协议"插件系统"
工作流（workflow）由可信脚本固定编排多次 agent 调用，可恢复"Agent"（工作流不含判断权）
目标（goal）会话级的完成条件，由独立判断器评审是否达成"prompt 里写一句'直到完成'"
附录像汽车仪表盘和维修手册

正文教你开车，附录帮你在车出问题时看懂仪表、翻到对应章节。你不需要背下整张术语表，但要知道"仪表亮这个灯，该查哪一章"。

类比到哪为止：修车可以交给 4S 店，harness 出问题只能你自己翻日志 —— 因为你造的车没有别人见过。

03故障排查手册

下面每一条都是真实会遇到的症状。按"症状 → 最可能的机制层 → 先做什么"的顺序排查，不要一上来就改 prompt：

症状先怀疑排查动作
模型一直调工具，停不下来循环终止条件 / 工具结果没回填打印每轮 tool_calls 与 messages 长度；检查 tool_result 是否真的 append 了
模型反复做同一个动作工具结果没有提供新信息 / 系统提示缺少约束看工具返回是否与上次相同；给工具加"已存在/已完成"状态，或加计划机制
API 返回 400 tool_use 配对错误压缩或手工编辑破坏了配对检查每个 tool_result.tool_use_id 是否都能找到对应 tool_use.id；压缩必须成对处理
长会话突然变傻上下文压缩丢信息 / 注意力稀释看是否触发了 compact；检查摘要是否保留了目标与关键约束；考虑子代理隔离
Agent 读不到刚写的文件工作目录 / 沙箱路径打印 cwd 与绝对路径；检查是否在不同 worktree 里操作
任务"完成了"但产物不对缺少验收步骤 / 停止条件太弱加可检查的完成条件（测试通过、文件存在、命令退出码为 0）；启用目标循环机制
多 Agent 互相覆盖文件共享工作目录，没有隔离任务绑定 worktree；认领必须原子；写入前检查任务所有权
后台任务结果丢了通知队列未在下轮注入检查 collect_background_results 是否在循环开头被调用；确认注入发生在模型调用之前
定时任务没触发cron 表达式 / 时区 / 队列未消费用固定时间点验证匹配函数；确认调度线程存活、队列在下轮被 ack
权限被拒后模型卡住拒绝理由没有回填拒绝也必须返回一条说明原因的 tool_result，让模型换路径
同一个工具调用被重复执行重试 / 恢复机制不幂等给副作用操作加幂等键（ch17 的稳定调用键思路）

排查时有一个通用原则：先把"模型看到的上下文"完整打印出来。90% 的"模型犯蠢"，打开上下文一看都是 harness 给错了信息 —— 结果没回填、顺序错了、压缩压掉了关键约束。

🔬 深入：如何评估一个 Agent 框架的 harness 成熟度？

看 README 里的功能列表最不可靠。下面这份清单按"越靠后越难伪装"排序，用来快速判断一个框架是不是真的工程化：

  1. 循环是否干净？核心循环能否用不到 100 行讲清，机制是否外挂而不是塞进循环。
  2. 工具是否有统一 schema 与错误约定？错误是否可被模型理解并自我修正。
  3. 权限是否在执行前？而不是靠事后审计或 prompt 请求。
  4. 状态是否落盘且可恢复？杀进程再启动能否继续。
  5. 上下文管理是否有不变量检查？比如 tool_use/tool_result 配对。
  6. 是否可观测？能否回答"这一轮模型看到了什么、花了多少 token、工具耗时多少"。
  7. 是否可替换模型？换 provider 不需要改业务逻辑。
  8. 是否有轨迹评估能力？能否回放历史任务并量化成功率。

前四项是及格线，后四项决定它能不能上生产。特别提示：一个框架如果宣称"零代码搭建 Agent"，通常意味着它把判断写进了配置与流程，正好踩中第 1 讲的反模式。

再深一层：如果想自己写一个，目录结构长什么样？

先写 core/loop.py 与 core/tools.py，跑通一个真实任务，再按痛点逐个加目录 —— 不要反过来先搭架子。这是整门课反复强调的顺序：机制由故障驱动，而不是由架构图驱动。

05学完之后的三条路

① 造产品

把课程机制落地成自己的编码/研究/运维助手。读官方 API 文档与 MCP 规范，重点补：沙箱、审计、评估。参考 Kode CLI 与 Agent SDK。

② 做常驻助手

从"用完即弃"走向"一直在线"：心跳、cron、IM 多通道、长期记忆、人格设定。仓库的姊妹项目 claw0 专门拆这套机制。

③ 参与训练

harness 产生的轨迹就是训练信号。往 RL / SFT 方向走，要补：任务环境构建、奖励设计、轨迹过滤、评估集。

推荐资源（按优先级）：本仓库各章 README.md 与 code.py 二刷 → Anthropic 官方文档（Messages API、tool use、context 管理）→ MCP 官方规范 → 姊妹项目 claw0（常驻 Agent）→ Kode CLI（真实产品实现）。

最有效的复利动作

给学过的每个机制写一段 200 字的"故障笔记"：什么症状、哪个机制、怎么修。三个月后你会拥有一本只属于自己的 harness 手册，比任何教程都值钱。

06常见误区

误区一：把附录当"看完就忘"的附表

这张故障表在你真正做项目时才会发挥价值。建议把它收藏成浏览器书签，或在项目里复制一份当 runbook。

误区二：以为"生产化 = 加更多机制"

生产化是让已有机制更可靠，不是再加 10 个机制。可观测、幂等、恢复、审计，这些是"深度"，不是"广度"。

误区三：忽略模型可替换性

把 provider 特有行为写进业务逻辑，换模型时会全线崩。第 1 讲说过：模型是变量，harness 是常量。

07自测

用户报告："Agent 昨天还好好的，今天一直重复读同一个文件。" 你的排查顺序是什么？

第一步查上下文而不是改 prompt：打印最近几轮的消息，确认 read 的 tool_result 是否真的回填、内容是否为空或被压缩掉了。第二步查工具层：文件路径是否变了（cwd / worktree）、读取是否有权限问题导致静默返回错误。第三步查状态：是否有记忆或 todo 注入了过期信息，让模型以为文件还没读。

对应机制：ch09 压缩（配对不变量）、ch12 后台（结果注入时机）、ch11 任务状态。多数"重复动作"的根因是"模型没拿到新信息"，不是模型笨。

"记忆"和"上下文"最容易混。用一句话说清区别，并各举一个只有它能解决的问题。

上下文是这一次模型调用能看到的东西（会消失、有 token 上限）；记忆是存在磁盘上、跨会话可召回的事实与偏好（持久、需要检索）。

只有记忆能解决：用户上周说过"这个项目用 pnpm 不用 npm"，本周新会话仍要遵守。只有上下文能解决：这一轮刚读到的报错日志，模型必须马上基于它推理。

同事说："我们给 Agent 加一个'如果连续失败 3 次就换方案'的 if-else，这样更稳。" 你会怎么回应？

先确认"连续失败"是否可被模型看到：如果每次失败的原因都已作为 tool_result 回填，模型本来就能自己换方案，硬编码判断反而剥夺了它的判断权；如果失败信息没回填，那才是真正要修的 bug。

如果确实需要兜底，正确做法是放在 harness 的"护栏"层：限制最大轮次、最大成本、重复动作检测、必要时升级给人（ch18 的出口设计），而不是写"第 3 次改走 B 方案"这种业务决策。判断归模型，护栏归 harness。

如果让你只用 3 个机制、100 行代码做一个能用的个人编码助手，你选哪三个？为什么？

推荐组合：循环 + 工具分发 + 权限（ch02–ch04）。理由：循环让它能连续行动；工具（读/写/改/glob/bash）决定它能对代码库做哪些动作；权限保证它不会在你睡着时把仓库删了。这三者构成"能用"的下限。

下一步按痛点加：如果它跑偏就加 todo（ch06）；如果上下文爆就加压缩（ch09）；如果任务跨天就加任务图（ch11）。不要一次上 17 个机制 —— 课程反复强调：机制由故障驱动。

全课结语

17 个机制，最终只服务一个目标：让模型的判断力在一个安全、可观测、可恢复的环境里充分发挥。你不需要造出第二个 Claude Code，你需要造出适合你自己领域的那一台。
