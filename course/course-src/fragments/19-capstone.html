01你手里已经有 17 块积木

先别急着写新代码。把这 17 个机制摊开看一遍，你会发现它们不是 17 个独立功能，而是围绕同一条循环长出来的六层能力。结课项目要做的，是按层装配，而不是按章复制。

层章节机制一句话职责
循环s01–s02Agent Loop / Tool Use让模型能连续行动，工具注册进分发表
边界s03–s04Permission / Hooks什么能跑、什么要问；扩展点不重写循环
复杂任务s05–s08TodoWrite / Subagent / Skill / Compact先规划、隔离上下文、按需加载知识、给上下文腾地方
长跑s09–s12Memory / Task System / Background / Cron跨会话记住、任务落盘、慢活后台、按时间触发
协作与开放s13–s15Agent Teams / MCP / Integrated Harness多队友分工、外部工具入池、机制共用一个循环
编排与收敛s16–s17Workflow / Goal Loop固定编排写成脚本、目标决定何时停

这张表的读法是“纵向可运行，横向可扩展”。每一层都能单独跑起来，也都能在下一层继续加东西；但如果你从六个层里各挑一个最难的先做，最后大概率得到一个能演示、不能调试的半成品。

像学厨艺从背菜谱到办一桌家宴

刀工、火候、调味、摆盘是分开练的，但办家宴不是把四项各表演一遍。你要先定菜单，再排上菜顺序，最后保证热菜上桌时还是热的。哪道菜失手，整桌的节奏都会乱。

类比到哪为止：家宴失手可以重做一道菜，harness 的权限边界和自动继续却不能“重来一次”——一次误删、一次虚报完成，代价可能不可逆。所以结课项目里，安全边界和验收标准的优先级高于功能数量。

02五个里程碑：每一层都要“能跑、能看、能验收”

里程碑的划分标准不是章节顺序，而是可独立演示的纵切面。完成 Mi 时，你应该能关掉后面的机制，只靠前 i 层跑一个真实任务。每个里程碑都按四件事验收：标准、现象、坑、对应章节。

→
M2计划 + 子代理 + 技能 + 压缩
→
M3记忆 + 任务图 + 后台 + 定时
→
M4团队 + MCP
→
M5工作流 + 目标循环

03M1：让循环真正转起来

M1 的目标不是“支持很多工具”，而是一个闭环：模型发 tool_use，harness 执行，把带 tool_use_id 的 tool_result 塞回 messages[]，再继续。外加两个边界：权限在工具执行前拦截，钩子在工具前后观察。

验收标准一个 while 循环；≥3 个工具；权限命中时返回可读的拒绝原因而不是崩溃；≥1 个钩子不修改循环代码
可观察现象同一会话连续多轮工具调用；被拒绝的命令以 tool_result 形式回填；钩子日志出现在执行前后
常见坑忘了 tool_use_id 导致 API 报错；权限只写在 prompt 里；钩子抛异常直接打断整个循环
对应章节s01–s04 · ch02–ch05

04M2：把“复杂任务”拆开

这一层第一次让上下文变成稀缺资源。计划把任务显式化，子代理把噪声隔离，技能把知识变成按需加载，压缩在上下文快满时腾地方。四者共同回答一个问题：任务变长时，怎么不失控。

验收标准todo 状态在一次会话内可更新；子代理拿到全新的 messages[]，只把最终文本返回主对话；技能先列目录再按需展开；压缩在阈值处触发且保留最近消息
可观察现象主对话里看不到子代理的中间探索；技能内容只在被调用时出现；长会话的 token 曲线出现“下降后再继续”
常见坑把子代理的全部过程拼回主对话；技能目录也全文注入；压缩把 tool_use 和 tool_result 拆散
对应章节s05–s08 · ch06–ch09

05M3：从“一次会话”到“一直在线”

M3 是很多项目真正的分水岭：状态开始离开进程，落到磁盘和消息队列上。记忆跨会话、任务图落盘、后台命令异步完成、cron 按时间触发。从这里开始，你的 harness 不再是一次性工具。

验收标准重启后仍能读回用户偏好或项目约定；任务图支持 blockedBy 与原子 claim；后台命令完成时通知进入会话；定时任务按表达式触发
可观察现象关掉终端再打开，agent 还记得上次的约定；两个并发请求只有一个能领到同一任务；后台任务完成消息自动出现；cron 在预期时间点执行
常见坑状态文件写一半损坏且无恢复；后台输出没人收；cron 重复触发或时区错位
对应章节s09–s12 · ch10–ch13

06M4：多一个队友，多一组工具

团队和 MCP 都指向“扩展”：前者扩展执行者，后者扩展工具池。它们共同的压力测试是命名与归属——任务归谁、工作目录归谁、外部工具在池子里叫什么。

验收标准≥2 个队友能并发 claim 任务且不重复；每个任务有独立工作树或工作目录；MCP server 的外部工具与内置工具进入同一 schema 池
可观察现象两个队友同时开工而任务不会被领两次；外部工具与内置工具在模型眼里长得一样；断开 MCP 时返回错误而不是静默消失
常见坑claim 不是原子操作；工作树互相踩文件；MCP 工具名与内置名冲突
对应章节s13–s15 · ch14–ch16

07M5：编排与收尾，让系统自己说完“完成”

最后一层不增加新能力，只改变两件事：谁来编排（脚本），以及谁来决定停（独立判断器）。M5 做对了，你的 harness 才从“能干活”变成“能交付”。

验收标准至少一个保存好的 workflow，支持 journal 续跑；resume 时未改调用命中缓存；/goal 条件可检查；有 max_turns、block_cap、impossible 三类出口
可观察现象续跑显示 agents=0 tokens=0；goal 未满足时自动进入下一轮；达到上限时控制权交还用户且目标仍在
常见坑调用 key 依赖并发顺序；判断器没看到证据也点头；自动继续没有出口

09三个项目选题

选题的原则是“真实、可验收、能在 30 天内做出演示”。下面三个方向分别偏个人生产力、信息处理和安全敏感场景，选一个你最想每天用的。

个人编码助手

面向单个仓库：读代码、改文件、跑测试、解释 diff。最贴近本课主线，M1–M5 都能自然用上。

自动化研究助手

给定问题，检索多个来源、做结构化笔记、生成带引用的报告。重点在子代理、技能与 workflow。

运维值班助手

接收告警、查日志、按 runbook 处置、必要时升级给人。重点在权限边界、后台任务与目标判断。

11评分标准：功能只占 40 分

维度分值看什么不合格信号
功能完整40里程碑是否真的能跑通；边界情况是否处理只有 happy path；换个输入就崩
健壮性25权限、失败恢复、并发、超时、预算无重试、无上限、无拒绝理由
可观测性20事件流、日志、任务状态、可复现的 demo出问题只能靠猜；没有 selftest
代码质量15模块边界、命名、测试、README单文件 3000 行；没有一行测试

注意这个配比传递的信号：一个“功能齐全但一碰就崩”的项目，最多拿 40 多分；而一个“只做到 M3，但权限、恢复、日志都扎实”的项目，反而可能拿到 70 分以上。这不是降低要求，而是把要求放到了 harness 工程真正难的地方。

验收不要靠肉眼。给自己写一个 selftest.py，把每个里程碑的“可观察现象”变成断言；再用一个脚本把它们串起来。下面是最小版本：

#!/usr/bin/env bash
set -euo pipefail

python -m pytest -q                       # 单元测试
python harness.py selftest --milestone M1 # 循环、工具、权限、钩子
python harness.py selftest --milestone M2 # 计划、子代理、技能、压缩
python harness.py selftest --milestone M3 # 记忆、任务图、后台、定时

# M5：真实 goal 验收，刻意把出口调紧
MAX_TURNS=6 CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=2 \
  python harness.py "/goal python -m pytest 退出码为 0"

# 续跑必须命中缓存，否则说明调用 key 不稳定
python harness.py workflow resume | grep -q "agents=0 tokens=0"

这个脚本本身就是项目的一部分。它把“我觉得做完了”变成“CI 认为做完了”，也是评分里“可观测性”那 20 分最直接的证据。

🔬 深入：为什么按里程碑，而不是按章节组织项目

17 个章节是横向切片：每一讲只隔离一个机制，方便理解。但工程交付需要纵向切片：每一层都能独立运行、独立验收。按章节拼装，你会得到 17 个“半成品接口”；按里程碑装配，你得到 5 个“能演示的系统”。前者适合学习，后者适合交付。

里程碑的边界也不是随便画的。M1 结束在“循环可信”，M2 结束在“上下文可控”，M3 结束在“状态可持久”，M4 结束在“执行者可扩展”，M5 结束在“结束条件可信”。每一条都是可以在演示里被观察到的性质，而不是代码量。

再深一层：从课程 demo 到真实产品，还差什么

课程代码是“机制示例”，不是产品。真实产品至少还要补五块：持久化（会话、事件、任务都要能恢复）、并发与隔离（多用户、多进程、工作树）、安全（密钥管理、路径沙箱、审计日志）、成本（预算、限流、缓存）、以及可观测性（指标、追踪、回放）。这五块没有一块能靠“再加一个工具”解决，它们都属于 harness 工程。

所以结课不是终点，而是把你的关注点从“机制怎么实现”切换到“系统怎么被信任”。下一站的路线已经很清楚了：读官方文档补齐 API 细节，读 sister repo claw0 看 always-on 的 harness 怎么加 heartbeat 与 IM 通道，再去 Kode 这样的真实产品里看这些机制怎么在工程约束下取舍。

13动手：今天就开始的三个任务

  1. 做一个 M1 最小版：只保留 loop + 3 个工具 + 一条权限规则 + 一个 PreToolUse 钩子。跑一个真实小任务（例如“找出仓库里所有 TODO 并汇总”），录下对话。
  2. 写第一个 selftest：把“拒绝的命令不崩溃”“连续 3 轮工具调用”“tool_result 带 tool_use_id”写成三个断言。先让它们失败，再让它们通过——这比读十遍代码有用。
  3. 为你的选题写验收清单：从第 09 节的评分维度里各挑一条，写成三行“如果我做到了，应该看到什么现象”。如果写不出“现象”，说明这个维度你还没想清楚。

14常见误区

  • 很多人以为结课项目是把 17 章代码拼接起来。其实每章代码是独立示例，接口并不统一；正确做法是重新设计一套模块边界，让每个机制只暴露最少的东西。拼接只会得到一座无法维护的代码博物馆。
  • 很多人以为功能越多分越高。功能只占 40 分，健壮性、可观测性、代码质量合计 60 分。一个能自动开 20 个工具但没有任何失败恢复的系统，评分会低于一个只有 5 个工具但每步可观测的系统。
  • 很多人以为有了 Goal Loop 就不需要测试。判断器只读对话，不跑命令；它能判断“证据是否出现”，不能替代证据本身。真正的验证仍然由测试和工具完成。

15项目自检问题

关掉终端再打开，你的 agent 还记得什么？哪些是“记忆”，哪些只是“日志”？

记忆是下次会被主动读回、影响决策的信息（用户偏好、项目约定、任务状态）；日志只是留档，不会被自动加载。答不上来，说明你的持久化边界还没设计；答得上来但两者混在一起，说明记忆会被日志噪声淹没。

如果模型连续 5 轮都说“已经完成”，你的系统凭什么不相信它？

凭一个独立的判断器和可检查的完成条件。判断器没有工具，只看对话里有没有命令、退出码、测试结果这些证据；连续宣称但没有证据时，它应该判“未完成”并给出缺少什么。如果你的系统只能相信模型的自述，那它还没有 M5。

两个队友同时 claim 同一个任务，会发生什么？你怎么证明不会重复执行？

如果 claim 不是原子操作，两个队友会同时以为自己领到了任务，然后各自改同一批文件。证明方式不是“看代码觉得对”，而是写一个并发测试：同时发起 N 个 claim，断言只有一个成功、任务 owner 唯一。这也是 M3/M4 验收里“原子 claim”的真正含义。

你的 workflow resume 命中缓存时，如何证明没有重复副作用？

先区分“重复调用”和“重复副作用”：journal 只保证同一个调用不重复执行，副作用是否重复取决于工具本身是否幂等。证明方法是给有副作用的工具加幂等键（例如 request id），并在 resume 测试里断言外部状态只变化一次。如果工具做不到幂等，就把副作用移出 workflow。

如果只能保留一个机制到线上，你保留哪个？为什么？

没有标准答案，但好的回答会给理由。常见选择是权限：没有权限边界，其他机制越强，破坏半径越大。也有人选可观测性：没有日志和事件，出了问题连“哪个机制坏了”都不知道。关键是你能说清取舍，而不是列举功能。
