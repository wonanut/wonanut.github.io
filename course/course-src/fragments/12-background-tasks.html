01五条慢命令，把一次对话拖成半小时

读文件、git status、ls 这些命令几乎瞬间返回，同步执行看不出问题。但安装依赖、跑完整测试、构建项目动辄几分钟。同步执行意味着：命令不返回，harness 就不会把 tool_result 写回 messages[]，也就不会发起下一次模型调用。整个 Agent 循环被一条命令按在原地。

更浪费的是，很多后续工作根本不依赖这条命令。Agent 启动了 npm install，本来可以顺手读一下 package.json、检查文档、整理待办，但这些都得等安装结束。你花在等上的时间，不是模型在思考，而是 harness 在阻塞。

还有一种更隐蔽的代价：如果这条命令卡住两分钟以上，用户会以为程序死了。一个“能干活但看起来没反应”的 Agent，体验上比一个“明确告诉你我在后台跑”的 Agent 差很多。

注意

后台化不是把所有命令都丢后台。只有“明确独立、结果可以稍后处理”的命令才适合；如果你下一步就要用它的输出，丢后台只会让你多等一轮。s11 把决定权交给模型：调用时显式传 run_in_background。

哪类命令值得后台

判断一条命令要不要后台，看两个维度就够了：它慢不慢、它的结果会不会被下一步立刻用到。

类型例子建议
快、结果被依赖read_file、git status同步，结果立刻进下一轮推理
慢、结果被依赖需要先跑完才能改代码的构建同步但接受等待，或拆成“后台跑 + 回头读日志”
慢、结果独立npm install、完整测试、部署后台，先返回号牌，完成后再处理

表格里最容易被忽略的是第二行：并不是所有慢操作都适合后台。如果你下一步必须读它的结果，丢后台只是把“等待”换成了“多一轮”，还可能让模型在结果没到时就做判断。后台化的前提是“这段时间里有别的事可做”。

02直觉：拿个号牌，先去干别的

生活里的做法是这样的：把衣服塞进洗衣机、按下启动，拿一个号牌就走；期间你去切菜、收拾桌子；估摸时间差不多了，再回洗衣房看洗好没有。关键有两点：洗衣机是另一条“执行线”，而你是主循环；你并不站在洗衣机前面等，只是隔一段时间回来收一次。

像洗衣房取号

把脏衣服（命令）交给洗衣机（后台线程），拿到一个号牌（bg_0001）；主线程继续做别的事，下一轮回到洗衣房时凭号牌取结果。号牌不是衣服，它只代表“有一件活正在那边跑”。

类比到哪为止：洗衣机洗完不会主动给你发消息，你也收不到通知——只有你再次走进洗衣房（进入下一轮 Agent 循环）时，才会看到结果。如果人离开房子（进程退出），衣服不会自己送上门；本章的后台线程是 daemon，进程一退，未收集的结果就丢了。

tool_usebash + run_in_background
→
execute_tool判断走后台
→
start()登记 + 起线程
→
占位 tool_result带 bg_id 立即返回
→
下一轮顶部collect → 注入通知

这里有个容易被忽略的协议问题：模型发出一个 tool_use，按 API 规则必须收到恰好一个对应的 tool_result。后台命令还没跑完，结果还不存在，怎么办？s11 的答案是先回一个占位结果，告诉模型“任务已启动，稍后收集”。这个占位结果同时承担了三个职责：满足 API 配对、告知 bg_id、提醒模型结果会在后续轮次到达。

tool_result:
  [Background task bg_0001 started] The result will be collected on a later turn.

这一轮就结束了，模型可以继续发新的工具调用。等命令跑完，结果不会伪装成原来的 tool_result，而是作为一条独立通知，在后续某一轮开始时被塞进对话。这个“一次 tool_use 只对应一次 tool_result”的约束，是后面所有设计选择的源头。

循环状态停在这次 bash 调用上拿到占位结果后继续

03代码精读：谁来决定去后台

判断逻辑短得几乎不需要解释，但它的“显式”二字很值钱：

def should_run_background(tool_name: str, tool_input: dict) -> bool:
    return (
        tool_name == "bash"
        and tool_input.get("run_in_background") is True
    )

它不问命令里有没有 install、build、test 关键词，也不猜“这条命令大概会慢”。是否后台由工具调用明确指定。这个设计避免了两种坏情况：误判关键词把一条需要立即结果的命令丢到后台，以及漏判把一条三分钟的命令留在前台。判断标准从“harness 猜”变成“模型说”。

对应地，bash 的 schema 多了一个布尔参数。注意 run_bash() 的签名里虽然有 run_in_background，函数体却完全没用它——真正的分流发生在更外层的 execute_tool()。读源码时别被签名骗了：这个参数只是提供给模型的“意图声明”，不是执行函数的开关。

{
    "name": "bash", "description": "Run a shell command.",
    "input_schema": {"type": "object",
                     "properties": {
                         "command": {"type": "string"},
                         "run_in_background": {"type": "boolean"}},
                     "required": ["command"]},
}

工具描述里也提前打了预防针：system prompt 写着“Set run_in_background to true only for independent Bash commands”。前半句是给模型的策略，后半句限定只有 bash 能后台——因为其他工具（读文件、写文件）本来就没有“后台”的语义，硬要支持只会让结果和消息顺序更难推理。

这也是工具设计的一个通用原则：能力边界写在 schema 里，使用策略写在描述里，约束写在 system prompt 里。三层各管一段，模型才有机会做出正确判断；只把规则藏在代码里，模型永远学不会怎么用。

分流发生在 execute_tool() 里，它也是整个机制唯一改动主循环的地方：

def execute_tool(block) -> str:
    blocked = trigger_hooks("PreToolUse", block)
    if blocked is not None:
        return str(blocked)

    if should_run_background(block.name, block.input):
        try:
            task_id = start_background_task(block)
            output = (
                f"[Background task {task_id} started] "
                "The result will be collected on a later turn."
            )
        except Exception as error:
            output = f"Error: {error}"
    else:
        output = call_tool(block)

    trigger_hooks("PostToolUse", block, output)
    return output

看结构：权限检查仍然在最前面，同步与后台的分叉在中间，钩子仍然在最后。也就是说，后台化只替换了“怎么执行”这一步，没有绕过任何前置检查与后置通知——这一点对安全性至关重要。

04BackgroundManager：一张登记表 + 一条完成队列

BackgroundManager 的全部状态只有四样：tasks（按 bg_id 登记的任务）、results（结果文本）、_ready（已完成待收集的 ID 列表）、_lock（保护前三者的互斥锁）。start() 先登记再起线程，然后立刻返回号牌。

def start(self, block) -> str:
    if block.name != "bash":
        raise ValueError("Only Bash commands can run in the background")
    command = block.input.get("command")
    if not isinstance(command, str) or not command.strip():
        raise ValueError("Bash command cannot be empty")
    with self._lock:
        self._counter += 1
        task_id = f"bg_{self._counter:04d}"
        self.tasks[task_id] = {
            "tool_use_id": block.id, "command": command,
            "status": "running",
        }
    thread = threading.Thread(target=self._run, args=(task_id, command), daemon=True)
    try:
        thread.start()
    except Exception:
        with self._lock:
            self.tasks.pop(task_id, None)
        raise
    return task_id

三个细节值得停下来看。第一，登记发生在起线程之前，而且任务状态先写成 running——这样即使线程瞬间跑完、立刻往 _ready 里塞结果，收集方也一定能找到对应的任务记录。反过来的顺序（先跑再登记）会丢结果。第二，daemon=True：主进程退出时不会被后台线程拖住。第三，thread.start() 失败时会回滚登记，避免留下一个永远 running 的幽灵任务。

_run() 是线程体，干活、格式化、改状态、入队，全部在锁里完成最后三步：

def _run(self, task_id: str, command: str):
    try:
        output, exit_code = _run_bash_process(command)
        result = _format_bash_result(output, exit_code)
        status = "completed" if exit_code == 0 else "failed"
    except Exception as error:
        result = f"Error: {type(error).__name__}: {error}"
        status = "failed"

    with self._lock:
        task = self.tasks.get(task_id)
        if task is None:
            return
        task["status"] = status
        self.results[task_id] = result
        self._ready.append(task_id)

命令以非零状态退出、或者 worker 自己抛异常，都会被归入 failed。但“失败”不会让结果消失——失败的结果同样进入 _ready，因为对模型来说“安装失败了”也是必须知道的信息。让失败静默，比让失败变慢更糟。

锁到底锁住了什么

这套并发结构里只有一个写者（后台线程）和一个读者（主线程的 collect()），它们共享三个容器。锁保护的不是“任务执行”，而是“登记与完成这两次状态变更”：后台线程在锁里改 status、写 results、追加 _ready，主线程在锁里把 _ready 整体取走。如果没有锁，可能出现“主线程看到 _ready 里有 ID，但 results 还没来得及写”的中间态。

def collect(self) -> list[str]:
    with self._lock:
        ready = []
        for task_id in self._ready:
            task = self.tasks.pop(task_id, None)
            result = self.results.pop(task_id, "")
            if task is not None:
                ready.append((task_id, task, result))
        self._ready.clear()

    notifications = []
    for task_id, task, result in ready:
        # ... 格式化 <task_notification> 并打印 collected 日志
        notifications.append(...)
    return notifications

注意锁的边界：格式化通知、打印日志、拼字符串都在锁外做。锁里只做“从共享容器里搬数据”这一件快事，避免慢操作拖住后台线程。写并发代码时，把“必须原子”的部分压到最小，是最省事的正确性策略。

把一次后台任务的生命周期串起来，其实只有五步：

  1. execute_tool() 用 should_run_background() 判断是否走后台；
  2. start() 登记任务、启动 daemon 线程、立刻返回 bg_id；
  3. 主循环把占位结果作为本次工具调用的 tool_result 回给模型；
  4. 后台线程命令结束，更新状态、写入结果、把 ID 放进 _ready；
  5. 下一轮开头 collect() 取走结果，格式化成通知注入对话。

这五步任何一步的顺序错了，都会出现“结果丢失”或“消息结构不合法”。把生命周期画出来，是排查后台类问题最快的方法。

05收集与注入：通知怎么进对话

收集发生在每一轮循环的最开头。collect() 在锁里把 _ready 里的任务一次性取走、清空队列，再在锁外格式化成通知文本。格式是固定的 XML 风格标签，字段包括 task_id、status、command，以及被截断到 500 字符的 summary：

notifications.append(
    f"<task_notification>\n"
    f"  <task_id>{task_id}</task_id>\n"
    f"  <status>{task['status']}</status>\n"
    f"  <command>{task['command']}</command>\n"
    f"  <summary>{result[:500]}</summary>\n"
    f"</task_notification>"
)

为什么是标签而不是自然语言？因为标签给模型一个明确的“这是一条系统事件”信号，也让它能稳定地区分“通知”和“用户新指令”。为什么带 task_id 和 command？因为一个会话里可能同时有好几个后台任务，模型必须能对上是哪一条。为什么 summary 只留 500 字符？完整结果可能几万字符，通知只是提醒，真正的细节需要时可以用 read_file 去看落盘日志（如果你的 bash 命令把输出重定向到了文件）。

注入函数 inject_background_results() 处理的是“这条通知放在哪”：

def inject_background_results(messages: list) -> int:
    notifications = collect_background_results()
    if not notifications:
        return 0

    blocks = [{"type": "text", "text": item} for item in notifications]
    if messages and messages[-1].get("role") == "user":
        content = messages[-1].get("content", "")
        if isinstance(content, list):
            content.extend(blocks)
        else:
            messages[-1]["content"] = [
                {"type": "text", "text": str(content)},
                *blocks,
            ]
    else:
        # 教学代码里走不到：agent_loop 返回时最后一条总是 user
        messages.append({"role": "user", "content": blocks})
    return len(notifications)

为什么优先追加到最后一条 user 消息，而不是新起一条？因为 agent_loop 每轮结束时，messages[-1] 正好是装着 tool_result 的 user 消息。把通知并进去，等于“在同一个回合的输入里补一条系统事件”，不会打断“助手回复 → 用户输入”的交替结构。如果最后一条不是 user（代码注释说当前不可达，但为将来从后台主动唤醒留了分支），才新起一条 user 消息。

接上循环只需要一行：

def agent_loop(messages: list):
    while True:
        inject_background_results(messages)
        response = client.messages.create(
            model=MODEL, system=SYSTEM, messages=messages,
            tools=TOOLS, max_tokens=8000,
        )
        # ... 执行工具、追加 tool_result

注意它放在 messages.create() 之前：每次调用模型前先“收信”，这样模型这一轮看到的是最新完成状态。放到循环末尾也可以，但放在开头更直观——“先看有没有新消息，再决定做什么”。

关键结论

后台结果进入对话的身份是“用户消息里的一段文本”，不是 tool_result。理解这一点，就能解释为什么它没有 tool_use_id、为什么钩子看不到它、以及为什么模型要自己判断它是不是新指令。

模型拿到通知后可以做什么

一条后台通知对模型来说是“环境变化”，不是请求。它可以据此做三件事：

  • 如果任务是后续步骤的前置（例如依赖装完了），继续原来的计划；
  • 如果失败了，决定重试、换方案，或者向用户报告；
  • 如果结果无关紧要，简单确认一句，继续等待真正重要的输入。

所以通知内容里必须带状态和命令原文，否则模型无法判断“这条通知意味着什么”。一个只写“任务完成”的通知，信息量等于零。

06进程组与结果截断：后台也不能失控

后台线程最大的风险是“留下孤儿进程”，因此每个后台命令都必须在三种退出路径上被收掉。一条 bash -c 命令可能 fork 出一串子进程，主进程被杀掉，子进程还在跑。s11 在 POSIX 上用 start_new_session=True 让 shell 成为独立进程组的组长，结束的时候对整组发信号：先 SIGTERM，给 0.05 秒，再 SIGKILL；Windows 没有 killpg，就退回 terminate() / kill()。

def _stop_process_group(process: subprocess.Popen):
    if os.name == "nt":
        for stop in (process.terminate, process.kill):
            if process.poll() is not None:
                return
            try:
                stop()
            except OSError:
                return
            # ... 等 0.05 秒，没退出就继续下一个信号
        return

    for sig in (signal.SIGTERM, getattr(signal, "SIGKILL", signal.SIGTERM)):
        try:
            os.killpg(process.pid, sig)
        except (ProcessLookupError, OSError):
            return
        time.sleep(0.05)

清理挂在三个位置，各自覆盖一种退出路径：

挂载点触发时机清理对象
命令结束的 finally跑完、超时、抛异常这次命令的进程组
atexit解释器正常退出（含 q）所有还登记着的 shell 进程
SIGTERM 处理器系统或用户要求终止进程全部 shell 进程，然后退出

这三处合起来覆盖了“跑完了”“用户按了 Ctrl-C”“系统在杀进程”三种情况。但必须说清楚：这是生命周期清理，不是沙箱。一个自己 setsid 脱离进程组的子进程仍然可以活下来；要真正的隔离，得上容器或 cgroup。

结果截断有两层：命令输出在 _run_bash_process() 里被截到 50000 字符，通知里的 summary 再截到 500 字符。前者防止一次巨大的构建日志把内存和后续处理拖垮，后者防止通知本身把上下文撑爆。两层截断的位置不同，目的也不同：一层保护进程，一层保护对话。

小技巧

需要完整输出时，让命令自己把日志重定向到文件（pytest -q > .test.log 2>&1），通知里只报“成功/失败 + 日志路径”。模型在需要时用 read_file 去读，比让 500 字符的摘要承载全部信息可靠得多。

设计要点

后台任务的“120 秒超时”和同步 bash 一样，但语义变了：同步时超时意味着这一轮白等；后台时超时只意味着这个任务 failed，循环早已继续。超时不该杀死整个会话，只应终结这一条任务。

🔬 深入：后台任务真正难的是“时间”和“一致性”

为什么不能直接阻塞等待

最直觉的实现是 thread.join() 或 future.result()，等结果回来再继续。但那等于把同步执行挪到另一个线程，主循环照样停住——你付出了线程的复杂度，却没换来任何并发收益。所以 s11 选择了“占位结果 + 后续轮次收集”：主循环从不为后台任务等待，只在新一轮开始时顺手看看有没有完成项。这个选择的代价是结果至少晚一轮到达，收益是循环永远不被单条命令卡死。

竞态：通知晚到与结果丢失

后台线程可能在任意时刻完成，可能在 collect() 刚返回、还没调用模型的那几毫秒里完成——这一轮就收不到它，只能等下一轮。这是“至少晚一轮”的正常代价，不是 bug。反过来，如果模型这一轮直接结束了（不再发起工具调用），而结果在 agent_loop 返回之后才到，这条通知就永远没机会进入对话；进程退出时，daemon 线程和未收集的结果一起消失。教学代码接受这个损失，因为主体场景是“用户继续追问”。生产系统要做得更稳，需要把结果落盘、或者用事件唤醒一个空闲的 Agent 循环——那是 s12 调度器要处理的问题。

后台任务与权限、钩子的关系

这是最容易被误解的一点。execute_tool() 在主线程先跑 PreToolUse，所以危险命令的确认仍然发生在你按下回车的那一刻，不会被后台绕过；但 PostToolUse 是在占位结果生成后立刻触发的，它看到的输出是“任务已启动”，不是最终结果。也就是说，像 large_output_hook 这类依赖真实输出的钩子，对后台任务基本失效。这不是疏漏，而是“钩子绑定在工具调用生命周期上”的必然结果；如果要在后台结果返回时做检查，得在 collect() 里另设一个钩子点。

失败与超时怎么回报

三类失败都走同一条通知通道：命令非零退出（status=failed，结果里带 Error: command exited with status N 和输出）、线程抛异常（Error: 异常类型: 信息）、以及 120 秒超时（输出 Error: Timeout (120s)，退出码为 None，按失败处理）。模型拿到通知后可以决定重试、换命令、或者向用户报告。这里有个小不一致：_format_bash_result() 把 None 当成成功处理（只拼接输出），而状态判定把 None 当成失败——读源码时留意这个边界，它在超时场景下会让结果文本里没有额外的错误前缀，但状态仍是 failed。

为什么只有 bash 能后台

读文件、写文件、glob 这类工具很快，后台化收益接近于零，却要引入“结果晚一轮”的复杂度；更重要的是它们的结果经常被下一步直接使用，放后台反而拖慢任务。设计上前台工具和后台工具不是对称的，应该按“耗时”和“是否被依赖”两个维度决定，而不是为了让能力表好看。

为什么不用 asyncio，而用线程

因为这里真正慢的是子进程 I/O，不是网络协程：subprocess.Popen + communicate() 本来就适合丢进线程阻塞。改用 asyncio.create_subprocess_shell 当然也能做，但会强制整个 Agent 循环变成 async，工具调用、钩子、REPL 都要跟着改。对一个教学用的同步循环来说，线程是侵入性最小的方案——只加了一个 threading.Thread，其余代码一行没动。

后台任务的内存边界

每个后台任务在 tasks 和 results 里各留一份记录，直到被 collect() 取走。如果某个任务的结果一直没被收集（比如循环已退出），它就会一直占着内存；如果用户连续启动几十个后台任务，_ready 会越积越长。教学代码没有限制并发数和队列长度，生产系统至少应该加一个“最多 N 个后台任务”的闸门，并在收集后立即释放引用——s11 的 pop 已经做了释放，缺的是入口限流。

再深一层：为什么通知不复用原始 tool_use_id？

因为原始 tool_use 已经用占位 tool_result 回复过了。Anthropic API 要求每个 tool_use 恰好对应一个 tool_result，再补一个同 ID 的结果会破坏消息结构。所以后台结果只能以“普通文本事件”的身份进入对话——这也提醒你：如果某个后台结果必须被结构化消费，最好让命令把机器可读结果写到文件，再让模型用工具去读。

07动手实验

后台实验需要模型配合产生 run_in_background，没有 API Key 的话可以跳过前几步，直接读代码 + 在 REPL 里手动调用 BackgroundManager。

  1. 跑一条真后台命令：启动 python s11_background_tasks/code.py，输入 Run sleep 20 in the background, then list all Python files。观察终端先打印 [background] started bg_0001，模型立刻收到占位结果并继续 glob；20 秒后的某一轮，才会出现 [background] collected bg_0001: completed。
  2. 看通知长什么样：在 inject_background_results() 里加一行 print(notifications)，再跑一次。确认通知里有 task_id、status、command、summary 四个字段，并且 summary 被截到 500 字符。
  3. 制造失败：输入 Run "exit 3" in the background。观察任务状态是 failed，结果文本以 Error: command exited with status 3 开头——失败同样会被收集，不会静默消失。
  4. 验证“晚到”：把 sleep 改成 1 秒，输入一条命令后立刻结束对话（不再追问）。你会发现这条通知可能根本没机会出现：结果是在循环结束后才完成的，而 daemon 线程不会唤醒已经退出的循环。这正是“晚到”的边界。
  5. 纯读代码实验：把 should_run_background() 改成“命令里含 install 就后台”，再输入 Run npm install。你会发现模型这次根本不会传 run_in_background，但你的代码却把它丢进了后台——理解“显式触发”与“关键词猜测”的差别。
  6. 观察进程组：在 Linux/macOS 上启动一条后台命令 sleep 300，然后在另一个终端 ps -o pid,pgid,command 找到它，确认它的 PGID 与主进程不同；再按 Ctrl-C 退出 Agent，确认这个 sleep 没有残留。这个实验能让你直观看到“清理的是进程组，不是单个 PID”。

08常见误区

很多人以为后台任务等于“并行思考”。模型本身并没有并行：后台线程只是在跑 shell 命令，Agent 循环仍然是串行的，一轮一次模型调用。后台带来的是“I/O 与推理重叠”，不是“多个模型同时思考”——后者是子代理和多 Agent 团队要解决的问题。

很多人以为占位 tool_result 是偷懒。恰恰相反，它是 API 协议的硬约束：每个 tool_use 都必须被回复，否则消息结构不合法。占位结果把“立刻回复”和“稍后给结果”拆开，才换来了不阻塞的自由。

很多人以为后台命令跑完会主动叫醒 Agent。不会。s11 的收集只发生在“下一轮循环开始时”，没有事件驱动、没有唤醒机制。如果你的 Agent 正在等待用户输入，后台结果就只能躺在队列里。要让 Agent 自己醒来处理结果，需要定时调度或心跳机制——下一讲会给出其中一种。

记住这条边界：后台任务只改变“何时执行”，不改变“谁在执行”；并发收益有上限，控制并发数比堆线程更重要。

09自测

如果把后台结果也包装成带原始 tool_use_id 的 tool_result 追加进去，会发生什么？

消息结构会被破坏：同一个 tool_use 出现了两个 tool_result，或者第二个 tool_result 没有对应的 tool_use。API 会拒绝这样的 messages[]。正确做法是让占位结果完成“一 tool_use 一 tool_result”的配对，后台结果以独立文本事件（task_notification）的形式进入对话。

PostToolUse 钩子能看到后台命令的最终输出吗？

看不到。execute_tool() 在启动后台任务后，立刻用占位文本触发 PostToolUse；真正的输出要等线程结束、被 collect() 收集后才存在，而那时工具调用生命周期早已结束。所以依赖真实输出的钩子（如大输出告警）对后台任务无效。需要检查后台结果，就得在 collect() 处新增钩子点。

为什么 start() 要先把任务登记进 tasks，再启动线程？

为了消除“线程跑得太快”的竞态。线程一启动就可能执行完并进入 _run() 的锁区，如果那时 tasks 里还没有这条记录，_run() 会认为任务已被取消而直接返回，结果就丢了。先登记再起线程，保证结果入队时一定有对应的任务记录可更新。

为什么后台线程用 daemon=True？改成非 daemon 会怎样？

daemon 线程不会阻止主进程退出：用户按 q 关掉程序时，Python 不会为了等后台命令而挂住。如果改成非 daemon，主线程结束时解释器会等待所有非 daemon 线程，一条忘记结束的后台命令就能让进程永远退不掉。代价是 daemon 线程的未完成结果会随进程一起丢失——这正好对应“后台结果只在下一轮收集”的设计。

一条后台命令以退出码 1 结束。模型最终会看到什么？

会收到一条 status 为 failed 的 task_notification，summary 里是 Error: command exited with status 1 加命令输出（截断到 500 字符）。失败不是异常路径，它和成功走同一条完成队列；模型可以据此重试或向用户报告。唯一不会发生的是“静默成功”——那才是后台任务最危险的失败模式。

这一讲带走

后台任务的关键不是“开一个线程”，而是“先回占位结果、让循环继续、下一轮再收集”这条协议：显式触发、登记先于启动、完成队列加锁、通知独立于 tool_use_id、结果与进程组都有边界。它把“等待”从循环里移走，但没有把“顺序”搞乱。

判断一个后台实现是否可靠，看三件事：占位结果有没有及时回、完成结果有没有一定被收集、异常路径有没有留下进程。tool_use_id 只是表面，这三件事才是里子。
