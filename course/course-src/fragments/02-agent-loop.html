01从一个真实的麻烦说起

你打开对话框，对一个 coding 模型说：帮我看看这个目录里有哪些文件，然后把其中的 demo.py 跑一遍。模型很配合，回你一条命令：ls -la && python demo.py。然后，它停住了。

命令躺在对话里，没有人执行。你只好复制、粘到终端、回车，再把输出复制回来、贴进对话框。它看完输出，再给你下一条命令，你再跑一遍、再贴回去。任务越长，你贴得越频繁；贴错一次，它就会基于错误的现场继续推理。

每一轮，你都在扮演一个没有名字的角色：中间层。你做的事情高度重复，而且完全可以用代码描述——把模型给的命令交给 shell，把 shell 的输出还给模型，直到模型不再要命令为止。

这一讲就是把这三件事写成代码。整章没有新模型、没有新 API、没有复杂框架，只有一个 while True、一个工具、一份 messages[]。但它是 Claude Code 这类工具的心脏：后面十六讲做的一切，都是围绕这个循环往上加东西，循环本身的形状几乎不再改变。

你手动做的事代码里对应什么
把模型的命令复制到终端run_bash(block.input["command"])
把终端输出复制回对话框tool_result 追加进 messages[]
判断还要不要再问一轮if not tool_calls: return
先记住这个分工

模型负责决策：要不要动手、用哪个工具、参数填什么。harness 负责执行：真的去调，并且把世界的反馈原样带回来。两件事都由模型做，你会得到一堆无法执行的建议；两件事都由 harness 做，你就回到了写死流程的脚本。

02直觉：一个循环，两个角色

先别急着写代码，把流程画出来：用户提一个问题，模型回一轮内容；如果内容里夹着工具调用请求，harness 就替它执行，把结果作为新消息塞回对话；然后再问一次模型。如此往复。

User提问
→
LLM返回响应，可能含 tool_use
→
Harness执行工具
→
messages[]追加 tool_result
→
回到 LLM再问一轮

循环的终止条件只有一个：这一轮响应里没有 tool_use block。注意，不是“模型说完成了”，也不是你去猜它有没有说完。模型不再请求工具，循环就退出。

为什么一个条件就够？因为“继续”的唯一信号，就是“它还想操作外部世界”。一旦它只想说话——把结论、把问题、把道歉说给你听——这一轮对话就该结束了。这个判断简单到有点粗暴，但正是这种简单让它稳定：不依赖模型的措辞，不依赖 stop_reason 的语义演变，只数一数响应里有没有要干的活。

你可以把每轮循环理解成三笔账：输入是当前全部 messages（越长越贵），输出是模型这一轮的决策（可能含工具请求），记账是把决策和结果写回 messages。循环本身不聪明，它只是忠实地把账记下去。

像给厨师配一个传菜口

把模型想成一位坐在厨房里的厨师：他能看懂订单、能决定先炒哪道菜、嗅觉极灵，但厨房门是锁着的，他走不出去，也没法自己按开关。tool_use 是他从窗口递出来的订单——“取三个鸡蛋”“把火开大”。harness 是传菜口：接单、执行、把做好的菜和现场情况一起送回窗口。厨师看到结果，决定下一单；看到“盐没了”，就改做别的。

类比到哪为止：真实厨房不会把成品再当成新订单送回去；而循环会把 tool_result 追加进 messages[]，模型下一轮读到的，是包括自己刚才那条订单在内的完整上下文。它不是“收到一盘菜”，而是“想起自己点过这道菜，又看到菜已经放在桌上”。这一点，是 Agent 能连续推理的关键。

关键结论

整个 harness 的工作可以压缩成一句话：让模型每一轮都能看到“上一轮自己做了什么、世界变成了什么样”。循环、工具、权限、钩子，都是在为这句话服务。

03代码精读：把中间层写成循环

先从入口看。用户输入被包成第一条消息，然后 messages 被交给 agent_loop。注意这个 list 是在函数外面创建的，传进去会被原地修改——这也是为什么 agent_loop(history) 返回之后，history 里已经多了好几轮对话。

messages = [{"role": "user", "content": query}]

response = client.messages.create(
    model=MODEL, system=SYSTEM, messages=messages,
    tools=TOOLS, max_tokens=8000,
)

tools=TOOLS 这一步很关键：它不只是告诉模型“有哪些工具”，还等于声明“你可以调用它们”。消息历史、工具清单、系统提示，每次请求都原样发过去——因为 Anthropic 的 Messages API 是无状态的，服务端不替你记任何东西。所谓“对话”，在协议层面就是“每次都把全部历史重发一遍”。

接下来是循环的前半段，也是整个机制里最容易写错的地方：

def agent_loop(messages: list):
    while True:
        response = client.messages.create(
            model=MODEL, system=SYSTEM, messages=messages,
            tools=TOOLS, max_tokens=8000,
        )
        messages.append({"role": "assistant", "content": response.content})

        tool_calls = [
            block for block in response.content if block.type == "tool_use"
        ]
        if not tool_calls:
            return

第一行 messages.append，把 response.content 整个追加进去，而不是只追加其中那段文字。这个细节是后面一切能成立的前提：模型下一轮必须“看到自己刚才发过 tool_use”，否则它不知道自己点过单，轻则重复调用，重则让 tool_result 变成没有归属的孤儿。

第二行 tool_calls 用列表推导筛出所有 tool_use block。为什么不直接判断 response.stop_reason？因为 stop_reason 回答的是“模型为什么停”，而这里真正要问的是“有没有要执行的活”。一次响应可能同时包含文字和多个工具请求，也可能因为 max_tokens 被截断——直接数 block 更贴近你要做的决策，也更不依赖 API 版本的措辞。

然后是后半段：执行、收集、回填。

        results = []
        for block in tool_calls:
            # ...
            output = run_bash(block.input["command"])
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": output,
            })

        messages.append({"role": "user", "content": results})

这里有三件事值得逐个盯住：

  • block.input["command"]：input 是模型按工具 schema 填好的参数字典。schema 里只有 command 一个必填字段，所以这里直接取。真实 harness 里要防着模型给错键、给错类型。
  • "tool_use_id": block.id：借条编号。模型一次可能开好几张借条，harness 还回来时必须一张对一张。少了它，API 无法把结果配对给调用，请求会直接失败。
  • messages.append({"role": "user", ...})：工具结果装在 user 消息里，不是 assistant 消息里。原因见下面的深入区。

还有一点容易忽略：results 是先收集、最后一次性 append 的，而不是每执行一个就 append 一条。因为一次 assistant 响应可能带多个 tool_use，协议要求这些调用的结果跟在同一条 user 消息里、按 id 一一对应。把一批结果打包送回，形状最稳。

顺序能不能换？

不能，而且这里有一个很隐蔽的坑：追加 assistant 消息必须发生在执行工具之前。如果你先跑完工具、再回头 append assistant，中间那个函数一旦抛异常（或者你手滑 return 早了），历史里就会出现一个没有请求方、只有结果的 tool_result，整段对话从此不自洽。

同理，判断“要不要退出”必须发生在 append 之后。因为即使这一轮没有工具调用，模型最后那段文字也需要留在历史里——用户下一句追问时，模型得记得自己刚说过什么。先判断再 append，等于每轮丢一句模型的话。

把这两条合起来，正确的顺序只有一种：追加 assistant → 判断有没有工具 → 执行 → 收结果 → 追加结果。这正是代码从上到下的行序。写循环时，让代码顺序和协议顺序重合，bug 会少一半。

把入口也读完：多轮对话是怎么接上的

循环写对了，但很多人会忽略入口处的 history。它不是每轮新建的，而是整个会话共用一份：

history = []
while True:
    # ... 读取 query，q / exit 退出 ...
    history.append({"role": "user", "content": query})
    agent_loop(history)
    response_content = history[-1]["content"]
    if isinstance(response_content, list):
        for block in response_content:
            if getattr(block, "type", None) == "text":
                print(block.text)

这段代码解释了两件事。第一，循环结束后 history 不会被清空，所以你可以接着追问“刚才那个文件里写了什么”，模型仍然看得到之前的工具结果——多轮对话的连续性，靠的就是这份不断变长的 list。第二，最终给用户看的只是 text block：工具调用、工具结果都留在 history 里当上下文，不直接打印给用户。

为什么最后要 isinstance(response_content, list) 再遍历？因为 history[-1]["content"] 是最后一条 assistant 消息的内容，正常是 block 列表；但如果你手动塞过字符串消息，这里就会炸。加一层判断，是给“未来的自己”留余地。

一次循环之后，messages 长什么样

光看 append 的代码容易抽象，把一轮之后的 messages 摊开来看就清楚了：

messages[0]  user       "列出当前目录，然后跑 demo.py"
messages[1]  assistant  [ text: "我先看看目录。" ,
                          tool_use(id="toolu_01...", name="bash",
                                   input={"command": "ls -la"}) ]
messages[2]  user       [ tool_result(tool_use_id="toolu_01...",
                                     content="README.md  code.py") ]

三个位置，三种内容，各司其职。第一个 user 消息是人的原话；assistant 消息里既有给用户看的文字，也有给 harness 看的 tool_use；第二个 user 消息里没有一句“人话”，只有机器可读的 tool_result。这就是为什么前面反复强调“user role 不代表一定是人说的”——它代表的是“模型之外的输入”。

id 长什么样、怎么生成，harness 完全不需要关心。它是一个不透明字符串，你唯一的责任是原样搬运：从 block.id 搬到 tool_use_id。不要解析它、不要拼它、不要为了“好看”重写它。把它当成数据库主键来对待，配对就不会出错。

再看一眼那三个 key：type、tool_use_id、content。前两个决定“这是什么、属于谁”，第三个是载荷。少任何一个，API 都拼不出完整的一轮对话。很多刚写 harness 的人会漏掉 type，结果得到一个长得像结果、但协议不认识的字典。

04三个不能省的设计决定

决定代码里的样子省掉会怎样
assistant 内容原样追加content: response.content模型下一轮不知道自己发过 tool_use，可能重复调用；tool_result 失去归属
结果携带 tool_use_id"tool_use_id": block.idAPI 无法把结果配对给调用，请求报错
结果放在 user 消息里{"role": "user", ...}协议里没有第三种角色，assistant 消息不能塞工具结果

这三条不是风格偏好，而是协议约束。你可以把 messages[] 想成一份必须自洽的聊天记录：每一句 assistant 的工具请求，后面都要紧跟着对应的结果；每个结果都要能指回它的请求。任何一条缺失，下一轮请求要么被 API 拒绝，要么让模型的理解出现裂缝。

也正因为如此，后面所有机制——权限、钩子、计划、子代理——都尽量不改这三条，而是改“循环外面”或“工具内部”。核心不变，能力外挂，是从这一讲开始贯穿全课的设计原则。

只存模型的文字

下一轮看不到自己发过 tool_use，容易重复调用；tool_result 也失去归属，成为孤儿。

把结果塞进 assistant

让模型“替世界发言”，既不合协议语义，也容易把它自己的输出当成事实引用。

失败时干脆不返回结果

少一个 tool_result 就少一张配对。正确做法是把错误信息也作为字符串回填。

注意 max_tokens 的含义

max_tokens=8000 限制的是单次回复的长度，不是上下文总量。多轮对话里 messages 只增不减，每一轮都把全部历史重发一次。这就是为什么长任务迟早会碰到上下文上限——第 9 讲 s08_context_compact 专门解决它。

05run_bash：最小防护，不是安全边界

工具执行函数本身只有十几行，但每一行都在防一个具体的坑：

def run_bash(command: str) -> str:
    dangerous = ["rm -rf /", "sudo", "shutdown", "reboot", "> /dev/"]
    if any(d in command for d in dangerous):
        return "Error: Dangerous command blocked"
    try:
        r = subprocess.run(command, shell=True, cwd=os.getcwd(),
                           capture_output=True, text=True, errors="replace",
                           timeout=120)
        out = (r.stdout + r.stderr).strip()
        return out[:50000] if out else "(no output)"
    except subprocess.TimeoutExpired:
        return "Error: Timeout (120s)"
    # ... 其余异常分支略 ...
  • 返回字符串，不抛异常：tool_result 的内容会原样发给模型，错误信息本身是有用的上下文。如果直接抛异常，一次失败就会炸掉整个循环，模型连“刚才那条命令失败了”都看不到。
  • timeout=120：没有超时，一条挂着 vim 或 yes 的命令就能让 agent 永远卡死。超时被捕获后变成一句可读的错误，循环继续。
  • out[:50000]：把输出截断在五万字符。不截，一次 cat 大文件就可能把上下文和 token 预算一起烧光。
  • errors="replace"：命令输出可能是非法 UTF-8，解码失败不该让工具崩掉。
  • dangerous 黑名单：字符串子串匹配，写死的几条。它能拦住手滑的 rm -rf /，但绕过方式多得很——加引号、拼变量、用 find -delete 都行。
别把黑名单当安全

这段代码的定位是“最小防护”：防止演示时把机器弄坏，不是安全边界。真正的权限判断发生在第 4 讲：执行之前先过拒绝列表、规则匹配和用户审批三道闸门。这里先有印象就好。

工具该返回多长的字符串？

这是一个很容易被忽略的取舍。返回太短，模型看不到关键信息，只能再跑一次命令，白白多烧一轮；返回太长，一次 ls -R 的输出就能吃掉几千 token，还会把真正有用的那几行挤到注意力边缘。

s01 用了一个极简策略：截到 50000 字符，空输出统一替换成 "(no output)"。前者防爆，后者防“空字符串让模型以为工具没执行”。这两个处理都不精细，但方向是对的——工具返回的是给模型看的摘要，不是给机器存档的完整日志。

成熟的工具会做得更细：读文件带 limit 并提示剩余行数，搜索只返回命中的路径，命令输出过长时截断中段并保留头尾。但无论怎么优化，原则不变：让模型用最少的 token 拿到“够做下一步判断”的信息。

🔬 深入：为什么 assistant content 必须原样 append？

因为 API 无状态。你每轮把 messages 完整发过去，服务端看到的是一份“剧本”：用户说了什么、assistant 回了什么、哪些 tool_use 被发出、哪些 tool_result 被回填。这份剧本必须自洽，模型才能接着往下演。

如果你图省事，只 append 模型回复里的文字（block.text），那下一轮的剧本里就出现了一句“我这就去读文件”，却没有对应的 tool_use，后面又跟着一个 tool_result。模型看到的是：一个没头没尾的工具结果。轻则困惑、重复调用，重则被 API 直接拒绝。

反过来，原样 append 还有个工程上的好处：response.content 里的 block 对象本身就是 SDK 定义的可序列化结构，下轮直接塞回请求即可，不需要你手工重组。少一次手工转换，就少一类 bug。

再深一层：为什么 tool_result 用 user role？

Anthropic 的 Messages API 只有两种角色：user 和 assistant。assistant 消息代表“模型说的话”，user 消息代表“模型之外的一切输入”：人的提问、系统注入的上下文、以及工具执行的结果。

工具结果不是模型生成的，是 harness 从外部世界拿回来的。把它放进 assistant 消息，等于让模型替世界发言，既不符合语义，也会破坏协议。放进 user 消息，模型读起来就是“环境给了我这些反馈”，和人类用户补充信息的地位一致——这也解释了为什么多轮里 user 和 assistant 会交替出现，哪怕中间没有人真的说话。

🔬 深入：这个循环什么时候会失控？

当前实现是裸的 while True：没有最大轮数、没有成本预算、没有 wall-clock 限制、没有“连续失败就停”的判断。它能正常结束，完全依赖一个经验事实——模型通常会在任务完成后停止请求工具。“通常”不是保证。

失控一般从三个地方开始：模型反复试错（同一命令换着花样跑）、工具持续失败但模型不放弃、任务本身没有明确终点（“帮我优化这个项目”）。典型信号很好认：同一工具同样参数被调用两次以上、每轮消息长度持续增长、错误信息在几轮里重复出现。

生产 harness 通常会在循环外面再套几层保险：最大迭代次数、总 token 预算、连续失败计数、可中断信号。这个仓库把“什么时候停”当成一个独立问题，放到第 18 讲的 goal loop 里认真讨论。现在你只需要意识到：循环能跑起来，和循环能安全停下来，是两件事。

🔬 深入：为什么不用递归、也不用事件回调？

三种写法都能表达“模型与工具反复交互”：递归（工具结果回来后调用自己）、事件回调（工具完成触发下一轮）、循环。仓库的 s01 选了最土的循环，原因是可观测性和可中断性。

递归会把每一轮的调用栈叠起来，长任务跑到几十轮，栈越来越深，想中途插一个“检查预算、决定是否继续”的动作就很别扭；事件回调则把控制流打散到多个函数里，读代码时你得在注册表、回调、主流程之间来回跳。

循环把所有决策点摆在同一屏里：想加预算检查，就在 while 开头加；想加退出判断，就在 return 前面加。后面十几讲加钩子、加压缩、加子代理，本质上都是“在循环的固定位置插逻辑”，而不是重构控制流。可读性就是可维护性，这在 Agent 这种“行为不完全可预测”的系统里尤其值钱。

🔬 深入：一个响应里同时有文字和 tool_use，怎么处理？

真实对话里，模型很少“只吐工具调用”。它更常见的样子是：先说一句“我先看看目录结构”，再发一个 tool_use。这是同一条 assistant 消息里的两个 block，顺序有意义。

s01 的处理方式非常干脆：整条 response.content 原样 append，文字和工具请求一起进历史；给用户展示时，只打印最后那条 assistant 消息里的 text block。这样模型下一轮既能看到自己说过的话，也能看到自己发过的请求，叙述和行动不会脱节。

产品化的 harness 会做得更细：每一轮的 text 实时展示给用户（让用户知道 agent 正在想什么），tool_use 展示成“正在执行 bash …”的状态条，tool_result 折叠起来按需展开。但注意，这些全是展示层的加工，底层 messages[] 依然保持原样，不能为了 UI 好看而裁剪历史。

至于流式（streaming）：它改善的是首字延迟和交互观感，不改变循环的判断逻辑。因为只有等响应完整结束，你才能确定这一轮到底有几个 tool_use、参数是否完整。所以“流式输出”和“循环怎么转”是两层；先把这个非流式循环写对，再谈流式不迟。

06循环的不变量：后面十六讲在改什么

这一讲之后，你会看到课程不断给 Agent 加能力。提前把地图摊开，你就不容易迷失：循环的形状始终是这四步——调用模型、判断要不要工具、执行、回填，变化的是工具、是工具外面的闸门、是循环前后的钩子。

07从零重写时的五个检查点

合上这一讲之前，别背代码，背检查点。下次你自己写循环时，按顺序问这五个问题，基本不会写错：

#检查点写错的典型症状
1调用模型时，messages、tools、system 都传了吗？模型答非所问，或完全不知道自己有工具
2assistant 的 content 原样追加了吗？模型重复调用同一工具，或 API 报配对错误
3是否用 block.type == "tool_use" 判断，而不是猜文字？模型说“完成”但工具仍在请求，循环提前退出
4每个结果都带上了对应的 tool_use_id 吗？下一轮请求 400，提示 id 不匹配
5工具函数返回字符串，而不是把异常抛出去吗？一次失败整个进程崩掉，模型看不到错误现场
调试顺序

循环不按预期工作时，先在第 2 个检查点附近打日志：把每轮 len(messages)、len(tool_calls)、block.name 打出来。九成的“Agent 卡住了”，真相是某一轮 append 的形状不对，而不是模型变笨了。

这五个检查点也解释了为什么这一讲值得慢读：它们不是“最佳实践”，而是协议层面的硬约束。你现在多花十分钟把形状记对，后面十几讲就不用反复回头 debug 消息结构。

最后给自己一个判断标准：如果你能在白板上画出 messages 的三个消息、并说清每个 block 属于谁，这一讲就真的过关了。画不出来，就回到“一次循环之后，messages 长什么样”那一节再看一遍。

09常见误区

  • 很多人以为循环靠模型输出“完成”来判断结束。其实代码里根本没有读模型说了什么。判断只看响应里有没有 tool_use block。模型哪怕写“我完成了”，只要同一个响应里还带了工具调用，循环就继续；反过来，它只说了一句“好的”，循环就结束。
  • 很多人以为工具结果该 append 成 assistant 消息。结果不是模型生成的，是 harness 执行出来的。用 assistant role 既不符合协议，也会让模型误以为那些输出是自己说的。正确做法是 user role，和“环境反馈”的语义对齐。
  • 很多人以为 run_bash 的黑名单就是安全机制。它只是防止演示时手滑的最小护栏。绕过它不需要什么黑客技巧，换个写法就行。真正的权限判断在执行之前，由专门的闸门负责，下一讲之后你就会看到。

10自测

模型返回了一段纯文本，循环会怎么走？

直接 return。因为 tool_calls 是空列表，if not tool_calls 成立。注意此时 assistant 消息已经被 append 了，所以这段总结文字会留在 messages[] 里，下次用户追问时模型还记得自己说过什么。

一次响应里有两个 tool_use，只回填一个 tool_result 会怎样？

不行。协议要求每个 tool_use 都有对应的 tool_result，下一轮请求会因为配对不完整而失败。就算侥幸没报错，模型也会缺一条结果，无法判断该继续还是该修正。正确做法是像代码里那样遍历 tool_calls，一个不落地收集。

把 tools 参数传成空列表，循环还会转吗？

不会转起来。循环本身不检查 tools，它的退出条件始终是“没有 tool_use”。但没有工具可调，模型第一轮只能回纯文本，于是第一次判断就退出。这也说明工具清单和循环控制是解耦的两件事：工具决定“能做什么”，循环只负责“做不做、做几轮”。

把 messages.append({"role": "assistant", ...}) 这行删掉，会发生什么？

下一轮请求的剧本里出现连续两条 user 消息，而且第二条里带着 tool_result，却找不到它对应的 tool_use。模型会失去“我请求过什么”的记忆，可能重复调用同一个工具；API 也大概率直接拒绝。这说明 assistant 原样追加不是可选的记录行为，而是维持对话自洽的必要条件。

把 max_tokens 调到 100，可能出什么问题？

回复会被截断。如果截断发生在 tool_use 的 JSON 参数中间，你拿到的是一个不完整的 block，block.input["command"] 可能取不到，甚至 input 本身就不合法。所以 max_tokens 不是越小越省，它要给“一次完整的工具调用”留够空间。真实 harness 还会检查 stop_reason 是不是 max_tokens，据此决定重试还是报错。

这一讲带走

Agent 的全部秘密不是模型多强，而是那个 while True：把模型的决策变成真实动作，再把动作的结果变成模型下一轮的上下文。三十行代码、一个工具、一个终止条件。以后所有机制，都是往这个循环的四周加东西。
