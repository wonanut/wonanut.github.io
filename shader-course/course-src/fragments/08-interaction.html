01鼠标坐标怎么传

浏览器给的是相对视口的像素坐标，shader 需要 0..1 的 UV。用 getBoundingClientRect() 把坐标映射到画布内，再把 y 翻转（WebGL 原点在左下）：

canvas.addEventListener("pointermove", (e) => {
  const r = canvas.getBoundingClientRect();
  pointer.x = (e.clientX - r.left) / r.width;
  pointer.y = 1.0 - (e.clientY - r.top) / r.height;
  gl.uniform2f(uMouse, pointer.x, pointer.y);
});

触摸屏用 Pointer Events 就能统一处理；如果要做拖拽/缩放，需要记录 pointerId 和初始位置，别把「移动鼠标」和「按下拖动」混在一起。

02分辨率与 DPR

CSS 宽高是显示尺寸，canvas 的 width/height 是像素尺寸。在 Retina 屏上如果直接用 CSS 尺寸，画面会糊；但完全按 DPR 放大，又会增加 4 倍像素。常见折中是限制 DPR 上限：

const dpr = Math.min(window.devicePixelRatio || 1, 1.5);
canvas.width = Math.floor(cssWidth * dpr);
canvas.height = Math.floor(cssHeight * dpr);
gl.viewport(0, 0, canvas.width, canvas.height);

shader 里的 uRes 应该传 canvas.width/height（像素尺寸），这样宽高比与采样密度都正确。窗口变化时用 ResizeObserver 重新设置，而不是只在初始化时算一次。

像用放大镜看画

DPR 是放大镜的倍数：放大能看清细节，但也要处理更多像素。限制 DPR 上限，等于在清晰度和性能之间选一个可接受的折中。

类比到哪为止：放大镜不会改变画的内容；DPR 会改变实际渲染分辨率，shader 里的高频图案在低 DPR 下更容易闪烁。

03暂停与恢复

页面里可能有多个 demo，滚出视口后继续 60fps 渲染纯属浪费。用 IntersectionObserver 在进入/离开视口时启动/停止 requestAnimationFrame；页面隐藏时也停掉。

new IntersectionObserver((entries) => {
  entries.forEach((en) => {
    if (en.isIntersecting) startLoop();
    else stopLoop();
  });
}, { rootMargin: "120px 0px" }).observe(canvas);

document.addEventListener("visibilitychange", () => {
  if (document.hidden) stopLoop(); else startLoop();
});

04shader 侧也有一些性能习惯

先降复杂度，再降分辨率

减少 raymarch 步数、减少 FBM 层数、避免在片元里做昂贵循环，通常比单纯降低分辨率更划算；分辨率下降会先损失清晰度。

另外，尽量把「每帧不变」的计算放到 JS 或 uniform，而不是每个片元重复算。shader 里一次多余的点积可能被几百万像素放大。

🔬 深入：为什么鼠标事件要节流/合并？

pointermove 触发频率可能高于 60Hz，如果每次都更新 uniform 并触发绘制，会浪费。通常只记录最新坐标，在下一帧统一上传；或者用 requestAnimationFrame 合并事件。UI 事件处理不应成为渲染循环的瓶颈。

05自测

为什么鼠标 y 坐标要 1.0 - normalizedY？

浏览器坐标原点在左上、y 向下；WebGL/UV 通常原点在左下、y 向上。翻转后才能让鼠标位置与画面一致。

canvas.width 和 CSS width 的区别？

CSS width 是显示尺寸；canvas.width 是实际像素缓冲尺寸。后者决定 GPU 渲染分辨率，前者只是布局。

为什么会用 IntersectionObserver 暂停 demo？

不可见的画面继续渲染会浪费 CPU/GPU 和电量。离开视口暂停、进入再恢复，是页面里有多个 WebGL demo 时的基本礼貌。
