L0第 1 课

Harness 是什么

模型只会产出下一步，harness 才是把意图变成行动的那层运行时

💡

为什么

第 03 课把 Agent 拆成「模型 + 工具 + 循环」。但如果你只盯着模型看，会漏掉真正让 Agent 跑起来的那层程序：harness。

模型本身是无状态的：它接收一段消息，预测下一段输出，然后忘掉一切。它不会自己执行 read_file，不会把结果塞回上下文，更不会在跑了 50 步之后主动停下。这些事全部由外面那层 harness 完成。

所以有一个反直觉但重要的结论：

✨

模型决定「下一步做什么」，harness 决定「这一步怎么发生、结果怎么回去、什么时候结束」。

理解 harness 有三个实际好处：

  1. 可解释——Agent 行为异常时，你知道该看模型还是看运行时；
  2. 可替换——同一套 harness 可以换模型、换 provider；
  3. 可审计——工具到底被谁执行、权限在哪一层拦截，有明确答案。

这一课先建立边界：harness 是什么，它和 agent framework、orchestrator 分别在哪一层。

🖼️

可视化

用一个具体请求走一遍，看「谁在干活」。用户说：「把 README 里的版本号改成 2.0.0，然后跑测试。」

💡
  • 模型看到消息，产出：调用 read_file，参数 { path: "README.md" }。
  • harness 解析这个 tool call，在本地读完文件，把内容作为 tool result 回填。
  • 模型看到文件内容，产出：调用 edit_file，把 1.0.0 换成 2.0.0。
  • harness 执行编辑，回填结果。
  • 模型产出：调用 run_tests。harness 执行，回填测试输出。
  • 模型看到全绿，产出最终回答。harness 判断这是 final，结束循环。

注意每一步里模型的输出都只是「意图」：一段结构化文本。真正碰文件系统、开子进程、做权限判断的，是 harness。这也是为什么安全边界应该画在 harness 上，而不是指望模型自觉。

三类系统经常被混为一谈，可以这样分层：

💡
  • Harness（运行时）：一次 Agent 会话的循环、上下文、工具协议、权限、流式与会话持久化。
  • Agent framework（开发框架）：在 harness 之上提供抽象，比如规划、记忆、状态机、多步编排、评测脚手架。
  • Orchestrator（编排器）：管理多个 Agent 或多个任务的调度、路由、并发、失败重试与交接。

Pi、Claude Code、Hermes 都处在第一层，但取舍不同：Pi 把核心压到最小，Claude Code 把权限与工作流做深，Hermes 强调记忆与技能蒸馏。第 6 课会展开。

🧮

形式化

给 harness 一个可操作的定义：

💡

harness = 模型调用 + 工具分发 + 结果回填 + 循环，直到模型给出最终回答，或触发某个终止条件。

最小循环的伪代码：

text
transcript = [system_prompt, ...history, user_message]
while true:
    decision = model(transcript)          # 模型只产出「下一步」
    transcript.append(decision)

    if decision is final_answer:
        return decision                    # 模型提议结束

    if decision is tool_call:
        result = dispatch(decision)       # harness 执行工具
        transcript.append(result)         # 结果回填
        continue

    if steps >= MAX_STEPS or timed_out or interrupted:
        return stop_reason                 # harness 强制结束

三个面试高频问题，答案都藏在这段循环里。

1. 谁负责执行工具？ harness。模型只输出结构化的 tool call，harness 校验参数、检查权限、调用真实函数、把返回值序列化成 tool result。模型永远不直接接触文件系统或网络。

2. 谁决定停止？ 分两层。模型提议停止（输出 final answer），harness 裁决停止（final、最大步数、用户中断、超时）。只靠模型自觉会死循环，只靠 harness 硬停会丢答案，所以必须两者配合。

3. 为什么每轮都要重读 transcript？ 因为模型是无状态的。它没有跨请求的记忆，harness 必须在每次调用时把完整对话重新发过去。跑 10 步，模型就看 10 次越来越长的上下文——这既是成本来源，也是上下文工程存在的理由。

把这三件事记住，你就已经能区分「模型能力问题」和「harness 设计问题」了。一个常见的判断法是：如果换更强的模型仍然复现，问题多半在 harness 的循环、上下文或工具协议上。

🛠️

动手

拿一个你熟悉的 Agent 产品（Claude Code、Pi、Cursor 均可），针对「跑一遍测试并修复失败」这个任务，列出 harness 负责的四个动作：

💡
  • 调用：把哪些消息发给模型？system prompt 里有什么？
  • 分发：run_tests 这个工具实际由谁执行？在哪个进程？
  • 回填：测试输出太长时，是原样塞回还是裁剪？
  • 终止：如果连续 10 次测试都失败，谁先喊停？

如果你能明确回答「执行在 harness、停止由 harness 裁决、每轮重发 transcript」，说明你已经建立了正确的分层直觉。

⚠️

常见误区：把「模型说它执行了工具」当成真的执行了。模型只能生成文本；没有 harness 的分发，tool call 只是一段 JSON。反过来，工具执行失败也不该让进程崩溃——harness 应该把错误当成一条 observation 回填，让模型有机会修正。

要点回顾

  • harness = 模型调用 + 工具分发 + 结果回填 + 循环。
  • 模型提议停止，harness 裁决停止；工具永远由 harness 执行。
  • 模型无状态，所以每轮都重读 transcript，成本和上下文压力随之线性增长。
  • harness / agent framework / orchestrator 是三个不同层级，不要混用。
