上下文工程

上下文是预算不是仓库：什么常驻、什么按需、什么必须丢

💡

为什么

第 2 课留下了一个问题：模型无状态，每轮都要重读 transcript。于是 transcript 会越来越长，而上下文窗口是有限的。

很多 Agent 的失败不是模型不够聪明，而是上下文管理失败：

  • 该记住的约束被压缩掉了，模型开始改错文件；
  • 2000 行测试日志原样回填，真正的错误信息被淹没；
  • AGENTS.md 写成一本手册，关键规则排在中间，模型根本没看；
  • 旧任务的历史一直挂着，和新任务冲突。

所以上下文工程的核心不是「怎么写得更多」，而是怎么选得更少。一句话：

✨

上下文是预算，不是仓库。 每个 token 都在和别的内容竞争，进入窗口必须有理由。

🖼️

可视化

下面的分词器是一个玩具实现：它按「连续的字母/数字」和「单个标点」切分，不是真实的 BPE。为了便于观察预算，窗口被缩小到 8 个 token。真实模型的窗口通常是 128k 到 200k，但预算逻辑完全一样。

你好#7，#8世界#9

ids: [7, 8, 9]

上下文窗口预算已用 3 / 8 tokens

窗口是硬预算：system prompt、历史对话、工具结果、本次输出都要挤在这条进度条里。

试三件事：

  1. 默认的「你好，世界」只占 3 个 token，窗口很空。
  2. 输入「把 README 的版本号从 1.0.0 改成 2.0.0」，进度条会直接变红——这个任务本身就要 17 个 token，还没算 system prompt、工具定义和历史。
  3. 删掉「把」「的」「从」这类虚词，观察 token 数下降，但语义是否还完整。

这个演示想说明的是：任务描述、工具结果、历史消息都在抢同一条进度条。真实 harness 里，system prompt 和工具 schema 往往就占掉几千 token，留给对话的空间比你想的少。

🧮

形式化

先写一个预算不等式。设窗口为 CwindowC_{\text{window}}Cwindow​，一次请求包含：

Cwindow≥Psystem+Hhistory+Ttool+OoutputC_{\text{window}} \ge P_{\text{system}} + H_{\text{history}} + T_{\text{tool}} + O_{\text{output}}Cwindow​≥Psystem​+Hhistory​+Ttool​+Ooutput​

其中 PPP 是 system prompt 与工具定义，HHH 是历史对话，TTT 是工具结果，OOO 是本次要生成的输出预留。四项互相挤占，任何一项膨胀都会压缩其他项。

上下文工程有四个主要杠杆：

1. System prompt：只放不变量

放角色、硬约束、输出格式、工具使用规则。不放具体任务细节，也不放可以按需加载的文档。system prompt 越稳定，越容易命中前缀缓存，长期成本越低。

2. AGENTS.md / CLAUDE.md：项目级常驻记忆

这是项目约定、常用命令、目录边界、禁止事项的落脚点。好的写法是短、命令式、可验证；坏的写法是把整个架构文档贴进去。它应该在会话开始时加载，而不是每轮重复解释。

3. 工具结果裁剪：保留信号，去掉噪声

常见策略是限制行数与字节数、保留头部和尾部、把结构化结果压成摘要、错误信息原样保留。裁剪时必须留下明确标记，例如「已截断 1800 行」，否则模型会误以为看到了全部。

4. 压缩（compaction）：有损但可控

当历史接近预算时，把旧轮次总结成一段结构化摘要：目标、已确认的事实、关键文件路径、失败过的尝试、未完成的步骤。原始日志可以丢，但决策与约束不能丢。压缩是有损操作，必须可观测。

把内容按「去留」分类，会更容易做决策：

💡
  • 常驻（resident）：system prompt、核心约束、当前任务目标、工具 schema。
  • 按需加载（on-demand）：项目文档、历史会话、大文件内容；通过检索或工具调用临时取用。
  • 应当丢弃（drop）：重复日志、已经被摘要覆盖的原始对话、与当前任务无关的旧上下文。

为什么这件事在 harness 层做，而不是交给模型？因为模型看不到「预算条」，也无法可靠地自我裁剪。谁持有 transcript，谁负责预算。这也是为什么每轮重读 transcript 不只是成本问题，更是设计问题：harness 必须在每次请求前决定「这一轮到底带什么」。

⚠️

两个常见失败模式：一是「中间遗失」，关键约束放在长上下文中间被忽略；二是「指令冲突」，旧 system 规则与新用户要求矛盾。解法不是加更多字，而是减少冲突源、把硬约束放在稳定且靠前的位置。

🛠️

动手

用上面的 playground 做一次预算练习。目标：让「把 README 的版本号改成 2.0.0 并跑测试」这个任务在 8 个 token 内表达清楚。

💡
  • 原句 17 个 token，超出 9 个。
  • 可以删虚词、合并动作，但不能丢掉「README」「2.0.0」「测试」这三个关键信息。
  • 如果怎么删都放不下，说明该做的不是继续压缩用户话术，而是把细节移到工具或按需文档里。

再为一个编码 Agent 写一份上下文策略，格式可以直接套用：

text
resident:
  - system: 角色、权限边界、输出格式
  - task: 当前目标与验收标准
  - tools: 工具 schema（稳定前缀）
on-demand:
  - AGENTS.md: 会话开始时加载，之后常驻
  - 大文件: 用 read_file 按范围读取
drop:
  - 超过 N 行的原始日志 -> 摘要 + 错误行
  - 已完成的旧轮次 -> 结构化摘要
  - 重复的工具输出 -> 只保留最后一次

最后自检：如果进程明天重启，你的摘要里还剩下什么？只剩「做过什么」而没有「为什么这么做」，说明压缩丢掉了决策依据。

要点回顾

  • 上下文是预算：system、历史、工具结果、输出预留共享同一个窗口。
  • 四个杠杆：system prompt、AGENTS.md/CLAUDE.md、工具结果裁剪、压缩。
  • 分类去留：常驻硬约束、按需加载文档、丢弃重复与过期内容。
  • 谁持有 transcript，谁负责预算；裁剪必须显式标记，压缩必须保留决策依据。
