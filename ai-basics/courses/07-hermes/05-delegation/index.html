L1第 5 课

委派、子 Agent 与 cron

把工作分给子 Agent、把巡检交给 cron：并行、隔离与可观测性

💡

为什么

记忆与技能解决「知道什么、怎么做」，但有些任务不是知识问题，而是执行拓扑问题。

一个复杂任务里，往往同时包含「查资料」「改代码」「跑测试」「写报告」。如果全在一个上下文里串行做，主 Agent 的窗口会被中间过程塞满：搜索结果、失败日志、临时文件……真正重要的结论反而被挤掉。

Hermes 的解法是把这类工作分出去：子 Agent 在自己的上下文里跑完整的 harness 循环，只把摘要交回来；cron 则让任务在你没有坐在终端前的时候也能发生。这一节讲清两件事的收益、成本与边界。

委派的核心不是「多一个 Agent」，而是「多一层上下文隔离」。

🧮

形式化

子 Agent 委派

委派的本质是用上下文隔离换协调成本。主 Agent 不再亲自执行每个细节，而是：

  1. 把任务拆成可独立完成的子任务；
  2. 为每个子任务写一份简报（brief）：目标、范围、约束、产出格式、验收标准；
  3. 创建子 Agent，让它在自己的上下文里跑循环；
  4. 接收子 Agent 的摘要，合并、校验、处理冲突。

子 Agent 通常不继承主 Agent 的完整对话历史。它拿到的是简报与必要背景，因此上下文更干净、推理更聚焦；主 Agent 也不必承载子 Agent 的几十次工具调用。

💡

三个主要收益：上下文隔离（主上下文不被中间过程污染）、并行（多个子任务同时跑）、专业化（每个子 Agent 只带自己需要的工具与技能）。

代价同样真实：

  • token 倍增：父子都要调用模型，复杂任务的成本可能是单 Agent 的数倍。
  • 协调开销：拆分不当会重复劳动，或留下没人负责的缝隙。
  • 摘要损失：子 Agent 回传的是压缩后的结论，细节与不确定性可能丢失。
  • 权限继承：子 Agent 能做什么，取决于你给的边界；边界过宽会放大风险。
  • 可观测性：多了一层，日志、耗时、失败原因都更难追踪。
⚠️

委派不是越多越好。小而紧耦合的任务（例如「把这个函数改个名」）自己做完更快；拆开反而增加协调成本。判断标准是：子任务能否独立定义验收？能，才值得分出去。

后台 review agent

别把它和任务子 Agent 混淆。nudge engine 触发的 review agent 是另一类：

  • 它由计数器触发，不由用户显式创建；
  • 它读最近的轨迹，做记忆整理与技能沉淀；
  • 它有较小的工具调用上限，避免后台任务失控；
  • 它在旁路运行，输出不打断主任务，失败也不影响主流程。

一句话：任务子 Agent 是「帮你干活」，review agent 是「帮你复盘」。

cron 定时任务

cron 把 harness 从「你问它答」扩展成「到点自己跑」。典型场景：

  • 日报 / 周报：汇总 Issue、提交、CI 状态；
  • 巡检：检查仓库健康、依赖过期、异常日志；
  • 长任务：定时拉数据、生成报告、跑回归。

公开资料描述 Hermes 支持 cron 调度，但工程上必须补齐四件事，否则定时任务会变成定时事故：

💡
  • 幂等：同一时间窗重复触发，不应产生重复副作用。
  • 超时与重试：长任务要能被打断，失败要能重试并告警。
  • 成本预算：每次运行都有 token 与工具成本，要有上限。
  • 可观测：记录 run id、输入、输出、耗时、失败原因，能回放。

还要处理「错过」与「重叠」：机器休眠导致任务没跑，要有补偿策略；上一次还没结束，下一次又触发，要有锁或跳过策略。

权限与可观测性

委派和 cron 都会放大权限面：一个 Agent 能做的事，乘以并行数、再乘以运行频率。最低要求是：

  1. 最小权限：子 Agent 只拿完成子任务所需的工具。
  2. 沙箱：终端与文件操作限制在项目目录内。
  3. 审计：每次委派与定时运行都有独立 trace，能回答「谁在什么时候做了什么」。
  4. 急停：有办法取消一个失控的子 Agent 或定时任务。

记忆与技能的写入仍然走第 3 节的扫描与回滚路径；委派不会绕过它，只会让「谁写的」更需要被记录。

🛠️

动手

先写一份可复用的委派简报模板。简报质量直接决定子 Agent 的产出质量：

text
目标：一句话说明要达成什么
范围：允许读写的目录 / 系统
约束：技术栈、风格、不能做的事
产出：文件、补丁、报告或结论
验收：如何判断完成（测试、命令、检查项）
回报：只回传结论、证据与未决问题

再设计一个「早晨巡检」的 cron 工作流：

text
每天 08:30
1. 拉取过去 24h 的 CI 失败与新增 Issue
2. 委派子 Agent：按仓库分组，判断是否为已知问题
3. 子 Agent 回传：失败摘要 + 疑似原因 + 建议动作
4. 主 Agent 合并为一份晨报
5. 高风险项标注「需人工确认」，不自动改代码
✨

上线前用三个问题自检：重复跑会不会产生重复副作用？失败时有没有人知道？单次运行的成本上限是多少？ 三问有一个答不上来，就不要让它无人值守。

要点回顾

  • 委派＝用上下文隔离换协调成本：简报、子循环、摘要回传、主 Agent 合并。
  • 子 Agent 适合可独立验收的子任务；紧耦合的小任务自己做完更快。
  • 后台 review agent 是「复盘」，任务子 Agent 是「干活」，两者不要混淆。
  • cron 适合日报、巡检、长任务；必须补幂等、超时重试、成本预算与可观测性。
  • 权限最小化、沙箱、审计与急停，是自动化的安全带。
