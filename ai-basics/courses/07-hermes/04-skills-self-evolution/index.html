L0第 4 课

Skill 系统与自进化

把一次复杂任务固化成 SKILL.md：触发、渐进加载、打补丁与风险

💡

为什么

情景记忆解决「记住事实」，但很多经验不是事实，而是流程。

比如「在这个仓库新增一节课程」：先读相邻课时对齐风格，再写 frontmatter，按五步模板组织正文，最后跑测试、检查行数与 MDX 陷阱。这条流程有十几步，每次从零推理既慢又容易漏。你真正想要的是：第一次摸索，第二次直接按步骤执行。

这就是技能记忆（程序化记忆）的价值。它把一次成功（或失败后修正）的轨迹，压缩成一份人类可读的 SKILL.md。从此以后，模型不必重新发明流程，只需要判断「这个任务像不像那个技能」，然后按需加载。

但技能也是自进化里风险最高的部分：事实写错只错一条，流程写错会错一串，而且会被反复复用。这一节既讲它怎么长出来，也讲它怎么长歪。

🖼️

可视化

技能的一生是一个闭环，不是一次性写入：

text
复杂任务完成 / 被纠正 / 从错误恢复
        ↓
   触发判定：值得沉淀吗？
        ↓
  写 SKILL.md：何时用、步骤、验证、坑
        ↓
  system prompt 只放索引（名字 + 一句话）
        ↓
   下次命中 → 按需加载全文 → 执行
        ↓
  发现过时 / 缺步骤 → 就地打补丁
        ↓
   失败则回滚到上一版本
✨

闭环的关键不是「写」，而是**「用的时候还会改」**。技能不是文档，是一份会被执行、被验证、被修订的活工件。

🧮

形式化

SKILL.md 的结构

公开资料描述 Hermes 采用 agentskills.io 风格的技能格式，典型结构包含 frontmatter（name / description）、何时使用、步骤、验证与常见坑（字段名以实际版本为准）。其中三部分最重要：description 决定「什么时候被选中」，写太泛永远不加载，写太窄稍有变化就命中不了；步骤 要可执行、有顺序、能验证，而不是泛泛的「认真分析」；验证与坑 让下一次执行能自检，这是技能比普通文档多出来的部分。

什么时候创建或更新技能

不是每个任务都值得沉淀。公开资料描述的触发条件通常包括：

💡
  • 任务包含 5 次以上工具调用；
  • 执行过程中从错误中恢复过；
  • 用户纠正了做法；
  • 流程明显非平凡，下次还可能重复。

这些条件的共同点是：信息量足够大，且复用概率不低。一次性的简单问答不该写成技能，否则技能库会被噪声撑爆。

更新则发生在使用时：如果技能里的命令过时、步骤缺失、或者环境已经变化，Hermes 会在执行中就地打补丁——常见做法是模糊匹配定位要改的段落，做局部替换；如果替换失败或校验不通过，就回滚到上一版本。模糊匹配意味着「可能改错地方」，所以补丁越自动，越需要版本记录与验证步骤。

渐进加载：为什么 system prompt 只放索引

技能全文可能很长。如果把所有 SKILL.md 都塞进 system prompt，上下文会被迅速吃光，而且大部分内容与当前任务无关。

Hermes 的做法是渐进加载（progressive disclosure）：

  • system prompt 里只放索引：技能名 + 一句话描述；
  • 模型判断相关后，再通过工具按需加载全文；
  • 执行完不必长期占用上下文。

这样技能数量可以增长，而基础上下文成本近似常数。代价是：索引质量决定召回质量。名字含糊、描述重复，模型就选不中或选错。

Nudge Engine：后台的整理工

技能和记忆不会只靠主任务顺手写。Hermes 还有一个 Nudge Engine：分别按轮次和工具迭代计数，公开资料描述默认大约每 10 次触发一次后台 review agent。

这个 review agent 做两件事：

  1. 整理记忆：把散落在轨迹里的事实、偏好、决策提炼进 MEMORY.md / USER.md。
  2. 沉淀技能：判断这次任务是否值得固化成 SKILL.md，或修补已有技能。

它的三个工程约束很关键：

  • 有工具调用上限：review 通常只能做少量操作，避免后台任务失控（上限以版本为准）。
  • 不打扰主任务：它在旁路运行，输出不打断用户正在进行的对话。
  • 可失败：整理失败不应影响主流程；写入失败则回滚。
💡

社区里常把「把长轨迹提炼成简短记忆/技能」称为蒸馏（distillation）。这是对机制的形象说法，不是 Hermes 已发布的某个独立模块或命令；公开资料描述的是 nudge + review 的整理流程。

收益与风险

收益是复利：

  • 同类任务越来越快，步骤越来越稳；
  • 团队共享技能，相当于共享「操作手册」；
  • 技能是纯文本，可 review、可 diff、可迁移到别的 harness。

风险也是复利：

  • 错误技能会被反复执行，一次错步骤可能污染一批结果；
  • 技能会过时：命令、路径、API 变了，技能不会自动知道；
  • 过度拟合：为一个仓库写的技能，换个项目可能完全不适用；
  • 技能蔓延：太多相似技能，索引互相干扰，召回变差；
  • 注入风险：技能内容来自轨迹，轨迹里可能混入不可信指令。
⚠️

自进化不等于自动可信。正确姿势是：把技能当代码管理——有版本、有测试、有 review、有淘汰。关键流程（发布、删除、对外发送）尤其要保留人工确认。

🛠️

动手

写一份最小可用的 SKILL.md，主题就用「给这个仓库加一节课程」。注意三件事：描述要能命中、步骤要可执行、验证要能自动跑。

text
---
name: add-course-lesson
description: 在本仓库 content/courses 下新增一节 MDX 课程时使用
---

# 何时使用
用户要求新增、改写或补齐课程章节。

# 步骤
1. 读目标课程的 course.json 与相邻课时
2. 写 frontmatter：title / order / level / summary
3. 正文从 Why 开始，依次写 Viz / Formal / HandsOn / Checkpoint
4. Checkpoint 放 Quiz 与「要点回顾」
5. 运行测试，检查行数与 MDX 陷阱

# 验证
- 五个区块齐全且顺序正确
- Quiz 数量达到该节要求
- 正文没有裸花括号或裸尖括号

# 常见坑
- code 属性里的换行要写成转义换行
- 正文里的花括号要放进反引号代码
- 新增文件后确认课程索引能扫描到

然后做一次「使用中修补」的演练：

✨
  1. 故意把第 5 步写成「跑 build」，执行一次，观察它是否发现测试才是更快的验证。
  2. 让它就地修改这一行，并保留其余步骤。
  3. 检查修改是否落在正确位置；如果它改错了，确认能否回滚。
  4. 把这次修补记进技能的「常见坑」，让下一次不再犯。

最后，给技能加一条淘汰规则：连续两次执行失败，或超过三个月未被使用，就标记为待审查。技能库需要新陈代谢，否则索引会被僵尸技能占满。

🎯

要点回顾

  • SKILL.md 三要素：可命中的 description、可执行的步骤、可自动跑的验证与坑。
  • 触发条件：5+ 次工具调用、错误恢复、用户纠正、非平凡流程。
  • 渐进加载：system prompt 只放索引，全文按需加载。
  • 使用中发现过时可就地打补丁，失败回滚；nudge engine 周期性做后台整理。
  • 「蒸馏」是社区称呼，不是已发布的独立模块；技能要像代码一样管理。
