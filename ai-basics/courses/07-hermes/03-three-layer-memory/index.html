L1第 3 课

三层记忆

工作记忆、情景记忆与技能记忆：经验如何被写下、召回并保护

💡

为什么

上一节说循环是标准的，那「越用越顺手」到底发生在哪里？答案是记忆。

模型本身是无状态的：每次调用只看得到你这次喂进去的上下文。如果没有外部记忆，所谓「学习」就只剩两种假象——要么你在提示词里重复交代，要么模型在长会话里碰巧没忘。两者都不可靠。

Hermes 把记忆拆成三层，分别回答三个问题：

  1. 此刻在想什么——工作记忆，活在一次会话里。
  2. 关于你和项目，长期该记住什么——情景记忆，跨会话保存事实与偏好。
  3. 这类事该怎么做——技能记忆，把流程固化成可复用技能。

三层合起来，才构成「经验」。这一节逐层拆开，并讲清楚两个容易被忽略的点：快照为什么要冻结，以及写入为什么必须过安全扫描。

🖼️

可视化

先点开三层，建立整体印象：

资料里三层常被叫作「工作 / 情景 / 语义」或「会话 / 持久 / 技能」；第三层也称「程序化记忆」，本质都是把经验固化成可复用技能。

工作记忆Working Memory

  • 存什么：本次任务的 system prompt、最近几轮对话、工具调用与结果。
  • 生命周期：只活在当前会话，受 context window 硬限制。
  • 怎么处理：接近上限时做一次摘要压缩，只保留最近几轮原文。
  • 类比：你此刻的工作台，项目收尾后会被整理归档。
💡

不同资料的命名略有差异：有人叫「工作 / 情景 / 语义」，有人叫「会话 / 持久 / 技能」，第三层也常被称为「程序化记忆（procedural memory）」。名字不同，指的是同一件事：短期上下文、长期事实、可复用流程。本课统一用工作 / 情景 / 技能。

一次会话里，信息大致这样流动：

text
用户消息 + 记忆快照 + 技能索引
        ↓
   模型调用 ⇄ 工具执行
        ↓
  工作记忆（当前上下文窗口）
        ↓  压缩 / 检查点 / nudge / 用户显式指令
  候选记忆 → 安全扫描 → 写入 / 回滚
        ↓
  MEMORY.md   USER.md   SKILL.md
        ↓
  SQLite + FTS5（跨会话全文检索）

注意：写入不是每轮都发生。它由几个明确时机触发，否则记忆会被噪声淹没。

🧮

形式化

第一层：工作记忆（Working Memory）

工作记忆就是当前会话的上下文窗口：system prompt、记忆快照、技能索引、最近几轮对话、工具调用与结果，全都在这里。

它的生命周期只到会话结束，且受 context window 硬限制。接近上限时，Hermes 会做一次摘要压缩：把较早的轮次压成摘要，保留最近几轮原文，让循环能继续跑。

⚠️

压缩是有损的。被压掉的细节，模型之后只能靠记忆文件或检索找回来。所以重要事实不要只留在对话里——这也是 Hermes 要在压缩前后做记忆沉淀的原因。

第二层：情景记忆（Episodic Memory）

情景记忆保存跨会话的事实、偏好与经历。它主要由两个人类可读的 Markdown 文件承载：

💡
  • MEMORY.md 记「事」：项目背景、关键决策、当前进度、踩过的坑。
  • USER.md 记「人」：你的身份、偏好、沟通风格、长期约束。

为什么用两个文件而不是一个？因为二者的生命周期与隐私级别不同。项目事实可以随仓库走、可以进 Git；个人偏好往往只属于你，不应该被提交到公共仓库。分开存，边界更清楚。

写入之后，情景记忆还有一条检索通道：SQLite + FTS5 全文索引。Markdown 文件负责「当前该注入什么」，FTS5 负责「历史里哪条相关内容该被找回来」。两者互补：文件是精炼后的稳定摘要，数据库是可搜索的原始经历。

最关键的设计是快照冻结：会话开始时，Hermes 把 MEMORY.md / USER.md 的内容冻结成一份快照，注入 system prompt；会话进行中即使文件被更新，也不会频繁改写这段前缀。

✨

为什么冻结？为了保护 prefix cache。模型 API 通常对稳定前缀有缓存优惠；如果 system prompt 每轮都变，缓存全失效，成本与延迟都会上升。冻结快照是用「一点新鲜度」换「稳定的缓存命中」。

情景记忆的写入时机通常是四类：

  1. 压缩前：趁细节还在，把值得留的写出去。
  2. 检查点：任务阶段性完成时做一次整理。
  3. nudge：后台 review agent 周期性整理。
  4. 用户显式指令：你说「记住这个」，它就应该写。

文件有容量上限，因此写入不是简单追加，而要做去重、合并、淘汰：旧决策被新决策替代时，保留最新结论而不是堆两份。

第三层：技能记忆（Skill / Procedural Memory）

技能记忆保存**「怎么做」，载体是 SKILL.md。分工可以一句话概括：情景记忆回答「是什么、发生过什么」，技能记忆回答「遇到这类任务，按什么步骤做」。技能不整篇塞进 system prompt，而是只放索引**：名字 + 一句话描述。模型判断需要时，再按需加载全文。这叫渐进加载（progressive disclosure），目的是让技能数量可以增长，而上下文成本近似常数。第 4 节会展开 SKILL.md 的结构与自修补机制。

写入路径与安全边界

三层记忆最终都要落盘，而落盘是这个系统最危险的动作之一：你把不可信内容写进了未来每一轮的上下文。

因此写入通常走一条受控路径：

text
1. 生成候选：模型判断「这条值得记」
2. 安全扫描：检查 prompt injection、密钥、个人信息
3. 受控写入：先写临时文件再替换（细节以版本为准）
4. 校验：读回确认格式与内容
5. 失败回滚：恢复上一版本，记录错误
⚠️

记忆是持久的攻击面。一个恶意网页、一条 Issue 评论，都可能试图让 Agent「记住」一条指令。扫描能挡掉一部分，但不能替代人类审查：涉及权限、密钥、对外发送内容的记忆，最好定期人工过一遍。

🛠️

动手

第一步，找到数据目录，直接读文件。不要只看 Agent 的自我描述：

text
<data-dir>/
  MEMORY.md
  USER.md
  skills/
  <memory-db>      # SQLite，具体文件名以你的版本为准

第二步，看数据库里有什么表。FTS5 通常表现为若干虚拟表，表名以实际 schema 为准：

bash
sqlite3 <data-dir>/<memory-db> ".tables"
sqlite3 <data-dir>/<memory-db> ".schema"

第三步，做一次跨会话召回实验：

text
会话 A
你：以后回答我时先给结论，再给理由。

会话 B（新开）
你：解释一下 prefix cache。
Hermes：结论：它缓存稳定的提示词前缀……
（观察它是否一上来就按「先结论后理由」回答）
✨

判断标准不是「它说记住了」，而是：新会话的 USER.md 快照里有没有这条偏好，以及回答风格是否真的改变。若没变，检查写入时机是否被触发、文件是否有容量淘汰。

最后做一个「该写哪里」的判断：项目约定进 MEMORY.md，个人偏好进 USER.md，可复用流程进 SKILL.md，一次性推理留在工作记忆、不落盘。

要点回顾

  • 工作记忆＝当前上下文窗口，会话结束即失，接近上限时摘要压缩。
  • 情景记忆＝MEMORY.md（事）+ USER.md（人），SQLite + FTS5 负责全文召回。
  • 会话开始时冻结快照注入 system prompt，用一点新鲜度换 prefix cache 的稳定命中。
  • 技能记忆＝SKILL.md，system prompt 只放索引，按需加载全文。
  • 写入时机：压缩、检查点、nudge、用户显式指令；写入前扫描，失败回滚。
