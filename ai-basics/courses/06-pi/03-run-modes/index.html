L1第 3 课

四种运行模式

同一个 harness 的四张「脸」：从交互到嵌入

💡

为什么

同一个 Pi，为什么要四种「运行模式」？

因为使用场景不同，交互方式就该不同。但关键洞察是：核心循环完全不变，变的只是输入/输出的外壳。理解这一点，你就抓住了「运行时」和「界面」分离的架构意义。

🖼️

可视化

四种模式的定位：

💡
  • InteractiveMode（TUI）：交互式终端界面，你一句我一句，面向人。
  • runPrintMode（print）：一次性提问，打印结果后退出，适合脚本 / 管道。
  • JSON / RPC 模式：输出结构化 JSON 或走 RPC，供程序解析。
  • SDK：createAgentSession() 直接嵌入你自己的 TS/JS 程序。

🧮

形式化

四者的本质区别是输入/输出的形态，而非内核：

💡
  • TUI：标准输入/输出 + 终端绘制，面向人；适合边看边改。
  • print：命令行参数进、纯文本出，可被 | 管道拼接；适合脚本化、批处理。
  • RPC / JSON：结构化消息进出，面向程序；适合把 Pi 当后端服务。
  • SDK：进程内 API（createAgentSession() + SettingsManager / SessionManager），完全在你的程序里运行；适合深度嵌入自己的工具链。

一个常见的架构面试点：为什么 print 模式要做成「纯文本、无装饰、退出一问一答」？ 因为只有纯文本才能干净地进管道——如果混入 TUI 的控制字符（ANSI 转义、进度条），下游程序就没法解析了。这背后是 Unix 哲学：做一件事，用文本流把它接起来。

SDK 则是另一极：你不想要进程边界，想要在同一进程里、用代码直接驱动一次会话，于是拿到的是 API 而不是子进程。

🛠️

动手

最常用的两个形态。

进入 TUI 交互式对话：

bash
pi

单次、脚本化的 print 用法（具体 flag 以 pi --help 为准）：

bash
pi -p "总结一下 README.md"

SDK 嵌入（示例骨架）：

ts
import { createAgentSession } from "@earendil-works/pi-coding-agent";
// 在代码里驱动一次会话，拿到结构化结果
💡

想输出 JSON 或走 RPC 时，用对应的模式开关。它们和上面共享同一套会话循环，只是把「结果」序列化成了机器可读的格式。

要点回顾

  • Pi 有 TUI / print / JSON / RPC / SDK 多种运行模式。
  • 区别只在输入输出形态，核心循环和工具不变。
  • 人机交互用 TUI，脚本用 print，嵌入用 SDK，跨进程用 JSON/RPC。
