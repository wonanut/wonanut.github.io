核心四件套 read/write/edit/bash

四个文件/Shell 工具的确切语义、边界与并发模型

💡

为什么

为什么核心工具只有四个——read / write / edit / bash？

因为对「用代码做事」的 Agent 来说，文件系统和 Shell 就是它的手和眼睛。几乎所有开发任务，最终都落到：

  1. 看：读文件、看命令输出（read、bash）；
  2. 改：写文件、改文件、跑命令产生效果（write、edit、bash）。

这四个工具覆盖了「读取现状 → 修改 → 验证」的完整闭环。

✨

工具越少，行为越可预测。每个工具的确切语义（边界、失败条件、并发行为）是你能推理 Agent 行为的前提——这也是面试会深挖的地方。工具数量不是能力，语义清晰才是。

🖼️

形式化

四个工具的语义，逐条说清——重点是边界和失败条件：

💡
  • read：读一个文本文件，分页（offset/limit）；长文件取头部截断（约 2000 行 / 50KB）。返回原始文本、不带行号前缀；对二进制/图片文件直接报错。
  • write：创建或整体覆盖一个文件；同一路径的写入串行化，避免并发写互相穿插。
  • edit：只改文件一部分。整个「读-改-写」在路径的变更锁下进行；用精确文本匹配定位，且每个 edit 都匹配同一份原始内容（不是前面 edit 的结果），再按反向偏移依次应用；匹配到 0 处或多于 1 处都视为错误。
  • bash：跑一条 Shell 命令；非零退出码 = 工具级错误（让模型把「失败的命令」当作失败看到）；支持超时；长输出取尾部截断（错误信息在末尾），完整输出存到临时文件并返回其路径。

几个面试必考的设计点，展开讲：

① edit 为什么用「精确文本匹配」而不是「行号」？

行号会随前面的编辑而漂移，且模型看到的文件没有行号（read 不带行号前缀）。精确匹配是幂等、可验证、失败即报错的：匹配到 0 处或多处，直接报错而不是静默改错文件——这叫 fail-closed（失败关闭），是「可预测」的关键。

② write vs edit 什么时候用哪个？

write 是整体替换，edit 是局部手术。对长文件，模型应优先 edit 只动该动的地方：省 token、少出错、变更可审计。整体 write 长文件等于把没变的内容也重发一遍。

③ bash 为什么把非零退出当错误？

否则模型会把「编译失败 / 测试挂了」误读成成功，接着在错误前提上继续干活。把 shell 的真实退出码透传给模型，是「让 Agent 能看见失败」的基本功。

④ 并发模型

多个工具调用串行准备、并发执行，但结果按源顺序收集返回。所以模型发两个 read，它们并行读，但回填顺序和发出顺序一致——模型看到的结果是确定性的。

⑤ 沙箱（sandbox）与路径边界

开了沙箱，文件工具和 bash 都作用在沙箱工作目录内，且拒绝路径越界（无法访问工作目录外的路径）；没开沙箱，文件工具操作 Pi 自己的 SQLite 数据库，bash 因无 shell 而报错。每个工具暴露的 *Operations 接口（ReadOperations / WriteOperations / EditOperations / BashOperations）就是「换 I/O 底座」的挂载点——沙箱、SSH、远程 API 都靠它接进来。

⑥ 截断上限（达到任一即截断）：

💡
  • bash：2000 行 / 50KB（取尾）；
  • read：2000 行 / 50KB（取头）；
  • grep：100 条匹配，500 字符/行；
  • find：1000 条结果；
  • ls：500 条。
🛠️

动手

在 Pi 的 TUI 里，你通常不需要手动调工具——模型会自动调用。但理解语义，能帮你读懂 trace、判断模型是否走对，也能在面试里讲清「为什么这么设计」。

想只装其中几个工具，用对应的工具工厂：

text
createReadTool / createWriteTool / createEditTool / createBashTool
⚠️

手动调用单个工具的命令名（如 /read <file>）可能随版本略有差异，以 pi --help 和官方文档为准。上面这些语义（分页、精确匹配、非零退出、并发序、截断）是稳定的核心概念。
