L0第 8 课

源码解析：工具引擎

edit 匹配算法、bash 退出码、截断与并发锁的逐行拆解

💡

为什么

这一课拆 Pi 最硬、也最能拉开面试差距的部分：四个工具的源码实现。

为什么值得逐行读？因为第 2 课讲的「精确匹配、非零退出即报错、源序回填」这些结论，源码里都有更精确、更反直觉的实现。比如：edit 其实不是纯精确匹配，而是「先精确、再 Unicode 归一化模糊」；bash 的非零退出在代码里是 isError: true；截断还专门处理了多字节 UTF-8 的边界。这些细节，就是「读过源码」和「看过文档」的区别。

🖼️

可视化

四个工具的共同骨架（读 tools/*.ts 时都长这样）：

💡
  • *Schema：用 TypeBox 声明输入参数（path / oldText / command…），同时生成 JSON Schema 给模型做受约束采样。
  • *Operations 接口：把「工具逻辑」和「I/O 底座」解耦（默认本地文件系统，可换成 SSH/远程）。
  • createXxxToolDefinition：组装 description + parameters + execute，返回一个 ToolDefinition。
  • execute：真正干活的函数，返回 { content: [{type:"text", text}], details, isError? }。

理解了这个骨架，下面每个工具就是「往骨架上填肉」。

🧮

形式化

① edit：最精彩的一个。tools/edit.ts + tools/edit-diff.ts

输入 schema（注意是 edits[] 数组，一次可改多处）：

ts
const editSchema = Type.Object({
  path: Type.String({ description: "Path to the file to edit (relative or absolute)" }),
  edits: Type.Array(Type.Object({
    oldText: Type.String({ description: "Exact text for one targeted replacement. It must be unique..." }),
    newText: Type.String({ description: "Replacement text" }),
  })),
});

真正干活的 applyEditsToNormalizedContent，核心逻辑（精简注释）：

ts
export function applyEditsToNormalizedContent(normalizedContent, edits, path) {
  // 1. oldText 为空 → 报错
  // 2. 每个 edit 先用 fuzzyFindText 匹配：先精确，失败再模糊
  // 3. countOccurrences > 1 → 报错 "must be unique"
  // 4. 没匹配到 → 报错 "old text must match exactly including all whitespace"
  // 5. 按 matchIndex 排序，检测重叠 → 报错 "overlap. Merge them into one edit"
  // 6. applyReplacements：反向遍历应用，保证偏移稳定
  // 7. 结果与原内容相同 → 报错 "No changes made"
}

第 2 课说「精确匹配」，更准确的说法是——先精确、再模糊。模糊匹配的归一化逻辑：

ts
export function normalizeForFuzzyMatch(text: string): string {
  return text
    .normalize("NFKC")
    .split("\n").map((line) => line.trimEnd()).join("\n")  // 去行尾空格
    .replace(/[\u2018\u2019\u201A\u201B]/g, "'")   // 智能引号 → ASCII
    .replace(/[\u201C\u201D\u201E\u201F]/g, '"')
    .replace(/[\u2010-\u2015\u2212]/g, "-")           // 各种破折号 → 连字符
    .replace(/[\u00A0\u2002-\u200A\u202F\u205F\u3000]/g, " "); // 特殊空格 → 普通空格
}
💡

为什么要有模糊匹配？因为模型可能用「智能引号」“ 而文件里是 ASCII "，或全角空格 　 vs 普通空格。归一化后再匹配，大幅降低「明明内容一样却匹配失败」的假阴性，同时仍要求归一化后唯一。这是工程上「鲁棒 + 安全」的平衡。

还有两个硬核细节：

💡
  • 行尾处理：edit 会先 normalizeToLF（把 \r\n → \n），匹配完再 restoreLineEndings 还原——所以改一个 Windows CRLF 文件不会把整份文件的行尾洗成 LF。
  • BOM 处理：splitBom 先剥掉 BOM 再匹配（模型不会把不可见的 BOM 写进 oldText）。

② read：tools/read.ts

ts
const readSchema = Type.Object({
  path: Type.String(),
  offset: Type.Optional(Type.Number({ description: "Line number to start reading from (1-indexed)" })),
  limit: Type.Optional(Type.Number({ description: "Maximum number of lines to read" })),
});

读完后如果被截断，会在末尾主动告诉模型怎么继续：

text
// 截断后的可执行提示
"[Showing lines 1-2000 of 5000. Use offset=2001 to continue.]"
// 首行就超字节上限时，指引用 bash 兜底
"[Line 300 is 80KB, exceeds 50KB limit. Use bash: sed -n '300p' file | head -c 51200]"

这是「工具和模型协作」的典范：工具不直接读全，而是返回一个「续读」的接口（offset），让模型自己决定要不要继续。

④ bash：tools/bash.ts 的退出码处理（第 2 课结论的源码实锤）

ts
if (exitCode !== 0) {
  return {
    content: [{ type: "text", text: appendStatus(outputText, `Command exited with code ${exitCode}`) }],
    isError: true,   // ← 非零退出 = 工具级错误
  };
}
return { content: [{ type: "text", text: outputText }], details, structuredContent };
// 信号终止：exitCode = 128 + signalNumber（标准约定，不会误判成成功）
// 无退出码：throw "Command terminated without an exit code"

另外 bash 会暴露会话元数据为环境变量 PI_*（PI_SESSION_ID / PI_PROVIDER / PI_MODEL 等），供命令内部使用。

⑤ 截断：tools/truncate.ts

ts
export const DEFAULT_MAX_LINES = 2000;
export const DEFAULT_MAX_BYTES = 50 * 1024; // 50KB
export const GREP_MAX_LINE_LENGTH = 500;
// truncateHead（读文件取头部）/ truncateTail（bash 取尾部）/ truncateMiddle（头尾保留）

truncateTail 处理多字节 UTF-8 边界时，会从后往前找字符起点（(buf[start] & 0xc0) === 0x80 判断是否为续字节），绝不把半个汉字切断。

⑥ 并发锁：tools/file-mutation-queue.ts

ts
const fileMutationQueues = new Map<string, Promise<void>>();
export async function withFileMutationQueue(filePath, fn) {
  const key = await getMutationQueueKey(filePath); // realpath 归一化
  const currentQueue = fileMutationQueues.get(key) ?? Promise.resolve();
  // ... 用 Promise 链：await currentQueue 再执行 fn
  await currentQueue;
  try { return await fn(); } finally { releaseNext(); }
}
💡

这就是第 2 课「write 串行化」的源码实现：Map<realpath, Promise>，同一个文件的操作排队串行，不同文件并行。用 Promise 链做锁，而不是全局大锁——并发粒度恰到好处。

🛠️

动手

把这几个文件按「由易到难」读一遍，每读一个问自己三个问题：

💡
  1. 输入参数是什么？（TypeBox schema 就是答案）
  2. 失败条件有哪些？（每个 throw / isError 都是一条）
  3. 返回值长什么样？（{ content, details, isError? }）

最能练手的是自己写一个自定义工具——第 5 课的 registerTool 里的 execute 签名，就是上面这些 ToolDefinition 的 execute。

⚠️

execute 的精确签名（(toolCallId, input, signal, onUpdate, ctx)）可能随版本微调，写扩展时以安装版本的 .d.ts 为准。核心机制——schema 驱动、Operations 解耦、isError 标记、每路径锁——是稳定的。

要点回顾

  • 四个工具共享骨架：TypeBox schema + *Operations 接口 + execute。
  • edit：edits[] 数组、精确→模糊（Unicode 归一化）、去重/重叠检测、反向应用、行尾/BOM 处理。
  • bash：非零退出 → isError: true；信号终止 = 128+n；尾部截断存临时文件。
  • truncate：2000 行 / 50KB，处理多字节 UTF-8 边界。
  • 并发锁：Map<realpath, Promise>，同文件串行、跨文件并行。
