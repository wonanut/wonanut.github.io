L0第 7 课

源码解析：架构与消息模型

从 createAgentSession 到消息流，源码级拆解

💡

为什么

前 6 课讲的是概念。概念会被文档美化，源码不会说谎。这一课开始直接读仓库 earendil-works/pi 的 packages/coding-agent/src（263 个源文件）。

为什么这对面试重要：当你说「Pi 的核心循环很小」时，能接着指出「装配逻辑在 agent-session-services.ts、消息转 LLM 在 messages.ts 的 convertToLlm、四个核心工具在 tools/index.ts 的 createCodingToolDefinitions」，你就不再是在背概念，而是在引证代码——这是从「会用」到「精通」的分水岭。

🖼️

关键观察：工具执行、会话树、扩展、压缩各自是一个独立目录，职责单一；而最核心的 AgentSession（turn 循环）在一个 165KB 的大文件里——这是「核心难啃，但边界清晰」的典型结构。

形式化

① 运行时装配：agent-session-services.ts

这是「服务怎么被组装起来」的入口。核心逻辑（已精简）：

ts
const modelRuntime = await ModelRuntime.create({
  authPath: join(agentDir, "auth.json"),
  modelsPath: join(agentDir, "models.json"),
});
const settingsManager = SettingsManager.create(cwd, agentDir);
const resourceLoader = new DefaultResourceLoader({ cwd, agentDir, settingsManager });
await resourceLoader.reload();  // 加载扩展
// 扩展声明的 provider / 虚拟模型，注册进 modelRuntime
for (const { name, config } of runtime.pendingProviderRegistrations) {
  modelRuntime.registerProvider(name, config);
}
await modelRuntime.refresh({ allowNetwork: false });

三个要点：

💡
  • ModelRuntime 读 auth.json（认证）和 models.json（模型配置），正是第 5 课说的 providers。
  • ResourceLoader.reload() 加载扩展，扩展可以注册 provider（第 5 课的「Providers 靠扩展」由此而来）。
  • 这一切完成后，才 createAgentSession(...) 组装会话。

② 消息/entry 类型：messages.ts

会话树上的节点，在代码里就是这些消息类型：

ts
export interface BashExecutionMessage {
  role: "bashExecution";
  command: string;
  output: string;
  exitCode: number | undefined;
  cancelled: boolean;
  truncated: boolean;
  fullOutputPath?: string;
  excludeFromContext?: boolean; // !! 前缀：不进 LLM 上下文
}
export interface BranchSummaryMessage { role: "branchSummary"; summary: string; fromId: string | null; }
export interface CompactionSummaryMessage { role: "compactionSummary"; summary: string; tokensBefore: number; }
export interface CustomMessage<T> { role: "custom"; customType: string; content: ...; display: boolean; }

注意 CompactionSummaryMessage.tokensBefore：压缩摘要记录了压缩前有多少 token——这正是第 4 课「压缩不删原始记录」的数据佐证。

③ active branch → LLM 上下文：convertToLlm

第 4 课说「模型只接收 active branch」，具体怎么转？就在这个函数——把内部消息翻译成各家 LLM 能吃的格式：

ts
export function convertToLlm(messages: AgentMessage[]): Message[] {
  return messages.map((m) => {
    switch (m.role) {
      case "compactionSummary":
        return { role: "user", content: [COMPACTION_SUMMARY_PREFIX + m.summary + COMPACTION_SUMMARY_SUFFIX] };
      case "branchSummary":
        return { role: "user", content: [BRANCH_SUMMARY_PREFIX + m.summary + BRANCH_SUMMARY_SUFFIX] };
      case "bashExecution":
        return { role: "user", content: [bashExecutionToText(m)] };
      case "system": case "user": case "assistant": case "toolResult":
        return m; // 直接透传
      default: return undefined;
    }
  }).filter((m) => m !== undefined);
}

关键洞察：压缩摘要、分支摘要、bash 执行，统统被转成 role: "user" 消息，用 <summary>...</summary> 或文本包裹后塞进上下文。也就是说，「摘要」对模型而言只是一条精心包装的 user 消息，没有任何魔法。

④ 工具注册表：tools/index.ts（一个必须澄清的点）

ts
export type ToolName =
  "read" | "bash" | "powershell" | "edit" | "write" | "grep" | "find" | "ls";

// 核心「四件套」
export function createCodingToolDefinitions(cwd, options): ToolDef[] {
  return [read, bash, edit, write];
}
// 只读集
export function createReadOnlyToolDefinitions(cwd, options): ToolDef[] {
  return [read, grep, find, ls];
}
⚠️

一个需要修正的表述：Pi 源码里内置的是 8 个工具（read/bash/powershell/edit/write/grep/find/ls）。所谓「核心四件套」指的是 createCodingToolDefinitions 返回的 4 个 coding 工具（read/bash/edit/write）；另有 grep/find/ls 作为只读发现工具，powershell 用于 Windows。面试时说「Pi 核心只有四个工具」要补一句「指的是 coding 四件套，另有只读发现工具」。
