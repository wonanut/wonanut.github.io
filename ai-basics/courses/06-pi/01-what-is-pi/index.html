Pi 是什么

极简 harness 的哲学与架构：核心小到你能真正掌控

💡

为什么

大多数「AI 编程助手」是一个黑盒：功能很多，但你不知道它内部在干什么，也很难改它。对专业工程师来说，黑盒意味着三件事都做不了：

  1. 推理失败模式——它为什么改坏了文件？你在一条不可见的状态链上猜。
  2. 审计与验证——你无法确认「它只做了它该做的」。
  3. 安全扩展——想加一个权限门禁，发现没有可挂接的接口，只能靠祈祷。

Pi 反其道而行：它是一个刻意做小的 harness（Agent 运行时）。核心只有四样：

  1. 一个循环：模型调用工具 → 工具执行 → 结果回填 → 模型继续；
  2. 四个工具：read / write / edit / bash；
  3. 一个终端界面（TUI）；
  4. 一套会话管理（树状分支 + 压缩）。

其余能力——子 Agent、MCP、权限门禁、计划模式、后台任务、任务清单——默认都不内置，要用扩展（extension）自己加。

✨

Pi 的哲学一句话：核心小到你能真正理解它、掌控它、改造它。它不是一个「密封的完整助手」，而是一个「你可以重塑的最小核心」。

🖼️

可视化

两种设计取向，本质是「能力放在哪」：

💡
  • 「大而全」的助手：把能力做进产品核心，开箱即用，但内部复杂、难改造、行为不完全可预测。
  • Pi 的极简 harness：核心只提供「最小循环 + 最中性的四个工具」，把能力放到可插拔的扩展里，按需加载。

这不是「谁更好」，而是能力 vs 可控性的取舍。你越想让核心可审计、可验证、可安全改造，就越该把它做小。第 6 课会用它和 Claude Code 做一次完整对比。

🧮

形式化

先给 harness 下一个可操作的定义。harness 是 Agent 的运行时循环：

💡

harness = 模型调用 + 工具分发 + 结果回填 + 循环，直到模型不再请求工具、给出最终回复。

更精确一点，一轮 turn 是这样的（while 直到模型停止调工具）：

text
loop:
  1. 组装当前 active branch 的消息，调用模型
  2. 若模型返回 tool_call → 分发到对应工具执行
  3. 把 tool_result 作为新消息回填
  4. 回到 loop，继续调用模型
  5. 若模型返回纯文本回复 → 结束，呈现给用户

在架构上，这个循环由几个职责单一的模块支撑，面试时能说出来是加分项：

💡
  • SessionManager：管理会话树（分支、leaf 指针、压缩），决定「喂给模型的 active branch 是什么」。
  • SettingsManager：管理配置与模型（~/.pi/agent/models.json）。
  • 模型适配层（provider adapter）：把统一的「工具调用协议」翻译成各家 API 的具体格式（OpenAI / Anthropic / Google / …）。
  • 工具执行层（tool executor）：每个工具暴露一个 *Operations 接口，把「工具逻辑」和「I/O 底座」解耦。

一个面试高频考点：harness、agent framework、orchestrator 三者区别。一句话版——harness 是「模型 + 工具的运行时循环」；agent framework 在 harness 之上加了规划/记忆/多步编排；orchestrator 更关注多 Agent 的调度与协作。Pi 故意只做第一层。

🛠️

动手

bash
curl -fsSL https://pi.dev/install.sh | sh
