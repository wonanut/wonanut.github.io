为什么需要 RAG

模型的知识边界在哪里，长上下文、微调与 RAG 各自解决什么问题

💡

为什么

前四门课回答的是「模型怎么工作、怎么用、怎么做事」。但它们都默认一件事：答案所需的材料已经在你手里，或者模型本来就会。

真实工作里这两个前提经常不成立：

  • 公司的接口文档、会议记录、工单历史，模型从没见过；
  • 模型的知识停在训练截止那天，新政策它不知道；
  • 问它没有依据的问题，它不会说「我不知道」，而是编一个看起来合理的答案——这就是幻觉。

RAG（Retrieval-Augmented Generation，检索增强生成）解决的就是这件事：回答之前，先去你的资料库里把相关材料找出来，再让模型基于材料回答。

✨

一句话：RAG 不改模型，它改的是模型看到的上下文。

🖼️

RAG = 检索（找材料）+ 增强（拼上下文）+ 生成（基于材料回答）

整条链路可以分成四个阶段，每一阶段都可能成为瓶颈：

💡
  1. 索引（离线）：把文档切成块，编码成向量，存进索引。文档更新时要重建。
  2. 检索（在线）：把问题编码成向量，找最相近的块。
  3. 拼装：按相关度排序、编号、塞进上下文预算。
  4. 生成：模型基于材料回答，并给出引用。

常见误区是只盯第 4 步。实际上，「答错了」八成是第 1 或第 2 步就没把对的材料找回来——模型拿到的是错的上下文，再聪明也答不对。

🧮

形式化

RAG 想最大化的是给定问题与检索材料时答案正确的概率：

P(y∣x,D)其中D=top⁡k({d:sim⁡(q,d)})P(y \mid x, \mathcal{D}) \quad \text{其中} \quad \mathcal{D} = \operatorname{top}_k\left(\left\{d : \operatorname{sim}(q, d)\right\}\right)P(y∣x,D)其中D=topk​({d:sim(q,d)})

拆开看有两个上界：

  • 检索上界：如果正确的块根本没进 D\mathcal{D}D，生成阶段无解。这就是召回率（recall） 为什么是 RAG 的第一指标。
  • 生成上界：材料在上下文里，模型也可能看漏、看错、或过度发挥。这是忠实度（faithfulness） 要解决的问题。

三种「让模型知道新知识」的方案，边界很清楚：

💡
  • 长上下文直接塞材料：实现最简单，适合材料少、单次问答、不常变的场景；缺点是每次都要付 token 成本，材料一多就超窗口，也容易「大海捞针」失败。
  • 微调（fine-tuning）：把知识写进权重。适合稳定的风格、格式、领域语感；不适合频繁更新的事实型知识——改一条就要重训，且难以溯源。
  • RAG：知识留在外部，按需检索。更新就是更新文档，答案可以带引用，权限也能跟着文档走。代价是多了一套索引与检索工程。

工程上通常不是三选一：RAG 管事实与更新，微调管风格与格式，长上下文兜住少量临时材料。

⚠️

RAG 不能消灭幻觉，只能把幻觉从「凭空编」变成「引用错材料」。没有评测的 RAG 系统，只是把不确定性换了个位置。

🛠️

动手

先给自己的场景做一次选型，不要上来就搭向量库。回答三个问题：

text
1. 知识规模：几十页 / 几千页 / 百万级？
2. 更新频率：几乎不变 / 每周 / 每天 / 实时？
3. 答案类型：查找具体事实 / 跨文档归纳 / 需要推理？

经验判断：
- 几十页 + 不常变      → 长上下文直接塞，别上 RAG
- 几千页 + 定期更新    → RAG（先做最小可评测版本）
- 风格/格式要统一      → 微调与 RAG 组合
- 需要引用与权限隔离   → RAG 几乎是唯一选择

再写下你的第一条验收标准。不要写「答得准」，要写成可测的句子，例如：

✨

在 30 条人工标注的问题上，正确材料出现在检索结果前 3 块中的比例 ≥ 90%，且回答中每一句事实性陈述都能在引用块里找到依据。

这条标准会贯穿整门课：后面每讲一个参数，都要回到「它能不能被这条标准检验」。

要点回顾

  • RAG = 检索 + 增强上下文 + 生成，不改模型。
  • 四个阶段：索引（离线）、检索、拼装、生成；答错先查检索。
  • 长上下文、微调、RAG 各有边界，工程上常常组合使用。
  • 验收标准要可测：召回率 + 忠实度，而不是「答得准」。
