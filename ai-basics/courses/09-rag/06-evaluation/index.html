L2第 6 课

评测与工程化

把「答得准」拆成可测指标：召回、排序、忠实度与回归门禁

💡

为什么

RAG 的失败有一个讨厌的特点：它看起来像模型的错，其实是检索的错。

用户反馈「答得不准」，你可能去改提示词、换更大的模型，结果毫无改善——因为正确的材料根本没进上下文。没有评测，你只能靠感觉调参，而且每次改动都可能悄悄弄坏别的场景。

这一节做两件事：

  1. 把「答得准」拆成检索指标与生成指标，分别测；
  2. 建一套小而稳的回归评测，让每次改动都有依据。
🖼️

可视化

评测系统分成两条独立的管线，任何一条挂了都能定位到具体环节：

💡
  • 检索评测（离线，不需要生成）：给定问题 + 人工标注的正确块，计算召回与排序指标。改切分、嵌入、top-k、rerank 都看这一条。
  • 生成评测：给定问题 + 正确材料，检查回答是否忠实、是否回答了问题。改提示词、模型、拒答规则都看这一条。
  • 端到端评测：真实检索 + 真实生成，度量用户最终体验；它变差时，用前两条定位是检索还是生成的问题。

调大 k：召回通常会上升，但 precision 会被更多噪声稀释；MRR 只关心第一个命中，k 超过首个命中位置后不再变化。

这里的 4 个查询、8 个块是玩具数据；真实评测集通常 30–100 条，每个问题人工标注正确的块 ID，再跑同一套指标做回归门禁。

同一套标注下拖动 k、开关 rerank，观察四项指标怎么一起变化：单个指标好看不代表系统好，要结合召回与排序分开看。

再回到真实工程：一个最小可用的评测脚本长这样：

text
# eval_set.jsonl 每行一条：
# {"question": "...", "gold_chunk_ids": ["..."], "gold_answer": "..."}

for case in load("eval_set.jsonl"):
  chunks = retrieve(case.question, k=10)
  retrieved_ids = [c.id for c in chunks]

  # 检索指标
  hit = any(i in retrieved_ids[:5] for i in case.gold_chunk_ids)
  recall_at_k = len(set(retrieved_ids[:5]) & set(case.gold_chunk_ids)) / len(case.gold_chunk_ids)
  mrr = 1 / (1 + index_of_first_gold(retrieved_ids))

  # 生成指标（LLM-as-judge 或人工）
  answer = generate(case.question, chunks[:5])
  faithful = judge_faithfulness(answer, chunks[:5])   # 每句是否有材料支撑
  relevant = judge_relevance(answer, case.question)

  record(hit, recall_at_k, mrr, faithful, relevant)

print(aggregate("metrics.json"))
⚠️

LLM-as-judge 不是免检牌。同一个模型既当运动员又当裁判会有偏好；judge 的提示要固定、要抽样人工复核，且每次评测记录 judge 模型版本。

🧮

形式化

检索指标（设正确块集合为 GGG，检索结果为前 kkk 个 RkR_kRk​）：

recall@k=∣Rk∩G∣∣G∣precision@k=∣Rk∩G∣k\text{recall@}k = \frac{|R_k \cap G|}{|G|} \qquad \text{precision@}k = \frac{|R_k \cap G|}{k}recall@k=∣G∣∣Rk​∩G∣​precision@k=k∣Rk​∩G∣​MRR=1∣Q∣∑q∈Q1rank⁡qnDCG@k=DCG@kIDCG@k\text{MRR} = \frac{1}{|Q|}\sum_{q \in Q} \frac{1}{\operatorname{rank}_q} \qquad \text{nDCG@}k = \frac{\text{DCG@}k}{\text{IDCG@}k}MRR=∣Q∣1​q∈Q∑​rankq​1​nDCG@k=IDCG@kDCG@k​
  • recall@k 回答「正确材料有没有被捞回来」，是 RAG 的第一指标；
  • MRR 关心「第一个正确结果排多靠前」，适合只有一个正确答案的场景；
  • nDCG 支持多级相关性（很相关 / 部分相关 / 不相关），适合排序质量评估。

生成指标：

  • faithfulness：回答中的事实性陈述被材料支撑的比例；
  • answer relevance：回答是否切题，而不是答非所问；
  • citation accuracy：引用的编号是否真的支撑对应句子；
  • refusal correctness：材料不足时是否正确拒答，材料充足时是否避免了过度拒答。
💡

评测集怎么建（比指标更重要）：

  1. 从真实用户问题里抽样，覆盖高频、长尾、模糊、拒答四类；
  2. 每个问题标注正确的块 ID（不是整篇文档）与参考答案要点；
  3. 规模 30–100 条即可起步，关键是稳定——每次改动都跑同一套；
  4. 线上出现新失败案例，脱敏后补进评测集，让它随系统一起成长。

失败分类表能直接指导下一步改什么：

| 现象 | 大概率原因 | 优先检查 | |---|---|---| | 正确块不在前 10 | 切分 / 嵌入 / 查询表达 | 检索指标、切分实验 | | 正确块在前 10 但没进前 5 | 排序能力不足 | rerank、混合检索 | | 进上下文但答案错 | 拼装 / 提示 / 模型 | 生成评测、拒答规则 | | 答案对但引用错 | 编号与拼装 | citation accuracy | | 旧答案 | 索引未更新 | 索引同步任务 | | 时好时坏 | judge 或数据不稳定 | 固定随机性、复核评测集 |

⚠️

回归门禁：把 recall@5 与 faithfulness 设成阈值（例如 recall@5 ≥ 0.9、faithfulness ≥ 0.95），每次改动跑评测，低于阈值不允许上线。小样本的指标波动很大，阈值要留余量，并报告样本数。

🛠️

动手

建一个 30 条的最小评测集，跑通一次完整评测：

  1. 选题：从你场景里挑 30 个问题——15 个高频、5 个模糊、5 个跨文档、5 个应该拒答。
  2. 标注：每条写下正确的块 ID（或至少正确文档 + 段落）与参考答案要点。
  3. 跑基线：记录 recall@5、MRR、faithfulness、refusal correctness 四项。
  4. 做一个改动（例如加 rerank），再跑一次，对比四项指标。

最后建立你的上线门禁：

text
# .rag-eval/gate.yaml
dataset: eval_set.jsonl
thresholds:
recall@5: 0.90
mrr: 0.75
faithfulness: 0.95
refusal_correctness: 0.90
on_failure: block_merge        # 低于阈值不允许上线
report: metrics.json + 失败样例清单
✨

评测的目的不是刷分，而是知道每次改动在改善什么、破坏什么。一个只有 30 条但稳定的评测集，比一个 500 条但没人维护的评测集有用得多。

要点回顾

  • 检索与生成分开评测：recall@k / MRR / nDCG vs. faithfulness / relevance / citation。
  • 评测集从真实问题来，30–100 条稳定起步，持续补充失败案例。
  • 失败分类表把现象映射到该改的环节。
  • 回归门禁让每次改动有据可依，阈值要留小样本波动余量。
