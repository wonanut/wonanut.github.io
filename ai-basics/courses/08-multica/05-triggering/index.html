L0第 5 课

怎么把活交给它：六种触发方式

分配、@提及、对话、快捷操作、工作流、自动化——先看要做什么，再选入口

💡

为什么

Multica 里一个反复出现的困惑是：「我 @ 了它，它为什么没动？」

答案通常不是 bug，而是入口选错了。Multica 有六种把工作交给智能体的方式，它们触发的对象、产生的记录、拿到的上下文都不一样。选错入口，要么它不动，要么它动了但你没看到记录。

💡

先看你想让智能体做什么，再选方式——而不是反过来先想「我该怎么叫醒它」。

🖼️

可视化

六种方式，按意图归类：

text
你想做什么                         用什么
─────────────────────────────────  ──────────────────────────────
让智能体负责一条任务               把任务分配给智能体或小队
请求帮助，保留原负责人             评论中 @智能体，或回复它的评论
经常发同一类请求                   保存成快捷操作（如代码审查）
按固定步骤交给不同处理人           为项目配置工作流
问一个问题，不需要新建任务         与智能体开始对话
按时间/外部事件做重复性工作        创建自动化

把这六种和「产生什么记录」对齐，差异就清楚了：

text
入口        产出         记录在哪          典型场景
──────────  ───────────  ───────────────  ────────────────────
分配任务    运行          任务时间线        要有人负责到交付
@提及       运行          评论线程          临时搭把手，不动负责人
对话        运行          对话记录          问问题、试想法
快捷操作    运行          任务内            高频同质请求
工作流      运行          项目/任务         多步骤交接
自动化      任务 或 运行  自动化运行历史    日报、巡检、Webhook

注意最后一行：自动化有两种输出模式，这个区别很实际——「创建任务」模式会先建任务再分配，讨论和状态都留在任务里；「仅运行」模式直接创建运行，不产生任务，结果只能在自动化的运行历史里看。

🧮

形式化

几个必须记住的触发规则，它们解释了绝大部分「它没动」：

规则一：分配 ≠ 一定触发。 backlog 状态的任务，分配本身不会触发智能体。移出 backlog 才会开始执行。小队也一样。

规则二：@ 是一种触发，不是通知。 纯文本 @name 不会触发任何人——必须是真正的 mention 链接。系统给的花名册里带的是可直接复制的 markdown：

text
[@Lambda](mention://agent/<uuid>)   ← 真正的提及，会触发
@Lambda                            ← 纯文本，不会触发任何人

规则三：名不是 id。 所有 --*-id 参数和 mention 链接都要真实 UUID（来自对应 list --output json）。用显示名，或者编一个格式正确但不存在的 UUID，失败信息会看起来像权限错误——然后你去排查访问权限，其实问题在 id。

规则四：只想留言不想叫醒它，用 /note。 发送评论前，输入框下方有触发预览，会告诉你这条评论会触发谁。

规则五：你只能调用自己有权限运行的智能体。 也就是 Access 允许你的那些。

还有一种和时间有关的触发，容易和自动化混淆：

💡
  • 自动化 Autopilot：按时间表或 Webhook 开始新的工作，每次可新建任务。
  • 任务唤醒 Wakeup：让智能体在某个时间、或任务上发生某件事之后，回到已有的那条任务接着做。

想让日报每天自己跑 → 自动化。想让某条任务等 CI 通过后再继续 → 唤醒。

自动化的「仅运行」模式还有一条硬规则：它要求触发时运行时可用，否则本次运行直接显示「已跳过」，不会留下一个等待中的任务。而「创建任务」模式和普通任务走同一个队列，运行时离线时照样先建任务、排队等上线。

🛠️

动手

用 CLI 走一遍「分配 → 观察 → 追加」的完整协作，重点在第 4 步。

bash
# 1. 拿到真实的 id（不要用显示名）
multica workspace list --output json
multica issue list --output json | head -40

# 2. 建任务并直接分配给智能体
multica issue create --title "验证触发方式" \
  --description "读一下 README，列出三个上手步骤" \
  --assignee "Lambda"

# 3. 看运行是否被创建
multica issue get <issue-id>

# 4. 在评论里 @ 另一个智能体（不改负责人）
#    界面：输入框下方确认触发预览，再发送
#    CLI：mentions 必须用 mention://agent/<uuid> 形式

# 5. 反向验证：只留一条不触发任何人的备注
#    评论加 /note 前缀
✨

第 4 步之后去看两个地方：任务右侧的执行日志会多一行新的运行（触发来源写着评论提及），而任务的负责人没变。这就是「@ 提及 ≠ 分配」的实证。

再做一个实验，体会「backlog 不触发」：

bash
# 把任务放进 backlog，再分配
multica issue status <issue-id> backlog
multica issue assign <issue-id> --to "Lambda"
# 观察：不产生运行

# 移出 backlog
multica issue status <issue-id> todo
# 观察：运行被创建
⚠️

--output json 写 stdout，警告与确认走 stderr。解析时不要加 2>&1——那会把成功的写入读成失败，然后触发重复重试。

要点回顾

  • 六种入口：分配、@提及、对话、快捷操作、工作流、自动化；另外有任务唤醒负责「回到旧任务」。
  • 纯文本 @ 不触发；必须用 mention 链接；/note 只留言不叫醒。
  • backlog 不触发；名不是 id；只能调用 Access 允许你的智能体。
  • 自动化「仅运行」要求运行时在线，「创建任务」走普通队列。
