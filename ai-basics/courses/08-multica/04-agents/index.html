L0第 4 课

智能体：配置、Access、Skill

智能体是一份配置而不是进程；它由什么组成、谁能运行它、skill 怎么复用

💡

为什么

第 2 课说智能体是一份「可复用的配置」。这一课把它拆开看：配置里到底有什么，决定了它干活的质量。

这件事值得认真对待，因为团队里最常见的翻车不是模型不行，而是配置写得含混：

💡

你把「修一下登录的 bug」派给一个指令只写着「你是一个有用的助手」的智能体，然后抱怨它做得不好——问题不在模型，在于你从没告诉它边界和交付要求。

Multica 把「这名智能体是谁」写成指令，把「这类工作怎么做」写成 skill，两者分开维护、分别复用。理解这个分工，是把智能体从「一次性的聊天对象」变成「团队资产」的关键一步。

🖼️

可视化

一份智能体配置由七块组成，可以按「身份 / 能力 / 执行」三组来记：

text
身份层
  名称、头像、描述      团队知道它是谁、适合做什么
                         （描述只用于展示，不进入执行提示）
  指令                  职责、工作方式、边界、交付要求
                         （每次执行都会使用）
  对话开场建议          最多三条示例，选择后只填入输入框不发送

能力层
  Skills                可复用的方法、参考资料、支持文件

执行层
  运行时、模型、思考强度  在哪台电脑、用哪个工具和模型；部分工具还可选速度档
  Access                哪些成员可以运行它
  执行配置              并发上限、环境变量、CLI 参数、MCP、外部集成

这里有一个重要属性：换模型或改指令不会创建新智能体。过去的任务、评论、执行记录都还在。智能体的身份是稳定的，配置是可迭代的。

🧮

形式化

先看指令与 skill 的分工，这是本节的核心区分：

text
           智能体指令                    Skill
         ─────────────────           ────────────────────────────
适合保存   长期不变的职责、边界、      某类工作可复用的步骤、
           交付要求                    资料和工具
使用范围   只属于一名智能体，          可添加给多名智能体，
           每次执行都提供              可单独启用/停用
例子       "只审查前端代码，           "一套无障碍检查清单
            不直接修改"                和报告模板"

再看 Access——它决定谁可以运行这个智能体（分配任务、评论里 @、对话）：

text
Access            谁可以运行
────────────────  ──────────────────────────────────
仅自己            只有智能体 owner（新建时的默认值）
整个工作区        工作区中所有成员
指定成员          智能体 owner + 指定的成员

权限不止「能不能运行」这一维，操作权限是分开的：

text
操作                              谁可以
────────────────────────────────  ─────────────────────────────────
在列表/选择器里看到它            owner、工作区 owner/admin、Access 授权成员
修改配置                         智能体 owner、工作区 owner/admin
修改 Access                       只有智能体 owner
⚠️

工作区 owner / admin 可以查看并管理所有智能体，但不能绕过 Access 运行别人设为「仅自己」的智能体，也不能修改它的 Access。这是刻意的设计：Access 是 owner 的私有控制权。

归档是另一个容易踩的点：

归档会取消该智能体所有尚未结束的运行，包括排队中和进行中的。归档后它不再出现在选择器里，不能被分配或 @，但历史记录保留、之后可恢复。「离线」和「已归档」是两件完全不同的事——离线只是运行时不在，已归档才是不能接活。

Skill 一侧的关键机制是托管来源：

💡

从 GitHub / ClawHub / Skills.sh 导入的 skill 会记住来源，可以「从来源更新」：保留 skill 身份（智能体分配、标签、创建者、创建时间），替换内容（名称、描述、SKILL.md 与全部支持文件）——本地修改会被覆盖。

手动创建、从压缩包导入、从运行时复制的 skill 没有托管来源，不能这样更新，只能重新导入。

🛠️

动手

写一个真正可用的智能体，和写一个敷衍的智能体，差别在指令的结构。先看反例，再看正例：

text
# ✗ 敷衍版
你是一个有用的助手。

# ✓ 结构化版
## 职责
只处理前端代码：React 组件、样式、前端状态管理。

## 边界
- 不修改后端接口和数据库迁移
- 不升级依赖版本
- 改动超过 3 个文件时先停下来汇报

## 交付要求
- 每次改动附一段"改了什么、为什么"的说明
- 跑 pnpm lint 和 pnpm test，把结果贴在评论里
- 在 PR 描述里写清楚回滚方式

然后给它挂一个 skill，验证「指令只属于本人、skill 全员可复用的差别」：

bash
# 从 URL 导入一个已发布的 skill
multica skill import --file ./review-helper.skill

# 看技能是否被多个智能体复用（同一份，不复制）
multica skill list

# 从来源拉取新版本：保留身份，替换内容
multica skill refresh <skill-id>
✨

新建智能体默认是「仅自己」。如果你打算让团队用它，在第一次派活前就把 Access 改好——否则同事看到的只是一个灰掉的选项，还要来问你是不是没配。

🎯

要点回顾

  • 智能体 = 可复用配置：身份、指令、skill、运行时/模型、Access、执行配置。
  • 指令属于一名智能体且每次都用；skill 可复用给多名并单独启停。
  • Access 三档：仅自己（默认）、整个工作区、指定成员；admin 不能绕过。
  • 归档会取消未结束的运行；离线 ≠ 归档。
  • 托管来源的 skill 可从来源更新，本地修改会被覆盖。
