L1第 3 课

一次运行的完整链路

从分配任务到结果写回，中间发生了什么；以及运行状态机的七个状态

💡

为什么

「把任务分配给智能体」在界面上只是一个下拉框加一个回车。但从这一下点击开始，系统里发生了一长串事情：

一次运行会被创建、排队、被某台电脑领走、拉起一个子进程、把工具调用流回来、把结果写回任务。

这串流程值得完整走一遍，原因很实际：卡住的时候，你能一眼看出卡在哪一段。是在排队（没有在线运行时）？在启动（CLI 环境有问题）？还是已经跑起来了但不出结果（智能体本身在绕圈）？三种情况的处理方式完全不同。

🖼️

可视化

先看链路，五个阶段，标注了每一步谁负责。点按钮逐步走一遍，注意每一步「卡住时」的症状对应哪一段：

任务任务提供上下文负责方：任务 / 提出者

任务本身保存工作说明、讨论记录与负责人。分配时，系统再从这里取用该智能体的指令、模型、skill 与运行时配置。

现象：智能体反复追问细节。多半是工作说明太短，或讨论里的关键决定没有被提炼进描述。

1 / 5 · 卡住时先定位是哪一段

把同样的链路画成一张可复制的图：

text
① 任务提供上下文
   任务保存：工作说明、讨论、负责人
   分配后系统取用：该智能体的指令、模型、skill、运行时配置
        │
        ▼
② Multica 创建运行
   运行进入队列；没有在线运行时就在队列里等
        │   （WebSocket 下发唤醒信号，守护进程批量领取）
        ▼
③ 运行时领取这次运行
   你的电脑上的守护进程，调用该智能体配置的 AI 编程工具
        │
        ▼
④ AI 编程工具在本地执行
   读取工作目录、运行命令、生成结果
        │   （心跳每 15s，结果流式回传）
        ▼
⑤ 结果写回任务
   进度、评论、结果显示在任务时间线与执行日志里

注意②③之间的细节：Multica 不是靠「每 30 秒问一次」来派活的。服务端通过 WebSocket 推送唤醒信号，守护进程收到后一次性批量领取；30 秒的轮询只是兜底——信号丢了或连接断了，才靠它兜住。所以正常情况下的取活延迟远低于 30 秒。

🧮

形式化

现在把运行的状态机写清楚。一次运行会在这些状态间迁移：

text
deferred                  已安排稍后触发，到点后进入队列
   │
   ▼
queued                    等待运行时领取
   │                        （运行时离线时停在这里，可能停很久）
   ├──► waiting_local_directory   目标本地目录被另一条执行占用，等锁释放
   ▼
  dispatched              运行时已领取，正在启动 AI 编程工具
   │
   ▼
running                   AI 编程工具正在执行
   │
   ├──► completed          正常结束
   ├──► failed             出错或中断
   └──► cancelled          被手动停止

几个不显然但很关键的规则：

  1. 排队不会让运行过期。 只要运行时还在发心跳（默认 15 秒一次），就说明它只是忙，积压的运行可以一直排下去。
  2. 排队中的运行失败需要两个条件同时成立：绑定的运行时心跳缺席超过重连宽限期，并且这条运行自己排队也满了同样久。第二个条件专门照顾「派给了一台已经休眠的机器」：你有完整的宽限期把机器唤醒。
  3. 心跳正常的长任务不会被服务器强杀。 是否卡住由运行时自己按实际活动判断（默认空闲看门狗 2 小时，工具调用期间另有独立的工具看门狗）。
  4. 派活前已知运行时离线时，部分即时操作会直接提示「当前无法运行」，根本不创建一条没人能领的运行——这比创建一条永远排队的记录更诚实。
⚠️

waiting_local_directory 这个状态容易被误认为卡死。它表示目标本地目录被另一条执行占着锁（比如同一仓库有两个运行同时要写）。等前一条释放就会继续，不是死锁，也不需要你干预。

还有一条边界最容易被忽略，它在读代码时是「设计意图」，在排障时是「踩坑点」：

运行时以无人值守方式跑智能体，所以工具自带的审批会被自动应答。 默认路径下文件系统沙箱也是关的：Codex 用 sandbox_mode = "danger-full-access"，Claude Code 用 --permission-mode bypassPermissions。这不是 bug，是刻意的（见第 6 课安全模型）。

🛠️

动手

用一条真实任务把链路走通，并且刻意制造一次「排队」。

bash
# 1. 确认有哪些运行时在线
multica workspace list
multica daemon status            # 本机的守护进程状态

# 2. 建一个任务，负责人选某个智能体
multica issue create --title "验证运行链路" --description "打印当前工作目录并汇总今天的改动"

# 3. 立刻看执行日志：状态应该是 queued → dispatched → running
multica issue get <issue-id>

# 4. 关键实验：先停掉守护进程，再分配一次
multica daemon stop
#    观察：运行停在 queued，不会失败
multica daemon start
#    观察：几秒内被领取，而不是等满 30 秒
✨

第 4 步是整个实验的核心。它同时验证了两件事：离线不丢活，以及取活靠信号不靠轮询。如果你看到启动后几乎是瞬间被领取，说明唤醒信号链路是通的。

如果想看运行到底做了什么，打开执行日志里某次运行的「查看记录」：智能体的消息、每一次工具调用和报错都带时间戳，运行未结束时内容还会实时追加。

要点回顾

  • 链路五段：任务提供上下文 → 创建运行 → 运行时领取 → 本地执行 → 结果写回。
  • 取活靠 WebSocket 唤醒信号，30 秒轮询只是兜底。
  • 状态机：deferred → queued → dispatched → running → completed/failed/cancelled。
  • 排队不过期；失败需心跳与自身排队双条件；长任务看心跳不看时长。
