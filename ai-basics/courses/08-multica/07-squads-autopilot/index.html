L0第 7 课

小队、自动化与自托管

让队长按花名册派活、按 cron 或 Webhook 自动开工，以及整套装到你自己的机器上

💡

为什么

到这里你已经能让一个智能体干好一件事。但 Multica 的野心是「两个工程师带一队智能体，有二十个人的推进速度」。

从「一个智能体」到「一支队伍」，缺三块：

💡

小队解决「这条任务该谁接」，自动化解决「没人催也要有人干」，自托管解决「这套东西归谁」。

三块都有各自的坑。小队的坑是以为它会并行；自动化的坑是以为它不会漏；自托管的坑是以为装完就完事。

🖼️

可视化

先看小队。它最容易被误解的一点，直接上图：

text
把任务分配给小队后：
  ✘ 不是同时运行所有成员
  ✔ 先唤醒队长，由它读上下文，决定下一步交给谁

执行流程：
  ① 队长运行时领走运行（不是每个成员各入一条）
  ② 队长拿到 briefing：
       Squad Operating Protocol（硬编码规则，不可编辑）
     + Squad Roster（花名册，每行带可复制的 mention markdown）
     + Squad Instructions（你写的路由规则）
  ③ 队长发一条派活评论，@ 选中成员
       被 @ 的智能体 → 入队一次新运行
       被 @ 的人     → 收到通知
  ④ 队长记录 evaluation：multica squad activity <issue-id> <outcome> --reason "..."
  ⑤ 父任务置为 in_progress（派活≠交付）
  ⑥ 队长停下，不亲自动手

「派完就停」是个好设计：队长只做路由，不做实现。被派成员有回复时队长会被自动唤醒再评估下一步——继续派活、上抛给人、还是在目标达成后把父任务推到 in_review。

done 永远留给人工确认或既有集成（例如带 close intent 的 PR merge）。

🧮

形式化

小队的再次触发规则，这张表能解释「队长为什么又动了 / 为什么不动」：

text
事件                                  触发队长？
────────────────────────────────────  ──────────
非小队成员（人类、外部智能体）发评论  会
小队成员发进展更新，不带任何 @        会
任何评论里显式 @ 了智能体/成员/小队或 @all   不会
队长自己发的评论                      不会
评论里只有任务互链                    会

逻辑是一致的：显式 @ 就是路由信号，队长让位；没有路由信号的变化，队长负责重新评估。另外还有去重——队长在这条任务上已有排队或已领取的运行，新触发不会重复入队。

还有两个边界：队长的 Squad Operating Protocol 里与状态相关的规则只对确实分配给本小队的任务生效。队长被别人任务里的 @小队 唤醒时，同样拿到花名册和派活规则，但会被明确告知不要改动那条任务的状态——状态归那条任务自己的负责人。

自动化的核心契约是一句区分：

text
自动化 Autopilot      按时间/Webhook 开始新的工作，可新建任务
任务唤醒 Wakeup       在某个时间或任务上的事件之后，回到已有的那条任务

输出模式
  创建任务   每次触发先建任务再分配 → 讨论/状态/执行记录都留在任务里
  仅运行     直接创建运行，不产生任务 → 结果只在自动化运行历史里看
             要求触发时运行时可用，否则本次「已跳过」

时间表支持标准 5 字段 cron（分 时 日 月 星期），时区用 IANA 名称如 Asia/Shanghai。一条自动化可以挂多个时间表；单独启停某个触发器要用 autopilot trigger-update。

自托管最省事的两条命令：

bash
curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash -s -- --with-server
multica setup self-host

# Windows：先设 $env:MULTICA_MODE="with-server"，再用 install.ps1

这会拉 GHCR 上的官方镜像，需要 Docker。如果选的标签还没发布，在代码目录里跑 make selfhost-build 兜底。

⚠️

自托管的服务端每天会发一份匿名的部署级快照：只有版本号和分桶计数，不含名称、内容或任何标识符。要关就在 API 服务端设 DO_NOT_TRACK=1。这属于合规上需要知情的一项，别装完才发现。

自托管还有个运维细节：自动更新默认是关的。要让守护进程轮询升级，需要显式打开 MULTICA_DAEMON_AUTO_UPDATE=true，并（可选）指向自己的镜像源 MULTICA_RELEASE_API_BASE_URL / MULTICA_RELEASE_DOWNLOAD_BASE_URL。

🛠️

动手

搭一个最小的小队，观察队长派活，并验证「显式 @ 时队长让位」。

bash
# 1. 建三个智能体（可以用同一个 provider，不同指令）：
#    frontend / backend / test

# 2. 建小队：队长选一个协调型智能体，成员是上面三个
#    角色说明写清楚："frontend 只改 React 组件；backend 只改 API；test 只写测试"

# 3. 小队指令里写路由规则：
#    "凡涉及 .tsx 或样式 → frontend；涉及 handler/service → backend；
#     完成后必须由 test 补一条回归用例"

# 4. 建一条任务，分配给小队（不是分配给某个智能体）
multica issue create --title "给登录页加错误提示" --description "..."

# 5. 观察三件事：
#    ① 只有队长产生运行（不是三个成员同时）
#    ② 队长的评论区里出现带 mention markdown 的派活
#    ③ 父任务变成 in_progress，而不是 done
✨

第 5 步的第①点是本节实验的关键。如果你看到三个成员同时被拉起，那多半是你把任务分配给了三个智能体，而不是一个小队。

接着用 cron 做一条自动化，并故意测「运行时离线」的两种模式差异：

bash
# 建一条每天 9:00 的自动化，输出模式选「创建任务」
# cron: 0 9 * * *    时区: Asia/Shanghai
# 保存前用页面上的「接下来」时间核对

multica daemon stop          # 制造离线
# 手动「立即运行」一次
# 观察：创建任务模式 → 任务已建、运行排队等上线
#      仅运行模式   → 本次显示「已跳过」
multica daemon start

要点回顾

  • 小队只唤醒队长；队长拿 Protocol + Roster + Instructions，派活后停下。
  • 显式 @ 是路由信号，队长让位；去重防止队长重复入队。
  • 自动化 vs 唤醒：开新活 vs 回到旧任务；输出模式决定是否建任务。
  • 自托管：install.sh --with-server + setup self-host；有匿名遥测可关；自动更新默认关。
