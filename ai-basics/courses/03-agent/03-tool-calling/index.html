工具与 Function Calling

模型怎么「调用」工具：JSON Schema、受限采样与错误处理

💡

为什么

上一课的 ReAct 循环里，模型会「调用工具」。但模型只是生成文本——它到底是怎么「调用」一个真实的函数的？

答案是 Function Calling（函数调用）：模型不直接执行任何函数，而是生成一段结构化的 JSON，声明「我想调哪个函数、参数是什么」。真正去执行的是外部的 harness。

打个比方：模型不是那个「按下开关的人」，而是「写下一张『请帮我按下这个开关』的便条」。harness 读到便条，才去按开关，再把结果写回便条递给模型。

理解了这个「模型只写便条、harness 才动手」的分工，就理解了 Function Calling 的全部。它也意味着：模型从来不能越过 harness 直接触碰你的文件、网络或数据库——这是 Agent 安全模型的基础。

🧮

形式化

① 工具是「JSON Schema 声明的函数」

每个工具都有一段 JSON Schema，声明它叫什么、接受什么参数。模型被要求：当需要时，输出符合这个 Schema 的 JSON。例如：

json
// 工具定义（描述给模型看的「说明书」）
{
  "name": "get_weather",
  "description": "查询某个城市的实时天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "城市名" }
    },
    "required": ["city"]
  }
}

// 模型据此输出的 tool_call
{ "name": "get_weather", "arguments": { "city": "北京" } }

② 模型怎么保证 JSON 合法？——受限采样（constrained decoding）

这是面试高频考点。模型是逐 token 生成的，不能保证「恰好输出合法 JSON」。两种做法：

💡
  • Prompt 约束（软）：把 Schema 写进 system prompt，让模型「尽量」遵守。不保证合法，可能漏括号、参数名拼错。
  • 受限采样（硬）：在解码层面强制下一个 token 必须让输出符合语法（grammar-constrained decoding / JSON mode）。保证合法 JSON，但会略降速度、且只对「语法」负责、不保证「语义」正确。

面试答题要点：「软约束保证不了格式，硬约束保证格式但不保证语义」——即使 JSON 合法，city 也可能填一个不存在的城市，所以 harness 执行前还要做语义校验（参数类型、取值范围、路径安全）。

③ 并行工具调用

一条 assistant 消息可以同时带多个 tool_call。比如「查 A、B 两城天气」，模型可以一次发起两个 get_weather，harness 并行执行后一起返回，省一轮往返。这是「省 token、省延迟」的关键优化——但前提是这些调用彼此独立。

④ 工具错误怎么办？

工具会失败：文件不存在、命令非零退出、网络超时。关键设计是：错误也要作为一条 tool_result 喂回模型，让模型自己决定怎么处理，而不是让 harness 直接崩掉。

⚠️

两种哲学：

  • Fail-closed（失败即报错）：工具失败返回 isError: true + 错误信息，模型必须读错误并重试/改方案。Pi 的 bash 就是这种——非零退出码标记为 error（第 6 课源码已确认）。
  • Fail-open（失败也当作正常结果）：把失败信息混在普通输出里，模型可能误判为成功。

面试问「工具失败了 agent 会怎样」，正确答案是：好的 harness 会把失败结构化地喂回，让模型显式感知并恢复，而不是静默吞掉或直接崩溃。

⑤ 工具越多，风险越大

给模型 4 个工具，它大概率选对；给 40 个，它开始选错、传错参数、甚至幻觉出一个不存在的工具名。所以工具集要克制——Pi 只给 4 个 coding 工具，就是这个道理（工具多 ≠ 能力强）。

🛠️

动手

亲手写一个工具的 JSON Schema。任务：给一个 Agent 加一个「发送邮件」的工具 send_email(to, subject, body)。

json
{
  "name": "send_email",
  "description": "发送一封邮件",
  "parameters": {
    "type": "object",
    "properties": {
      "to": { "type": "string", "description": "收件人邮箱" },
      "subject": { "type": "string", "description": "主题" },
      "body": { "type": "string", "description": "正文" }
    },
    "required": ["to", "subject", "body"]
  }
}

现在问自己三个问题（面试官会这么追问）：

💡
  1. 如果模型漏了 to 参数怎么办？—— harness 校验 required 拒绝执行，把「缺少参数」作为错误喂回，让模型补。
  2. to 填了 "12345"（不是邮箱）怎么办？—— Schema 只保证是 string，不保证是邮箱。所以要么在 Schema 里加 format: "email"，要么 harness 执行前再做一层语义校验。
  3. 这个工具「危险」吗？—— 会真实发信，属于「有副作用、难回滚」的工具，应该加权限确认（第 6 课护栏）。

要点回顾

  • Function Calling：模型生成 JSON「便条」，harness 才执行——分工即安全边界。
  • 工具用 JSON Schema 声明参数；软约束保证不了格式，硬约束保证格式不保证语义。
  • 并行 tool_call 省往返，但要求调用彼此独立。
  • 工具错误要结构化喂回（fail-closed），让模型显式恢复。
  • 工具集要克制，多 ≠ 强。
