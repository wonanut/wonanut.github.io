评测与工程化

怎么判断 Agent 好不好：轨迹评测、失败模式与护栏

💡

为什么

前 5 课讲「Agent 怎么造」。这一课讲「Agent 怎么算好」——因为「能跑」和「能上线」是两回事。

Agent 比普通 LLM 应用难评测得多。一个聊天机器人，你给它一句、看一句，好坏一眼便知。但一个 Agent 跑 20 步、调 10 次工具、中间还失败重试了 2 次——「最终答案对了」不等于「这个 Agent 做得好」。它可能绕了远路、多花 10 倍 token、还差点删错文件。

这一课建立一套评估 Agent 的框架：测什么、怎么测、最常见的失败模式、以及上线前必须装的护栏。这是面试里「工程化」和「调包侠」的分水岭。

🖼️

可视化

评估一个 Agent，不能只看「答案对不对」，要看四个维度：

💡
  • 任务成功率（最终正确率）：在 N 个测试任务上，有多少次交付了正确结果。
  • 轨迹质量（过程正确率）：每一步是否合理——工具选对了吗？有没有多余的调用？有没有走到死胡同？
  • 效率（token / 步数 / 延迟）：同样完成一个任务，花了多少步、多少 token。
  • 安全与合规：有没有越权操作、泄露敏感信息、产生不可逆副作用。

其中轨迹质量最容易被新手忽略，但它恰恰是 Agent 独有的评测维度——普通 LLM 没有「过程」可评，Agent 有。

🧮

形式化

① 终点评测 vs 轨迹评测

⚠️
  • 终点评测（只看结果）：给任务，比对最终答案。实现简单，但会漏掉「结果对、过程烂」的 Agent——比如为了改一行代码，把整个文件重写了 10 遍。
  • 轨迹评测（看过程）：逐步评估每一步的 Thought / Action / Observation。能发现「工具选错」「绕远路」「中间出现危险操作」等问题，但标注成本高、需要人工或更强的模型来当「评委」（LLM-as-judge）。

工程上的常见做法是分层：先跑便宜的量大的终点评测做回归，再抽样做轨迹评测抓质量问题。

② Agent 最常见的五种失败模式

💡
  1. 死循环 / 无法终止：模型在「调工具 → 结果不满意 → 再调」里打转，永远不输出 final answer。→ 解法：最大步数、超时强制终止。
  2. 工具误用：调了错误的工具，或传错参数（把 ls 当成 read 用）。→ 解法：工具描述写清楚、失败后让模型读错误重试。
  3. 幻觉工具调用：调一个根本不存在的工具，或捏造参数值。→ 解法：严格校验 schema + 错误喂回。
  4. 过早终止：任务才做一半就宣布「完成」。→ 解法：在 system prompt 里要求「交付前自我核对」，或加一个验证步骤。
  5. 上下文溢出 / 记忆丢失：跑太久，关键信息被压缩掉或挤出窗口，Agent 忘了目标。→ 解法：压缩策略 + 把目标常驻窗口头部。

③ 护栏（guardrails）与权限

Agent 会执行真实副作用（改文件、发请求、删数据），所以上线前必须装护栏：

💡
  • 权限最小化（allowlist）：默认拒绝，白名单放行。比如只允许读写某个目录、只允许 read/grep 这类只读工具。
  • 人工确认（human-in-the-loop）：高风险、不可逆的操作（删除、发送、部署）在执行前暂停，等人类点头。
  • 超时 / 最大步数：兜底，防止死循环烧钱。
  • 只读默认：探索阶段只给只读工具，动手阶段才给写权限（Pi 的 createReadOnlyTools vs createCodingTools 就是这种分层）。

④ 可观测性：出了 bug 怎么查

Agent 的问题几乎都发生在「某一步」。所以必须能回放：

text
# 一条可回放的轨迹（trajectory / trace）
turn 1: user → "修这个 bug"
turn 2: assistant → read("src/app.ts")
turn 3: tool → [文件内容]
turn 4: assistant → edit(...)
turn 5: tool → isError: true  "No changes made"
turn 6: assistant → edit(...)  # 重试
turn 7: tool → 成功
...
💡

面试真题风格：「用户反馈 Agent 没完成任务，你怎么定位？」标准回答：先拿到完整轨迹，定位到「第一次偏离正确路径的那一步」——是工具选错了、结果被误读了、还是中间被压缩丢了信息？然后针对那一步修（改工具描述 / 改 system prompt / 改压缩策略），再用回归集验证。

⑤ 成本：Agent 的每一「步」都是钱

回到第 2、4 课的权衡——Agent 的 token 成本是「步数 × 平均上下文长度」，通常比单次对话高 1~2 个数量级。所以「能省一步是一步」：

💡
  • 能并行就别串行（一次发起多个独立 tool_call）；
  • 能只读探测就别直接大动作（先 grep 定位再 edit）；
  • 规划要与风险匹配（低风险任务别先想 10 步）。
🛠️

动手

给你一条失败轨迹，做一次面试真题诊断。任务：「把 config.js 里的端口从 3000 改成 8080」。

text
turn 1: assistant → read("config.js")
turn 2: tool → "port: 3000, host: localhost, ..."
turn 3: assistant → edit(oldText="3000", newText="8080")
turn 4: tool → isError: true  "Found 3 occurrences. Must be unique."
turn 5: assistant → edit(oldText="port: 3000", newText="port: 8080")
turn 6: tool → 成功

诊断：这不是 bug，而是一个「健康恢复」的例子。第 3 步的 oldText="3000" 不唯一（文件里出现了 3 次），工具 fail-closed 报错；模型读到错误后，在第 5 步加了更多上下文（port: 3000）使匹配唯一，成功。

⚠️

但注意：如果这个 Agent 没有第 5 步的恢复，而是卡在第 3 步反复重试同一个 edit，那就是「死循环」失败模式——需要靠「失败后换策略」的能力或最大步数兜底。这道题的进阶问法是：「如何防止它卡在第 3 步？」 答案：① 工具错误信息里明示「需要更多上下文使其唯一」（Pi 的报错正是这么写的）；② 设置最大重试次数。

要点回顾

  • 评测四维度：成功率 / 轨迹质量 / 效率 / 安全。
  • 终点评测便宜但漏过程问题；轨迹评测能抓「结果对、过程烂」。
  • 五种失败模式：死循环、工具误用、幻觉调用、过早终止、上下文溢出。
  • 护栏：权限最小化、人工确认、超时/步数上限、只读默认。
  • 定位 bug 靠回放轨迹，找「第一次偏离正确路径的那一步」。
