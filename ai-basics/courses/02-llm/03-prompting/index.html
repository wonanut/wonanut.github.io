提示工程

把提示当成程序：六要素、few-shot、CoT 与结构化输出

💡

为什么

同一个模型，换一种问法，输出质量可能差一个档次。这不是玄学，而是因为提示决定了模型看到什么上下文、被约束成什么行为。

把提示当成一段「自然语言程序」会更准确：你负责声明角色、任务、输入、约束和输出格式；模型负责在这个约束下补全。提示写得好，等于给模型一个清晰的接口；写得糊，模型只能猜，猜错就变成幻觉或废话。

这一节的目标不是背「魔法咒语」，而是掌握一套可复用、可调试的提示结构。

🖼️

可视化

一次带示例的提示请求，在系统里是这样流动的：

共 6 步

当前显示全部 6 步

点击图中箭头或下方步骤可互相跳转高亮；聚焦本卡片后用 ← / → 切步、空格播放或暂停。

提示不是直接发给模型的「一句话」，而是应用组装出的完整上下文；输出还要经过解析与校验。

注意链路里有两个容易被忽略的角色：应用负责组装（角色、示例、约束都在这里拼进去），解析器负责兜底（模型输出未必合法）。提示工程不是只写一句 prompt，而是设计这条链路。

🧮

形式化

一个可复用的提示通常包含六要素：

💡
  1. 角色（Role）：你是谁、以什么身份回答，例如「你是资深法务，只依据给定条款回答」。
  2. 任务（Task）：要完成的具体动作，用动词开头，避免含糊的「帮我看看」。
  3. 上下文（Context）：完成任务所需的事实、文档、用户背景；用分隔符与指令隔开。
  4. 示例（Examples）：输入—输出对，展示期望的格式与判断标准（few-shot）。
  5. 约束（Constraints）：不能做什么、边界在哪，例如「不知道就说不知道」「不得编造引用」。
  6. 输出格式（Format）：JSON、Markdown 表格、固定字段；越明确越容易解析。

Few-shot 是用 2–5 个示例把「隐含标准」显式化。示例要覆盖边界情况，且输入输出格式必须一致；示例太单一，模型会过拟合到某种句式。

CoT（Chain-of-Thought） 是让模型先写推理过程再给结论。对数学、多步逻辑、需要权衡的任务通常有效；对简单分类反而可能增加噪音。注意：CoT 的推理文本不一定忠实反映模型真实计算过程，所以不能把 CoT 当作审计证据。

结构化输出解决「模型说了但程序用不了」的问题：要求输出 JSON，最好再配合 JSON Schema 或 function calling 做约束。即便如此，仍要在应用侧校验——模型可能少字段、类型错、或多包一层 Markdown 代码块。

好提示与坏提示的差别，往往是「有没有把隐含要求写出来」：

⚠️
  • 坏：「帮我总结一下这个会议。」——没有长度、对象、格式、用途。
  • 好：「你是项目经理。把下面的会议记录总结成 3 条待办，每条包含负责人和截止日期；若记录未提及负责人，写『待定』。只输出 JSON 数组，字段为 owner、task、due。」
  • 坏：「回答要专业。」——「专业」不可验证。
  • 好：「只引用给定文档中的条款；文档没有的信息回答『文档未提及』。」

但提示不是万能。三个硬边界必须记住：

⚠️
  • 知识截止：模型不知道训练截止后的事实，也不知道你的私有数据；靠检索或工具补。
  • 幻觉：模型会自信地编造引用、API、数字；用「允许说不知道」、引用校验、外部工具降低风险。
  • 提示注入：用户输入或网页内容里若藏有「忽略以上指令」，模型可能照做；要把不可信内容放进明确的数据分隔区，并在应用层限制工具权限。

换句话说：提示能提升概率，不能提供保证。关键业务要有确定性校验与权限边界。

🛠️

动手

把一条坏提示改写成六要素版本。原始需求：「帮我写个产品介绍。」

text
角色：你是面向开发者的技术文案。
任务：为下面的 API 写一段 120 字以内的产品介绍。
上下文：<产品资料>…</产品资料>
示例：输入「日志 SDK」→ 输出「三行代码接入，自动采集…」
约束：只使用资料中的事实；不承诺未提供的性能数字；不确定就不写。
输出格式：一段纯文本，不用标题，不用 emoji。

再进一步，把输出改成可解析的结构：

text
请只输出 JSON：
{"title": "不超过 20 字", "body": "不超过 120 字", "keywords": ["3-5 个"]}
不要输出 Markdown 代码块，不要附加解释。

练习：给「会议纪要 → 待办」任务补上 few-shot 示例，要求覆盖两种情况——记录里明确写了负责人，以及没写负责人。然后思考：如果模型仍然输出多余解释，应用层应该怎么处理？

💡

参考答案：解析器先尝试提取第一个 JSON 对象；失败则用一次「只输出 JSON，不要解释」的修复调用；再失败则降级为纯文本展示并记录日志，而不是把异常直接抛给用户。

要点回顾

  • 提示是自然语言程序：角色、任务、上下文、示例、约束、输出格式六要素。
  • Few-shot 显式化标准；CoT 帮助多步推理但解释未必忠实；结构化输出要配合校验。
  • 好提示把隐含要求写出来，且要求可验证。
  • 提示有硬边界：知识截止、幻觉、提示注入；靠检索、工具、校验与权限兜底。
