L1第 5 课

Function Calling

模型只提议调用，harness 负责校验与执行：一次完整工具往返

💡

为什么

模型本身不能执行任何代码、不能访问网络、不能查数据库。它能做的，是生成一段结构化的「调用意图」：函数名加 JSON 参数。真正执行的是外面的应用（harness）。

这个分工是理解 Agent 的关键：

  • 模型负责理解意图、选择工具、填参数；
  • 应用负责校验参数、检查权限、真正执行、把结果喂回；
  • 模型再根据结果，决定继续调用还是给出最终回答。

把 Function Calling 当成「模型会调用函数」是危险的误解。准确说法是：模型会输出一个符合 schema 的调用请求，是否执行、如何执行由你决定。

模型只输出调用意图；应用校验并执行工具，再用 tool_call_id 把结果回填给模型。

注意中间那一步：应用可以先拒绝。参数不合法、用户没权限、工具不存在，都不应该盲目执行。模型提议，应用决策。

🧮

形式化

工具通过 JSON Schema 描述。一个天气工具大致长这样：

text
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询指定城市的当前天气",
    "parameters": {
      "type": "object",
      "properties": {
        "city": { "type": "string", "description": "城市名，如 北京" },
        "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }
      },
      "required": ["city"]
    }
  }
}

模型看到的不是函数实现，而是这份 schema。schema 写得越清楚，模型选错工具、填错参数的概率越低。description 不是装饰，它是模型判断「何时用这个工具」的主要依据。

模型返回的调用意图通常长这样：

text
{
  "role": "assistant",
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": { "name": "get_weather", "arguments": "{\"city\":\"北京\"}" }
    }
  ]
}

注意 arguments 往往是一个 JSON 字符串，需要先解析；不同厂商的字段名略有差异，但结构类似。应用的循环是：

text
1. 发送 messages + tools 给模型
2. 若返回 tool_calls：
   a. 逐个解析 arguments 并做 schema 校验
   b. 检查权限、业务规则、是否需要用户确认
   c. 执行工具（可并行），捕获异常
   d. 追加 role=tool 消息，带 tool_call_id 与结果
3. 再次调用模型
4. 直到模型返回普通文本或达到步数上限

并行调用：模型可以在一条 assistant 消息里返回多个 tool_calls，例如同时查北京和上海。应用应并发执行，并为每个调用各回填一条 role=tool 消息，tool_call_id 必须一一对应。顺序错配会让模型把结果张冠李戴。

错误回填：工具失败时不要把异常直接抛给用户，也不要把空结果当成功。应返回结构化错误，例如 {"error": "CITY_NOT_FOUND", "retryable": false}，让模型决定是改写参数重试、换工具，还是向用户解释。

⚠️

参数校验至少三层：

  • 语法层：JSON.parse 是否成功，字段类型是否符合 schema；
  • 业务层：城市是否存在、日期是否合理、金额是否超限；
  • 权限层：当前用户能否执行这个操作，副作用操作是否需要二次确认。

永远不要相信模型填的参数：它可能编造城市、传错类型、甚至被提示注入诱导调用高危工具。执行侧要遵循最小权限，写操作要幂等（idempotency key），并对超时与重试设上限。

🛠️

动手

给一个「查订单」工具写 schema，并走一遍往返。先定义工具：

text
{
  "name": "get_order",
  "description": "按订单号查询订单状态",
  "parameters": {
    "type": "object",
    "properties": { "order_id": { "type": "string" } },
    "required": ["order_id"]
  }
}

用户问「订单 123 到哪了」。模型返回 get_order 调用后，应用执行并回填：

text
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "{\"status\":\"shipped\",\"carrier\":\"顺丰\",\"eta\":\"2026-11-02\"}"
}

模型据此回答：「已发货，顺丰承运，预计 11 月 2 日送达。」

练习：

  1. 如果 order_id 传成了数字而不是字符串，应用应该怎么处理？
  2. 如果工具返回 500 超时，回填什么内容最有利于模型恢复？
  3. 用户说「把订单 123 取消掉」，这是副作用操作，应用在调用 cancel_order 前还应做什么？
💡

参考：1 先做类型转换或直接返回 INVALID_ARGUMENT，不要静默猜；2 返回 {"error":"UPSTREAM_TIMEOUT","retryable":true}，让模型决定重试或告知用户；3 必须做权限校验与用户二次确认，并保证取消操作幂等。

要点回顾

  • 模型只提议：输出函数名加 JSON 参数；harness 负责校验、权限与执行。
  • 工具用 JSON Schema 描述，description 直接影响模型的选择。
  • 一次往返：模型 → tool_calls → 应用执行 → role=tool 回填 → 模型 → 最终回答。
  • 并行调用要一一对应 tool_call_id；错误要结构化回填；参数至少做语法、业务、权限三层校验。
  • 最小权限、幂等与超时控制是生产环境的底线。
