Token 与上下文窗口

模型按 token 读写、按 token 计费，窗口是一份必须精打细算的硬预算

💡

为什么

大模型不直接读字符，它读的是 token：一段文本先被分词器切成 token，再映射成整数 id，模型只处理这些 id。这个事实带来三个直接影响：

  1. 计费：API 按输入/输出 token 数收费，不按字数；
  2. 限长：上下文窗口（context window）是硬上限，超了请求直接失败；
  3. 延迟：token 越多，prefill 与生成越慢。

所以「怎么把模型用好」的第一课，不是提示词技巧，而是建立 token 预算意识。很多人以为窗口是「能存多少聊天记录」，其实它是一个所有东西共享的总预算。

✨

记住一句话：token 是模型的计价单位，也是它的工作记忆单位。 你写的每个字、每段历史、每个工具返回，最终都要折算成 token。

🖼️

可视化

下面的玩具分词器把窗口故意缩小到 8 个 token，方便你直观看到「预算被谁吃掉」。输入中文、英文、标点，观察 token 数量与 id，以及进度条何时变红。

你好#7，#8世界#9

ids: [7, 8, 9]

上下文窗口预算已用 3 / 8 tokens

窗口是硬预算：system prompt、历史对话、工具结果、本次输出都要挤在这条进度条里。

⚠️

这是教学用的简化分词器（按词与标点切分），不是真实大模型的 BPE/子词分词器。真实模型的 token 边界更碎、词表更大；窗口设为 8 也只是为了在几行文本内观察溢出，真实窗口通常是几万到上百万 token。

试试这些输入，感受 token 与「字数」的差异：

  • 你好，世界：中文字符、标点各自可能占 token；
  • hello world：常见英文词通常更「省」；
  • unbelievable：真实 BPE 可能拆成 un + believ + able；
  • 一长串数字或罕见符号：往往比你想的更费 token。
🧮

形式化

BPE 的直觉：Byte Pair Encoding 从字符/字节开始，反复统计相邻 pair 的频率，把最高频的一对合并成新 token，直到词表达到目标大小。

text
初始: l o w e r
高频对: (e, r) -> er
合并: l o w er
继续: (l, o) -> lo, (lo, w) -> low
结果: low + er 两个 token

这解释了两件事：高频片段会被压成一个 token（所以常见词省 token），罕见词会被拆成多个子词（所以模型仍能处理没见过的词）。词表（vocabulary）就是所有 token 的集合，每个 token 对应一个整数 id；模型内部只认 id。

上下文窗口是硬预算。一次请求里，下面四类内容都算进同一个窗口：

nsystem+nhistory+ntools+noutput≤Cn_{\text{system}} + n_{\text{history}} + n_{\text{tools}} + n_{\text{output}} \le Cnsystem​+nhistory​+ntools​+noutput​≤C

其中 CCC 是模型的最大上下文长度。注意 输出也算预算：很多 API 要求你预留 max_tokens，输入 + 输出不能超过 CCC。工具返回的 JSON、检索到的文档、图片转成的 token，同样占额度。

token 成本可以粗略写成：

cost≈nin×pin+nout×pout\text{cost} \approx n_{\text{in}} \times p_{\text{in}} + n_{\text{out}} \times p_{\text{out}}cost≈nin​×pin​+nout​×pout​

通常 pout>pinp_{\text{out}} > p_{\text{in}}pout​>pin​（输出更贵），所以「让模型少说废话」不仅体验好，也真的省钱。

窗口满了怎么办？常见四种策略：

💡
  • 截断（truncation）：丢掉最旧或最不相关的消息；简单，但会丢信息。
  • 压缩/摘要（compaction）：把旧对话总结成一段短摘要；保留语义，但有损且可能丢细节。
  • 检索（RAG）：不把全部资料塞进去，只取与当前问题最相关的片段。
  • 滑动窗口：只保留最近 kkk 轮；实现简单，适合长对话但不利于长期记忆。

还有个工程细节：模型对上下文中间部分的利用率往往低于开头和结尾，这就是「lost in the middle」。所以重要的约束（system prompt、关键资料）应放在显眼位置，而不是埋在一大段历史中间。

不同模型的 tokenizer 不同，同一个字符串在不同模型上的 token 数可能不一样。做成本估算时要用目标模型自己的 tokenizer，不能拿一个模型的计数套另一个。

🛠️

动手

在 playground 里做三个实验：

  1. 输入 你好，世界，记下 token 数与 id；再输入 hello world，比较谁更省。
  2. 不断追加句子，直到进度条变红——观察「超窗」提示，思考此时 harness 应该截断、摘要还是检索。
  3. 输入一个很长的英文单词（如 internationalization），观察玩具分词器与真实 BPE 的差异。

成本估算练习：某模型输入单价 3 美元/百万 token，输出单价 15 美元/百万 token。一次请求输入 10,000 token、输出 1,000 token：

cost≈10000×3106+1000×15106=0.03+0.015=0.045 美元\text{cost} \approx \frac{10000 \times 3}{10^6} + \frac{1000 \times 15}{10^6} = 0.03 + 0.015 = 0.045\ \text{美元}cost≈10610000×3​+1061000×15​=0.03+0.015=0.045 美元

一个 harness 若每轮都把完整历史重发，10 轮后的输入成本会远高于单轮——这就是上下文管理的经济动机。

text
budget = C - reserve_output
if used_tokens(messages) > budget:
    messages = [system] + summarize(old_messages) + recent_messages
⚠️

截断与摘要都是有损的。对需要精确引用的任务（合同、日志、代码），优先用检索把原文片段放回去，而不是依赖摘要。

要点回顾

  • 模型按 token 读写与计费；token 是子词片段，不等于字或词。
  • BPE 通过反复合并高频 pair 构建词表，高频片段省 token，罕见词被拆开。
  • 上下文窗口是硬预算：system、历史、工具结果、输出全都算。
  • 超窗策略：截断、摘要压缩、检索、滑动窗口；都有信息损失，需按任务选择。
  • 成本约等于输入 token 乘输入单价加输出 token 乘输出单价。
